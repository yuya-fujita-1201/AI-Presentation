# RAGのパイプライン

RAGの解説を2つ3つ読むと、たいてい最初に混乱する。ある解説は「3ステップ」と言い、別の解説は「4段階」、また別の解説は「5段階」と言う。どれが正しいのかと考え始めると先に進めない。

結論から言えば、**どれも間違っていない**。違うのは粒度と関心であって、指している処理そのものは重なっている。この節では、まず数え方の食い違いを並べて見比べ、次にそれらを1つの図に統合し、最後に「そもそも段に分けて考えると何が得か」を示す。

## 数え方は資料によって違う

| 資料 | 数え方 | 内訳 |
|---|---|---|
| [Supabase自作RAG](../sources/video-rag-supabase-diy-chatbot.md) | 3ステップ | ドキュメントを事前に変換して保管 → 質問に関係する文書を検索 → 取ってきた文書を渡して回答生成 |
| [RAGの歴史・仕組み・限界](../sources/video-rag-history-mechanism-limits.md) | 4段階 | インデクシング → リトリーバル → ランキング（再ランキング） → ジェネレーション |
| [Ollamaローカル型RAG](../sources/video-rag-ollama-local-privacy.md) | 5段階 | 取り込み → 分割 → ベクトル化 → 検索 → 生成 |
| [社内文書RAGの作り方2026](../sources/article-rag-todoonada-pipeline-guide.md) | 4段 | パース → 埋め込み → 検索 → リランク |

見比べると性格の違いが分かる。3ステップは「何が起きているか」を最短で説明する粒度、5段階は事前準備を細かく割った粒度である。最後のTodoONada株式会社の4段は、生成そのものを数に入れていない。これは同社が**精度を左右する工程に絞って**構成を論じているためで、実際に同社は「RAG精度を決めるのはLLM本体ではなく、パイプライン設計です」という立場を明示している（[社内文書RAGの作り方2026](../sources/article-rag-todoonada-pipeline-guide.md)）。

なお、4段階を挙げる動画の説明はauto字幕を出所とするため、ここでは「標準的なRAGパイプラインはインデクシング・リトリーバル・ランキング・ジェネレーションの4段階に分かれると説明している（聞き取り）」という帰属の形で扱う。5段階についても同様に、「取り込み・分割・ベクトル化・検索・生成の5段階に分解して説明している（聞き取り）」という形で扱う。

## 2つの時間軸に置き直す

食い違いは、**処理が走るタイミング**で並べ直すと解消する。RAGの工程は、質問が来る前に済ませておくものと、質問が来てから走るものに分かれる。

**事前準備（オフライン。資料を入れたときに1回）**

1. **取り込み・パース** — PDFやWord、スプレッドシートから文字と構造を取り出す
2. **分割（チャンク）** — 検索できる大きさの塊に切る
3. **ベクトル化（埋め込み）** — 各チャンクを意味を表す数値の列に変換する
4. **格納** — ベクトルデータベースなどの索引に入れる

**応答（オンライン。質問が来るたび毎回）**

5. **検索（リトリーバル）** — 質問も同じ方法でベクトル化し、意味の近いチャンクを複数拾う
6. **再ランク（リランキング）** — 拾った候補を精度の高いモデルで並べ替え、上位だけに絞る
7. **生成（ジェネレーション）** — 絞り込んだチャンクと質問を1つのプロンプトにまとめ、LLMに答えさせる

先ほどの4つの数え方は、この7工程のどこをまとめ、どこを省いたかの違いにすぎない。3ステップは1〜4を「保管」に、5〜6を「検索」にまとめたもの。5段階は格納を分割・ベクトル化に含めたもの。TodoONadaの4段は7（生成）を数に入れていないもの、と読める。

## 各段が担う仕事

### 取り込み・パース

TodoONada株式会社は、日本語の企業文書のパースには三大障害があるとし、PDFレイアウト崩れ・罫線帳票・スキャン画像を挙げている。同社はこの工程を「最初にして最大の難所」と位置づけ、鉄則として「パース品質を先に目視確認してから次へ進む」ことを挙げる。本文と表が正しく取れているかを人間の目で確認しないと「RAG全体が砂上の楼閣になります」と警告している（[社内文書RAGの作り方2026](../sources/article-rag-todoonada-pipeline-guide.md)）。

同社はパースツールとして3系統を挙げている。IBM発OSSのDoclingは表・図・レイアウト・数式を含む文書理解に強く、PDF/DOCXに対応する。YomiTokuは縦書き・帳票に強い一方、**CC BY-NC-SA非商用ライセンスのため商用利用には別契約が必要**である。画像をそのままLLMに読ませるVLM直読みも選択肢の一つとして挙げられている。ライセンス条件は業務判断に直結するため、採用前に必ず現物を確認したい。

新入社員がまず覚えるべき勘所はここである。派手なのは検索や生成だが、壊れやすいのは入口である。

なお、日本語文書の三大障害（レイアウト崩れ・罫線帳票・スキャン画像）のうち罫線帳票やスキャン画像への発展的な対処として、画像や表を含む文書から情報を抽出する**マルチモーダルRAG**の研究も進んでいるとされる（[RAGの歴史・仕組み・限界](../sources/video-rag-history-mechanism-limits.md)）。

### 分割（チャンク）

チャンクサイズには小さすぎると文脈が失われ、大きすぎると情報が薄まるというトレードオフがある。セマンティックチャンキングやオーバーラップといった対策の詳細は[チャンク分割と埋め込み](chunking-and-embedding.md)で扱う。

### ベクトル化（埋め込み）

**会話用のLLMと埋め込みモデルは別物**であり、日本語文書では埋め込みモデルの対応言語を最初に確認しておく必要がある。選び方の詳細は[チャンク分割と埋め込み](chunking-and-embedding.md)で扱う。

### 検索

なぜベクトルにするのかは、キーワード検索と比べると分かりやすい。普通のキーワード検索は語が一致するかどうかで探すため、「疲れた」で検索しても「体が重たい」という文章は引っかからない。ベクトル検索は文書の意味を数値で表現して保存するため、語が違っても意味が近い文章を拾える——という対比で説明されている（[Supabase自作RAG](../sources/video-rag-supabase-diy-chatbot.md)）。

### 再ランク

最初の検索結果に残るノイズを、計算コストの高いモデルで関連性の高い順に並べ替えて絞り込む段である。国産リランカーは軽量で費用対効果が高いとされる。仕組みと評価の詳細は[検索とリランキング](retrieval-and-reranking.md)で扱う。

### 生成

選び抜かれたチャンクと元の質問文を組み合わせ、1つのプロンプトとしてLLMに入力する。これによりLLM単体の内部知識では答えられなかった最新情報や専門分野の質問にも、根拠を持って答えられるとしている（[RAGの歴史・仕組み・限界](../sources/video-rag-history-mechanism-limits.md)）。

この段では、プロンプトに「資料に書いてないことは答えないで」という制約を加えることで、ある程度ハルシネーションを防げるとされている（[Supabase自作RAG](../sources/video-rag-supabase-diy-chatbot.md)）。

## 段に分けて考える3つの実利

**1. 壊れた場所を特定できる。** 「RAGの精度が悪い」は診断名ではない。取り込みで表が崩れているのか、分割で文脈が切れたのか、検索が拾えていないのか、拾えているのにLLMが読み落としているのか——段に分けて初めて、次に何を直すかが決まる。

**2. データを外に出すかどうかの判断が具体的になる。** パイプラインを段ごとに分解して初めて、どこにリスクがあるかを具体的に検討できるようになる。外出し判断の詳しい考え方は[入れる前と入れた後](governance-and-adoption.md)で扱う。

**3. 精度の効きどころが段ごとに違う。** 実際、精度を上げるコツとして挙げられているのは、チャンクサイズの調整・プロンプトへの制約付与・検索件数の調整の3点であり、いずれもモデルの差し替えではない。なお検索件数を増やすとコストも処理時間も増えるため微調整が必要だとされている（[Supabase自作RAG](../sources/video-rag-supabase-diy-chatbot.md)）。

## この節の要点

- 工程の数え方（3・4・5）の違いは粒度と関心の差であり、矛盾ではない
- 事前準備（取り込み→分割→ベクトル化→格納）と応答（検索→再ランク→生成）の2軸で並べ直すと統合できる
- 入口のパース品質は最も壊れやすく、目視確認が鉄則とされている
- 会話用のLLMと埋め込みモデルは役割が別で、日本語文書では埋め込みモデルの対応言語を先に確認する
- 段に分ける実利は、故障箇所の特定・情報を外に出す範囲の判断・精度の効きどころの見極めの3つである
