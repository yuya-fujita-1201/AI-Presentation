# 作るか借りるか

RAGには決めるべきことが山ほどある。チャンクサイズ・オーバーラップ・埋め込みモデル（[チャンク分割と埋め込み](chunking-and-embedding.md)で扱う）、ハイブリッド検索・リランカー・取得件数（[検索とリランキング](retrieval-and-reranking.md)）、評価セットの設計（[評価](evaluation.md)）——いずれも本節の判断より下の階層にある論点で、ここでは中身を知らないまま読み進めてかまわない。

これを全部自分で決めるのか、それとも誰かが決めた既製品に乗るのか。それが実装方式の選択である。

ここで注意したいのは、**この選択が「安いか高いか」でも「簡単か難しいか」でもない**という点である。既製品に乗れば決めるべきことは減るが、同時に**直せる場所も減る**。RAGは[7つの失敗点](failure-modes.md)で見た通り、段ごとに壊れる。壊れた段に手が届かない構成を選べば、そこは永久に直せない。

だから比較の軸は一本でよい。**何が自分の手に残るか**である。

## 選択肢A: マネージド型（ホスト型ツール）

クラウドベンダーが検索の実装ごと引き受ける方式である。

**OpenAI File search** は、Responses APIで利用可能なホスト型ツールとして提供されている。公式ドキュメントは「By creating vector stores and uploading files to them, you can augment the models' inherent knowledge」（ベクトルストアを作成しファイルをアップロードすることで、モデル本来の知識を拡張できる）と説明しており、検索の実行自体はOpenAI側が管理するため開発者がコードで検索処理を実装する必要はなく、モデルがツール使用を判断すると自動的に呼び出される仕組みだとしている（[File search | OpenAI API](../sources/article-rag-openai-file-search.md)）。

つまり**[パイプラインの段](rag-pipeline-stages.md)のほとんどが見えなくなる**。ファイルを入れれば、分割も埋め込みも検索も向こう側で終わっている。ドキュメントは検索の仕組みを「semantic and keyword search」と総称するのみで、クエリ書き換えの内部処理の詳細は明記されていないとしている。手元に残る調整項目は限られており、検索結果数を制限する `max_num_results`（トークン使用量とレイテンシの両方の削減に効くとされる）と、メタデータによる絞り込みの `filters` が挙げられている。対応ファイル形式はPDF・DOCX・TXT・JSON・Markdownなど23種類以上、テキスト形式はutf-8/utf-16/asciiのいずれかが必須。レート制限はTier 1で100 RPM、Tier 2〜3で500 RPM、Tier 4〜5で1000 RPMと段階設定されているとしている。

**Google Cloud Agent Search** のAnswer Generation APIは、同じくホスト型だが**接地ソースを選べる**点に特徴がある。公式ドキュメントは接地ソース（Grounding Sources）として3種類——Google Search（世界知識や最新情報に接続したい場合）、インラインテキスト（最大100個のfact textを直接指定）、Agent Search data stores（エンタープライズドキュメント）——を挙げ、複数組み合わせる場合は最大10個まで指定できるとしている（[Generate grounded answers with RAG | Agent Search](../sources/article-rag-google-cloud-grounded-gen.md)）。

同ドキュメントで実務上おもしろいのは**動的取得（Dynamic Retrieval）**である。Google Searchを接地ソースに使う場合、0〜1の予測スコアとしきい値を設定でき、「If the prediction score is greater than or equal to the threshold, the answer is grounded with Google Search.」——予測スコアがしきい値以上のときにのみ検索が実行されるとしている。デフォルトのしきい値は0.7で、必要な場合にのみ外部検索を走らせる設計である。**毎回検索しない**という判断が組み込まれている点は、RAGを「常に検索する仕組み」と捉える素朴な理解を一段更新するものである。

レスポンスには grounding score、回答を支える supportChunks、claim textと支持チャンクを対応づける groundingSupport が含まれるとされる。根拠の透明性という観点では、[評価](evaluation.md)で見た「どの文書を根拠にしているか」の確認材料が構造化されて返ってくることになる。

一方で制約もある。同ドキュメントは複数ターンの会話について「in each request you must send all the text exchanged between the user and the model in all the previous turns」——過去のやり取り全文を毎回のリクエストに含める必要があると明記している。会話が長引けば送るテキストは膨らみ続ける。

## 選択肢B: OSSエンジン（セルフホスト）

取り込みから回答生成までを一体で提供するソフトウェアを、自分たちのサーバーで動かす方式である。

RAGFlowを紹介する動画は、これをリポジトリ名「infiniflow/ragflow」で公開されているオープンソースのRAGエンジンだとしている（聞き取り）（[RAGFlow入門](../sources/video-rag-ragflow-oss-intro.md)）。同動画は、公式の説明として「最先端のRAGとエージェント機能を融合させ、大規模言語モデルにとって優れたコンテキスト層を作る」という位置づけが掲げられていると紹介し、**主役はモデルではなく「モデルに何を渡すか」の部分**だと解説している。

この方式の位置を理解するには、同動画の類似ツール比較が分かりやすい。LangChainやLlamaIndexは検索や連携の**部品を提供するライブラリ**であり、自由度が高い代わりに組み合わせと調整は開発者の仕事になる。Difyは**アプリ構築基盤**で、アプリの見た目や配布に重心が置かれている。対してRAGFlowは知識ベースの管理から検索・回答生成までを備えた実用前提のエンジンとして完結しており、検索の精度と分割の設計そのものに重心があるとしている。同動画はこれを優劣ではなく「**部品から組みたいのか、動く土台から始めたいのか**」という選択だと位置づけている。この一言が、本節の軸そのものを言い当てている。

ライセンスについて、同動画はRAGFlowがApache 2.0で公開されており商用利用・改変・社内システムへの組み込みが認められているとしている（聞き取り）。ただし無条件ではなく、配布する際には著作権表示とライセンス本文の同梱が必要で、改変を加えた場合はその旨を示すことが求められるとも述べている。プロジェクトの活発さについては、リポジトリ公開が2023年12月12日、獲得スター数が8万5718、最新リリースがV0.264（2026年7月7日公開）だとしている（聞き取り）。ライセンス条件とバージョン番号は業務判断に直結するため、**採用前に公式リポジトリで現物を確認すべき事項**である（動画の数値は視聴時点のものであり、スター数やバージョンはその後も動く）。

同動画は注意点も挙げている。セルフホストはコンテナ前提の構成であり、文書の取り込みや検索用索引の作成はそれなりに資源を使うため、メモリやディスクに余裕のない小さなサーバーに載せると取り込み処理の途中で詰まりやすくなる。リリース間隔が短めなので、バージョンは明示的に固定し、上げる際は検証してから行うのが基本だとしている。試し方としては、まず公式のクラウド版で自分たちの文書を入れて検索結果と回答を確かめ、手応えを掴んでから自社環境に持ち込むかを判断すれば無駄がないと勧めている。

## 選択肢C: 自作（部品を組む）

ベクトルDBとLLM APIを自分で繋ぐ方式である。かつては重い選択肢だったが、コーディング支援AIの登場で見え方が変わった。

KIZUKI PROJECTの近藤氏は、Supabase Vector（無料で使えるベクトルデータベース）とClaude Code、OpenAIを組み合わせ、自分のドキュメントに答えるチャットボットをゼロから構築する様子を実演している（[SupabaseとClaude/OpenAIで作る自作RAGシステム](../sources/video-rag-supabase-diy-chatbot.md)）。作業は3ステップ——Supabaseでベクトル保存用テーブルをSQLで作成、テキストをチャンク分割してエンベディング変換し保存、質問を受けて類似検索しClaudeに文脈を渡して回答——で、ここまでの構築におよそ15分程度を要したとしている。チャットボットはローカルで動作すればよいためデプロイは不要としている。

この方式で手元に残るものは大きい。同氏が精度を上げるコツとして挙げるのは**チャンクサイズの調整・プロンプトへの制約付与・検索件数の調整**の3点で、いずれもマネージド型では触れないか触れる範囲が限られる項目である。検索件数を増やすとコストも処理時間も増えるため微調整が必要だとしており、[検索とリランキング](retrieval-and-reranking.md)で見たトレードオフを自分の手で握ることになる。

実演中にClaude側の呼び出しがエラーとなりOpenAIへフォールバックして回答が出力される場面があったとも述べられている。**モデルを差し替えられる**のも自作の性質である。マネージド型では検索とモデルが一体なので、この切り替えはできない。

## 選択肢D: ローカル完結

外部への通信を発生させず、すべてを手元のマシンで動かす方式である。

Ollamaを使ったローカル型RAGの解説動画は、RAGの処理を「取り込み・分割・ベクトル化・検索・生成」の5段階に分解し、この全段階を手元のパソコンだけで動かせるとしている（聞き取り）（[Ollamaローカル型RAGの作り方](../sources/video-rag-ollama-local-privacy.md)）。動画は、外部のAIに検索を頼ると2つの問題にぶつかると説明する。ひとつは応答速度・安定性に関わるレイテンシのばらつき、もうひとつは**社外に出せない文書そのものを扱えるかどうか**という、より根本的な制約である（いずれも字幕の表記が乱れており、文脈からの解釈）。

コスト構造も他と異なる。同動画は、処理を手元で完結させれば使用量に応じた課金は発生せず、かかるのは電気代と自分のマシン代だけだとし、課金を気にせずいくつものモデルを気軽に試せる利点があるとしている。一方で落とし穴として、会話用のLLMと埋め込みモデルの取り違えを挙げている（この論点の中身は[チャンク分割と埋め込み](chunking-and-embedding.md)で扱う）。

規模別の現実的な構成については、TodoONada株式会社が個人〜小規模向けにOllama＋AnythingLLM／Open WebUI内蔵RAGを挙げ「半日で立つ」としている。AnythingLLMはMITライセンスでRAG＋エージェント主機能をゼロ設定で使えるとされる。部門規模向けにはvLLM＋ハイブリッド検索＋リランカーを標準構成として、精度と速度の両立を図るとしている（[社内文書RAGの作り方2026](../sources/article-rag-todoonada-pipeline-guide.md)）。埋め込みについても国産オープンモデルの成熟により、**ローカル完結＝精度を諦める、という等式はもう成り立たない**というのが同社の立場である（詳しくは[チャンク分割と埋め込み](chunking-and-embedding.md)）。

## 4択を1枚に

| | A マネージド | B OSSエンジン | C 自作 | D ローカル完結 |
|---|---|---|---|---|
| 代表例 | OpenAI File search / Google Cloud Agent Search | RAGFlow | Supabase＋LLM API | Ollama＋AnythingLLM |
| 分割・埋め込みの調整 | ほぼ不可 | エンジンの設定範囲で可 | 自由 | 自由 |
| 検索方式の差し替え | 不可（内部仕様） | 可 | 自由 | 自由 |
| モデルの差し替え | 不可〜限定的 | 可 | 自由 | 自由 |
| 文書の外部送信 | あり | 自社サーバー内 | ベクトルDBとLLMに依存 | なし |
| 立ち上げの速さ | 最速 | 中（コンテナ運用） | 早い（支援AI活用時） | 中 |
| 継続的な運用負荷 | 最小 | インフラ＋バージョン管理 | 自前で全部 | マシン管理 |
| 主な制約 | レート制限・内部仕様が不透明 | 資源消費・更新頻度 | 自分で全部決める必要 | マシン性能 |

表を縦に読むと、**AからDへ行くほど手元に残るものが増え、同時に自分の仕事も増える**。これは当然のトレードオフに見えるが、重要なのは[失敗モード](failure-modes.md)との関係である。FP2（検索が拾えない）やFP3（コンテキストに載らない）が出たとき、Aでは`max_num_results`と`filters`くらいしか手がない。B〜Dなら検索方式そのものを変えられる。**将来出るであろう故障に対して、自分がどこまで手当てできる立場にいたいか**が、この表の読み方になる。

表の「継続的な運用負荷」行は、方式に関わらず共通して発生するコスト要素を踏まえて読む必要がある。「AIの履歴書」の解説動画は、高度なRAGシステムの構築・運用にはベクトルデータベースの運用コスト、エンベディングや再ランキングモデルの計算コスト、パイプライン全体を最適化する専門知識が必要であり、構築したシステムの性能評価自体も難しい問題だと指摘している（[RAGの歴史・仕組み・限界](../sources/video-rag-history-mechanism-limits.md)）。マネージド型（A）はこれらの一部をベンダー側に肩代わりさせる代わりに費用として支払い、B〜Dは自分たちで抱え込む、という違いとして読める。

パースツールのライセンスも導入前に必ず確認したい事項である。TodoONada株式会社は、縦書き・帳票に強いYomiTokuを紹介しつつ、**CC BY-NC-SA非商用ライセンスのため商用利用には別契約が必要**だとしている（[社内文書RAGの作り方2026](../sources/article-rag-todoonada-pipeline-guide.md)）。同社の構築前チェックリストにも「パースツールのライセンス確認（YomiToku商用利用注意）」が挙がっている。B〜Dのようにパース工程を自分たちで組む方式ほど、このライセンス確認は見落とすと後から効いてくる。

## 選び方: 段階で考える

情報の外出し判断は「クラウドか自前か」の丸ごとの二者択一ではなく、**段ごとに置き場所を選べる**（埋め込みだけローカルで作って検索はクラウド、といった中間解を含め、判断基準は[入れる前と入れた後](governance-and-adoption.md)を参照）。

ここではRAGとエージェントの違いだけ補っておく。Ollamaの解説動画は、FAQのように答えがあらかじめ決まっているケースならRAGで十分だとし、RAGを決まった手順で答えを返す仕組み、エージェントを状況に応じて動き方を自分で判断する仕組みとして区別している（聞き取り）。

実務的な決め方に落とすと、次の順で問うのがよいだろう。

1. **扱う文書に外部送信できないものが含まれるか** → 含まれるならD、または機微な段だけを手元に残す構成
2. **まず動くものを見せて判断したいのか** → AかDの小構成（RAGFlowならクラウド版で試す手もある）
3. **すでに自作していて精度に行き詰まっているか** → B（動く土台に載せ替える）
4. **調整項目を全部握って作り込みたいか** → CまたはD

RAGFlowの動画が向いている人として挙げているのも、①社内文書AIアシスタントの開発を任されたエンジニア、②すでにRAGを自作していて精度と運用の両立に行き詰まっている開発者、③社内資料を外部サービスに預けられない事情を抱える情報システム担当者、の3タイプであり、上の2〜4と概ね重なる。同動画は一方で、扱う文書が少数で完結するならここまでの仕組みは過剰かもしれないとも述べ、規模と手間の釣り合いを最初に見ておくよう注意している。

## どれを選んでも変わらないこと

最後に、4択のどれを選んでも解決しない問題を確認しておく。**入れる文書の質**である。

RAGFlowの動画が指摘する「整理は導入前にやる方が結局早い」という論点は、[入れる前と入れた後](governance-and-adoption.md)で扱う。TodoONada株式会社も構築前チェックリストの筆頭にパース結果の目視確認を置いており、その理由は[RAGのパイプライン](rag-pipeline-stages.md)で見た通りである。

つまり、方式選択で悩む前にやることがある。

## この節の要点

- 比較の軸は「何が自分の手に残るか」。既製品に乗ると決めることが減るが、**直せる場所も減る**
- A マネージド型: OpenAI File searchは検索実行をベンダーが管理し開発者のコード実装が不要。調整は`max_num_results`・`filters`程度で、内部処理の詳細は非公開
- Google Cloud Agent Searchは接地ソースを3種類から選べ（最大10個組み合わせ）、しきい値デフォルト0.7の動的取得で必要時のみ検索する。ただしマルチターンでは過去のやり取り全文を毎回送る必要がある
- B OSSエンジン: RAGFlowは「部品から組みたいのか、動く土台から始めたいのか」という選択軸で、LangChain/LlamaIndex（部品）やDify（アプリ基盤）とは重心が違うとされる（聞き取り）。ライセンスとバージョンは公式で現物確認すること
- C 自作: 支援AIを使えば構築は速い。チャンクサイズ・プロンプト制約・検索件数を自分で握れ、モデルも差し替えられる
- D ローカル完結: 課金は電気代とマシン代のみ。国産埋め込みモデルの成熟により「ローカル＝低精度」は成り立たなくなったとされる。会話用LLMと埋め込みモデルの取り違えに注意
- 丸ごとの二者択一ではなく、**5段階のうち何段を外部任せにするか**という段階的な判断で考える
- どの方式でも、入れる文書が汚ければ答えは汚い。整理は導入前にやる方が早い
