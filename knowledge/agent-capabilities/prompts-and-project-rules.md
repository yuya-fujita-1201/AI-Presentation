# プロンプトとプロジェクトルール

4つの手段のうち、いちばん手前にあるのが「言葉で足す」ことである。ファイルもサーバーも作らず、入力欄に書くだけで能力が変わる。だからこそ最初に試すべきで、同時に**いちばん早く限界が来る**手段でもある。このファイルでは、その場かぎりの**プロンプト**と、それを常設化した**プロジェクトルール**（Claude Code の `CLAUDE.md` など）を1つの連続した話として扱い、書き方の指針と、書き切れなくなる境界線を示す。

## 一言定義

**プロンプトはその場かぎりの言葉による指示、プロジェクトルールはそれをファイルに落として常設化したものである。**

## プロンプトは残らない、という性質から出発する

チャットでAIに丁寧な指示を書くと、その会話ではうまくいく。翌日、新しい会話を開くと、また同じ説明を書くことになる。この当たり前の体験が、この手段の性質そのものである。

[Anthropicの公式ドキュメント](../sources/article-tools-agent-skills-overview.md)は、Skillsとプロンプトの違いをここに置いている。

> 引用: 「Skills load on demand, so you don't have to repeat the same guidance across conversations.」

裏返せば、プロンプトは**会話単位の一時的な指示**であり、会話をまたいで持ち越されない。ここから、実務で使える簡単な判定が1つ導ける。

**同じ説明を2回以上書いているなら、それはプロンプトで済ませるべき仕事ではない。**

[CLAUDE.md運用の実務記事](../sources/article-he-claude-md-best-practices.md)も、これを短期記憶と長期記憶の対比として説明している。同記事の筆者は、`/clear` で会話履歴をリセットするとチャットログ（短期記憶）は消えるが `CLAUDE.md`（長期記憶）は読み直される、と述べたうえで、「毎回同じことを説明しているな」と感じたらそれは短期記憶にしか情報がない証拠なので、すぐに長期記憶へ書き込むべきだとしている。

## 常設化の受け皿——プロジェクトルールは「自動で読まれるファイル」

では書き込む先はどこか。公式の[Agent SDK overview](../sources/article-he-agent-sdk-overview.md)は、Skills・commands・memory がプロジェクトの `.claude/` とホームディレクトリの `~/.claude/` から**自動的に読み込まれる**と説明している。ここが、能力を常設化するための土台になる。

プロンプトとの違いは、読まれるタイミングだけである。

| | プロンプト | プロジェクトルール |
|---|---|---|
| 置き場所 | 入力欄 | リポジトリ内・ホーム配下のファイル |
| 読まれ方 | その会話でだけ | セッション開始時に自動で全文 |
| 効く範囲 | その会話 | そのプロジェクト（または全プロジェクト） |
| 消え方 | 会話を閉じたら消える | 消さない限り残る |

「セッション開始時に自動で全文」という点が重要である。Skill が必要な時だけ読まれるのに対し（[progressive-disclosure.md](./progressive-disclosure.md)）、プロジェクトルールは**毎回・無条件に・全部**読まれる。この違いが、次の落とし穴を生む。

## 落とし穴——書けば書くほど守られなくなる

初心者がまずやりがちなのが、「大事なことは全部ルールに書いておこう」である。これは逆効果になる。

[CLAUDE.md運用の実務記事](../sources/article-he-claude-md-best-practices.md)は、これを**「コンテキスト汚染」**と呼んでいる。同記事の筆者は、LLMが一度に安定して扱える「ルールの数」には限界があり、指示が増えれば増えるほど守られない指示が出てくると指摘する。そのうえで、次の目安を示している。

> 引用: 「推奨されるのは、できるだけ小さい CLAUDE.md です。目安は 300 行以下。指示としては 150〜200 個程度に収める。」

この数字は同記事の筆者が示す目安であり、公式仕様として定められた上限ではない点は押さえておきたい。ただし背後にある理屈は一般性がある。同記事はコンテキストウィンドウを人間の**ワーキングメモリ（作業メモリ）**になぞらえ、不要な情報でメモリを埋め尽くすと本当に重要なタスクに割けるリソースが減り、推論能力の低下を招くと説明している。

もう1つ、同記事が挙げる失敗パターンが**自動生成への丸投げ**である。「このリポジトリから `CLAUDE.md` を作って」と指示して生成させると、冗長でノイズの多い、「全部書いてあるけど、どれも守られない」ドキュメントになりやすいため、`/init` ベースの生成は基本的に避けたほうがよいとしている。

## 何を書くべきか——スタイルではなく「知識・罠・運用ルール」

同記事が挙げる、どんなプロジェクトでも機能しやすい3要素は次のとおりである。

1. **プロジェクトを一行で説明する**（例:「Next.jsで実装された顧客向け決済ポータル」）。リポジトリ全体を読む前に全体像を掴める一文があると、タスク理解が安定する
2. **頻繁に使うコマンドに絞る**（起動・ビルド・テスト・Lint・DBマイグレーションなど）
3. **罠を「トリガー（いつ）」＋「アクション（何をするか）」のセットで書く**

3つ目が最も効く。同記事は、悪い例「`schema.prisma` の直接編集は禁止」と、良い例「`schema.prisma` を変更したいときは、必ず `schema/*.prisma` を編集してから `pnpm build:schema` を実行すること」を対比し、具体的な行動指示（Actionable）にすることで遵守率が劇的に向上すると述べている。**禁止だけを書くと、AIは代わりに何をすればよいか分からず、別の間違った道を選ぶ。**

逆に書くべきでないものも明確である。インデント幅・クオートの種類・import順序といったフォーマットやスタイルの指示は、Lint・Formatter・Git hooks で機械的に強制する方が確実だと同記事は指摘する。**人間の言葉で頼むより、機械に落とせるものは機械に落とす**——これはプロンプトという手段の限界を認めた設計判断でもある。

## 置き場所を分ける——ルールにも段階的開示を効かせる

`CLAUDE.md` にすべてを書き切る必要はない。同記事は、DBスキーマは `docs/schema.md`、APIドキュメントは `docs/api.md`、複雑なドメインルールは `docs/domain-rules.md` のように詳細を別ファイルへ分け、`CLAUDE.md` にはその場所と概要だけを書く設計を推奨している。

これは Skill の設計原理とまったく同じ考え方である（[progressive-disclosure.md](./progressive-disclosure.md)）。**段階的開示は Skill だけの仕組みではなく、コンテキストという有限資源を扱うときの一般解**だと捉えるとよい。

スコープの使い分けも整理しておく。[Claude Code Skillの運用記事](../sources/article-tools-claude-code-skill-design.md)は、Skill の配置優先順位を「Enterprise > Personal > Project」の順で上位が優先されるとし、Personal（`~/.claude/skills/`）は全プロジェクトに、Project（`.claude/skills/`）はそのプロジェクトのみに適用されると説明している。ルールファイルも同じ発想で、全プロジェクト共通の作法はホーム配下、そのリポジトリ固有の罠はリポジトリ内、という置き分けになる。加えて[CLAUDE.md運用の実務記事](../sources/article-he-claude-md-best-practices.md)は、Claude Code が親・サブディレクトリの `CLAUDE.md` も自動探索する特性を使い、モノレポではルートに共通ルール・各パッケージ配下に固有ルールを置く構成や、個人用設定をコミットせず `claude.local.md`（`.gitignore` 対象）に書く運用を紹介している。

なお同記事は、Claude Code のシステムメッセージに「`CLAUDE.md` の文脈はタスクと無関係な場合がある」という前提が含まれており、状況によって一部が意図的に無視されることがあるとも述べている。**ルールに書けば必ず守られる、という保証はない。** そのうえで、LLMは入力の先頭と末尾を強く重み付ける傾向があるため、本当に守ってほしいことは冒頭に書き、「IMPORTANT」などで明示的に強調するのが有効だとしている。

## 会話は下流に届かない——サブエージェントという落とし穴

もう1つ、言葉で足すことの限界がはっきり出る場面がある。作業を別のエージェントに切り出したときである。

[サブエージェント解説動画](../sources/video-ge-subagent-overview-basics.md)は、サブエージェントがメインから受け取る情報はエージェント定義・タスク指示・作業ディレクトリ等の環境情報・skillsフィールドで指定したスキル内容・永続メモリの5つに限られ、**メインの会話履歴は一切受け取らない**と説明している（[22:00]、聞き取り）。同動画はまた、Claude Code の機能を「実行主体／能力（スキルとMCP）／ルール・環境（`CLAUDE.md` やフック）」の3つに整理すると分かりやすい、という見方を私見として述べている（聞き取り）。

つまり、**チャット欄で口頭合意した前提は、下流のサブエージェントには届かない**。届かせたいなら、ファイルに書いてあるもの（ルール・Skill・タスク指示）に載せるしかない。これは「その場のプロンプトで済ませるか、常設化するか」を分ける、もう1つの実務的な判定基準になる。

## どこで書き切れなくなるか——次の手段への移行線

言葉だけで足りなくなるサインは、おおむね3つに集約される。

- **同じ説明を毎回書いている** → プロジェクトルール、または[Skill](./what-are-agent-skills.md)へ
- **手順が長く、補助ファイルやスクリプトが要る** → [Skill](./what-are-agent-skills.md)へ。ルールに全部書くとコンテキスト汚染になる
- **手を動かす先が外部サービスにある** → [MCP](./what-is-mcp.md)、またはCLI

判断そのものは[choosing-skill-mcp-or-cli.md](./choosing-skill-mcp-or-cli.md)で扱う。ここで押さえておきたいのは順番である。**プロンプトで試す → 効いた指示だけをルールに常設化する → 手順とスクリプトが要るならSkillに切り出す**。この順で進めると、最初から作り込むより早く、しかも無駄が少ない。効くかどうか分からない指示をいきなりSkillにするのは、たいてい遠回りになる。
