# WebMCPとこれから

## 一言定義

**WebMCPとは、ページ自身がAIエージェントにツールを公開する提案であり、まだ標準として確定していない。**

## 何を解決しようとしているのか——「画面から推測する」の壊れやすさ

AIエージェントにWebサイトを操作させたことがある人なら、うまくいったりいかなかったりする感覚に覚えがあるはずだ。同動画は、その原因をこう整理している（聞き取り）。

従来のサイト操作は、画面の文言とDOM構造を対応づけ、目的の要素をセレクタや位置から探すという、**複数の推測処理の積み重ね**だった。サイトが更新されてボタンの文言やDOMの入れ子、レイアウトが変わると、それまで効いていた手がかりが外れ、エージェントは別の候補を再試行することになる。壊れやすさは「操作の意味を画面から推測する部分」に集中しており、手順が長いほど探索と再試行が増える。

ここで発想が反転する。**推測させるのをやめて、サイト側が「これができます」と構造化して申告すればよい**——これがWebMCPの出発点である。

## ツールの形——4つの要素

同動画によれば、サイト側は `document.modelContext` の `registerTool` を通じて、公開したい操作をツールとして登録する。ツールは次の4要素で構成されるとしている（聞き取り）。

| 要素 | 中身 |
|---|---|
| `name` | 操作を識別する名前 |
| `description` | 自然言語での用途説明 |
| `inputSchema` | JSON Schema による入力形式 |
| `execute` | 引数を受けて既存機能を呼ぶ実行処理 |

**この4要素はSkillのSKILL.mdとよく似た構造をしている**。`name` と `description` で「何ができて、いつ使うか」を宣言し、本体は別に置く——[writing-good-skills.md](./writing-good-skills.md)で扱った「description が起動を決める」という論点は、そのままここにも当てはまる。AIに能力を足す仕組みは、置き場所が変わっても**宣言と実体を分ける**という形に収束しているように見える。

同動画は、ツールがページの状態に応じて動的に増減でき、ログイン前後や選択中の対象によって公開するツールを変えられること、取り消しには `AbortSignal` を使うことも紹介している（聞き取り）。登録方法にはJavaScriptによる命令型のほか、HTMLフォームをもとにした宣言型も提案されているが、**宣言型は命令型ほど仕様が固まっておらず、呼び出し側（`getTools`・`executeTool`）の仕様も未確定（TODO）**だとしている。

## サーバー側MCPとの役割分担

[what-is-mcp.md](./what-is-mcp.md)で見たとおり、MCP公式ドキュメントはMCPを**Host / Client / Server**のクライアント・サーバー型として定義し、ローカルプロセス間の Stdio transport と、リモート通信の Streamable HTTP transport という2つの通信経路を規定している（[Architecture overview](../sources/article-tools-mcp-architecture-overview.md)）。

WebMCPはこの置き換えではない。同動画は、切り分けの軸を**「接続先」と「実行場所」**の2つだと説明している（聞き取り）。

| | サーバー側MCP | WebMCP |
|---|---|---|
| 接続先 | 画面やタブを介さず外部からサービスへ | 開いているページ自身 |
| 実行場所 | サーバー側 | そのページのブラウザ内 |
| 向く場面 | ブラウザを開いていない状態でサービスに繋ぐ | 今の画面や訪問者の権限を使いたい |

同じサービスが両方を併用する構成も成立する、と同動画は述べている。またWebMCPは**MCP通信全体をブラウザに移したものではなく**、生成元ごとの境界やPermissions Policyといったブラウザ固有の制約に合わせて、ページ内の操作公開に絞って設計されているとしている（聞き取り）。

この整理は、MCP公式側の記述とも矛盾しない。公式ドキュメントは「MCP focuses solely on the protocol for context exchange—it does not dictate how AI applications use LLMs or manage the provided context.」と、**規定する範囲を意図的に限定している**と明言している。規格が薄く保たれているからこそ、その外側に別の公開経路を足す提案が出てくる余地がある、と読める。

## ベンダー実装は標準そのものではない

同動画は、WebMCPが提案段階である一方、Cloudflareが既存サイトへの橋渡し機能をDeveloper Previewとして提供していると紹介している（聞き取り）。管理画面の Agent Readiness > Labs で Enable WebMCP を有効にすると、HTMLRewriter が橋渡し用スクリプト（`bridge.js`）を挿入し、選択した Tool packs を `document.modelContext` へ登録する仕組みだとしている。

Tool packs は2種類あるとされる。画像のC2PA来歴情報をエージェントへ渡す「Content Credentials」（**署名を新規生成する機能ではない**）と、サイト自身のMCPサーバーが公開したツールをCloudflareが中継する「Site MCP server」である。同動画は、**いずれもWebMCPの標準そのものではなくCloudflare独自の実装だ**と繰り返し強調している（聞き取り）。

提案段階の技術を評価するときの一般的な注意として押さえておきたい。**「動くデモがある」ことと「標準が決まった」ことは別である。** ベンダー実装を見て仕様を理解したつもりになると、後で食い違う。

## まだ決まっていないこと

同動画が挙げる未確定の論点は、どれも実運用の可否に直結する（聞き取り）。

- **公開範囲**: ツールを誰に見せるかはiframeの生成元によって変わり、最上位文書と同じ生成元のiframeは既定で利用できる想定だが、異なる生成元は `allow` 属性で `tools` を明示的に委譲する必要があるとされる。公開先をエージェントの生成元単位で絞る `exposedTo` という案もあるが、**これも提案中で確定していない**
- **権限**: WebMCPを有効にしても権限が自動で増えることはなく、実行に使われるのは訪問者が既に持つログイン状態と権限のみとされる。Permissions Policy で `tools` を空にすると、その文書はツールを公開できなくなるとも説明されている
- **確認の責任者**: 副作用のある操作を実行する前の確認を、**ブラウザとエージェントのどちらが担うかは未決**である
- **説明の信頼性**: 悪意あるページがツール名や説明・戻り値でエージェントの判断を誘導する懸念が論点に挙がっている

最後の1点は、このバンドル全体に効く指摘である。同動画は締めくくりで、**標準化されるのはツールの「受け渡し方」だけであり、ページが何を書くか・悪意ある説明にどう備えるかは別途決まっていく論点だ**としている（聞き取り）。これは[distribution-and-governance.md](./distribution-and-governance.md)で見た、悪意あるSkillのリスクとまったく同じ構造である。**説明文が起動を決める仕組みは、説明文が嘘をつける仕組みでもある。** Skill・MCP・WebMCPのどれを使うにせよ、この問題は形式では解けず、入手元の信頼という運用側の話に落ちる。

## 今どうなっているか——製品対応は確認できていない

検証手段について同動画は、Chromeでの公開試験（origin trial）の対象は **Chrome 149 から 156** であり、Cloudflareの検証文書に残る Chrome 146 という数字は古い記述で公開試験の対象ではないと訂正している（聞き取り）。公開サイトでの試験にはChromeのorigin trial登録、ローカル試験にはChromeのflags画面での enable WebMCP testing という別々の入口があるとしている。Cloudflare Browser Run も使え、`wrangler browser create` でセッションを作り `navigator.modelContextTesting` の `listTools`・`executeTool` で試験的に呼び出せるが、**これはページ作者が使う `document.modelContext` とは別の試験専用の入口**であり、試験で呼べることと一般製品での採用は別問題だと注意を促している。

そして最も重要な現状認識がこれである。同動画は、**Claude・ChatGPT・Gemini・PerplexityがWebMCPを実際に呼べるかどうかは、対応を肯定も否定もできる一次資料が見当たらず、公式には確認できていない**と明言している（聞き取り）。

つまり、2026年8月時点で「WebMCP対応サイトを作れば主要AIが使ってくれる」とは言えない。**本ファイルの内容に基づいて今日着手すべき実装作業はない。**

## それでも読んでおく理由

では読む意味は何か。3点ある。

1. **「足す側が誰か」が変わる兆しである**。ここまでの4手段は、すべて**使う側**が能力を足していた。Skillを書くのも、MCPサーバーを繋ぐのも、CLIを入れるのも自分である。WebMCPは、**サービス提供側**が「AIエージェント向けにこう使ってください」と申告する形を提案している。もし定着すれば、自社サービスの側に検討事項が発生する
2. **設計の型が繰り返されていることが分かる**。`name` + `description` で宣言し、実体は別に置く——Skill・MCPのツール定義・WebMCPが同じ形をしている。この型を理解しておけば、次に出てくる仕組みも同じ枠で読める
3. **未確定の技術を評価する練習になる**。提案とベンダー実装の区別、試験用の入口と本番の入口の区別、「対応している」と「確認できていない」の区別。**確認できていないことを確認できていないと書ける**かどうかは、技術選定の質をそのまま左右する
