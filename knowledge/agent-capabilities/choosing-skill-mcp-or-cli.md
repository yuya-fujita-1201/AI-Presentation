# Skill・MCP・CLIのどれを選ぶか

「AIにGitHubを操作させたい」「AIにCodex CLIを呼ばせたい」——こうした用事に対して、[what-are-agent-skills.md](./what-are-agent-skills.md) のSkillでも、[what-is-mcp.md](./what-is-mcp.md) のMCPでも、単にCLIコマンドを叩かせるやり方でも実現できてしまう。**同じことが3通りでできる**のが、この分野の分かりにくさの正体である。

このファイルは、その3つを選び分けるための判断軸を扱う。結論を先に言えば、軸は2つしかない。**常時いくら払うか（コンテキストコスト）**と、**処理が即応か長時間か**である。

## 一言定義

**Skill・MCP・CLIのどれを選ぶかは、常時払うコンテキストコストと処理が即応か長時間かの2軸で決まる。**

## 前提：3つの手段は同じ土俵に立っていない

まず整理しておくと、3つは対等な選択肢ではない。

| 手段 | 実体 | 何のためのものか |
|---|---|---|
| **Skill** | ファイルシステム上のフォルダ | AIに**手順**を教える |
| **MCP** | 別プロセスで動くサーバー＋通信規格 | 外部サービスに**接続**する |
| **CLI** | OSにインストール済みのコマンド | 既存の**道具**をそのまま使わせる |

解いている問題が違う。それでも選択の問題が生じるのは、**「外部の何かをAIに使わせる」という目的が3つとも満たせてしまう**からである。たとえばGitHubを操作させたいとき、GitHub MCPサーバーを繋いでもいいし、`gh` コマンドの使い方を書いたSkillを置いてもいいし、単に「`gh` を使え」と指示するだけでもいい。

なお、CLIは3つの中で唯一「新しく作るもの」がない。**すでにOSに入っている道具をAIに叩かせるだけ**であり、AIがコマンドを実行できること自体は[Agent SDK overview](../sources/article-he-agent-sdk-overview.md)がBuilt-in tools（ファイル読み書き・コマンド実行・Web検索）として挙げている標準機能である。

### CLIとは何か

Skill・MCPは「新しく用意するもの」だが、CLIだけは違う。AIにコマンド実行という標準機能を与えれば、あとは**すでにOSにインストール済みの既存の道具（`gh`・`aws`・`docker`・`ffmpeg`等）を、そのまま呼ばせるだけ**である。専用の接続規格もフォルダも要らない。ゼロが固定費である理由（軸1で扱う）は、この「何も新しく足していない」という性質そのものに由来する。

この単純さゆえに、CLI側の設計論点は1つに集約される。**LLMの事前知識は古くhallucinationしやすいので、コマンドの正しい使い方をモデルの記憶に頼らせず、`help`を毎回叩かせて確認させる**という安全弁である。[google/skills解説動画](../sources/video-tools-google-skills-marketplace.md)が紹介するgcloud CLI Skillのように、helpコマンドを持つツールであれば、Skill側に「まず`help`を叩いてから実行する」という一手間を書き込むことで、CLIそのものは何も変更せずにhallucinationを防げる（詳しくは後述）。

## 軸1：常時いくら払うか

最も効く判断材料はコンテキストコストである。3手段の課金方式はまったく違う。

| 手段 | 接続・設置しているだけで払うコスト | 使ったときに払うコスト |
|---|---|---|
| **Skill** | name + description のみ（1つあたり約100トークン） | SKILL.md本文（目安5,000トークン未満）＋参照ファイル |
| **MCP** | **接続中のサーバーのツール定義が常に載る** | 実行結果 |
| **CLI** | **ゼロ**（何もインストールされていないのと同じ） | コマンドの出力のみ |

Skillの側は[Anthropicの公式ドキュメント](../sources/article-tools-agent-skills-overview.md)が明記している。「until a Skill is triggered, only its name and description occupy context」——起動されるまで、Skillはnameとdescriptionしかコンテキストを占めない。約100トークンである。詳しくは[progressive-disclosure.md](./progressive-disclosure.md)を参照。

**問題はMCPの側である。**[MCP公式ドキュメント](../sources/article-tools-mcp-architecture-overview.md)が示すとおり、各プリミティブは `*/list`（発見）してから `tools/call`（実行）する2段構えになっている。裏を返せば、**接続している間ずっと、そのサーバーが公開する全ツールの定義がコンテキストに載り続ける**。使わなくても払う、定額の固定費である。

この固定費が実際どれくらいかを実測した報告がある。[Claude CodeからCodex CLIを呼ぶ手段を比較した記事](../sources/article-tools-codex-cli-mcp-vs-skill-bash.md)は、5サーバー58ツールという構成で**約55,000トークンを消費した**としている。1サーバーあたり1万トークン強、1ツールあたり1,000トークン弱という計算になる。

この数字の意味を掴むために並べてみる。同じ枠にSkillなら約550個の name+description が入る。**「便利そうだからMCPサーバーを5つ繋いでおく」は、Skillを550個置くのと同じコストを毎回払っている**ということである。[Claude Skills入門動画](../sources/video-tools-claude-skills-beginner-guide.md)がMCPは毎回余計な情報も読み込むためトークン消費が大きくなる問題があったと指摘している（[17:00]、聞き取り）のは、この構造を指している。動画側はauto字幕由来だが、公式の2段構え設計と実測記事の55,000トークンが同じ方向を向いており、**3つの独立した出所が整合する**。

### 実務的な帰結

- **使っていないMCPサーバーは切る。**固定費なので、繋ぎっぱなしは純損である
- **「とりあえず入れておく」が成立するのはSkillだけ。**約100トークンなら数十個置いても実害が出にくい
- **CLIは無料。**`gh` や `ffmpeg` がインストール済みなら、それを使わせるのに事前コストは一切かからない

## 軸2：即応するCRUDか、長く走る重い処理か

コストだけでは決まらない。処理の性質による向き不向きがある。前掲の比較記事は、実際に両方を試した結果として次のように使い分けている。

**MCPが向くもの——即レスポンスが返るCRUD処理。**同記事は、データベース検索・カレンダー操作・Slack連携といった用途にはMCPが向くと評価している。「作成・読み取り・更新・削除」を1回叩けば即座に結果が返る類の操作である。

**MCPが向かないもの——重い処理。**コード生成のような重い処理をMCP経由で実行させた際には、次の課題があったとしている。

> 引用: 「処理が非常に重く、数分～数十分待たされることがあった」（[MCP vs SKILL/BASH 比較記事](../sources/article-tools-codex-cli-mcp-vs-skill-bash.md)）

同記事は加えて、処理中は進捗が見えない**ブラックボックス感**も課題として挙げている。数十分待たされる間、何が起きているか分からない状態は実用に耐えない。

**SKILL/BASH（CLIを叩く形）が向くもの。**同記事は切り替え先として `codex exec` をCLIから叩く方式を試し、コード生成・テスト実行・長時間タスクに向くとして、①リアルタイムで進捗を確認できる ②動作が軽快 ③コンテキスト消費が少ない、の3点を利点に挙げている。著者の最終的な推奨は**現時点ではSKILL/BASHが実用的**というものである。

ただし同記事はこれを断定的な結論とはしておらず、MCPのTasksプリミティブ（2025年11月実装）が今後安定化すれば判断が将来的に変わりうると付言している。**「MCPは重い処理に向かない」は規格の本質的欠陥ではなく、現時点のエコシステム成熟度の話**だという留保である。

## 判断フロー

2軸を踏まえると、こう順序立てられる。

1. **既存のCLIコマンドで済むか？** → 済むならCLI。固定費ゼロ、進捗も見える。`gh`・`aws`・`docker` のような成熟した道具があるなら、わざわざMCPサーバーを探す理由はない
2. **手順を覚えさせたいだけか？（接続先は不要）** → Skill。「わが社の見積書の作り方」のような手続き的知識は、繋ぐ相手がいないのでMCPの出番ではない
3. **外部サービスへの接続が要り、かつ即応するCRUDか？** → MCP。Slack・カレンダー・DBのような、規格化された接続が効く領域
4. **外部サービスへの接続が要るが、処理が長時間か？** → CLI＋Skill。進捗が見え、コンテキストも食わない
5. **どれも「常時オンにする価値があるか」で最終確認する** → MCPだけは固定費がかかる。月に数回しか使わないサーバーなら、必要なときだけ繋ぐ

### 組み合わせるのが普通である

排他の選択ではない点は繰り返しておきたい。[Agent SDK overview](../sources/article-he-agent-sdk-overview.md) はBuilt-in tools（コマンド実行）・MCP・Skills を同じ機能表に並列に列挙しており、3つとも同時に使える。実際、前掲の比較記事の推奨形である「SKILL/BASH」自体が、**Skill（手順書）とCLI（実行）の組み合わせ**である。手順をSkillに書き、実行はCLIに任せる——これが最も素直な形になることが多い。

公式のベストプラクティスも両者の併用を前提にしている。[Skill authoring best practices](../sources/article-tools-agent-skills-best-practices.md) は、SkillがMCPツールを使う場合は完全修飾名 `ServerName:tool_name`（例: `BigQuery:bigquery_schema`）を使うべきで、サーバー名を省略すると「tool not found」エラーになりうるとしている。**Skillの中からMCPツールを呼ぶ構成が想定されている**わけである。

SkillとCLIの組み合わせにも、実務で効く設計パターンがある。[google/skills解説動画](../sources/video-tools-google-skills-marketplace.md)は、gcloud CLI Skill for AI Agentsを他のgcloud関連スキル全部の前提になる「安全弁」だと紹介している。LLMの事前知識は古くhallucinationしやすいため、毎回 `gcloud help` を叩いてleaf-levelで検証するよう強制する設計であり、LLMの記憶に頼らずCLI側の正解を都度引かせる仕組みだとしている（聞き取り）。**CLIにhelpコマンドがあるなら、Skill側にそれを毎回叩かせる一手間が、hallucinationを防ぐ安全弁になる。**helpが親切でないツールでは使いにくい点には注意が要る。

## もう1つの選択肢：コンテキストを分ける

3手段のどれを選んでもコンテキストを食うなら、そもそも**別のコンテキストで動かす**という手がある。**サブエージェントとは、メインの会話とは別に、専用のコンテキストで動く子エージェントのことである。**本バンドルの4手段（プロンプト・Skill・MCP・CLI）のいずれにも属さない、コンテキストを分けるための補助的な選択肢として扱う。[サブエージェント解説動画](../sources/video-ge-subagent-overview-basics.md)は、サブエージェントがメインセッションとは別の固有のコンテキストを持ち、ツールアクセスや権限もメインとは個別に設定できると説明している（[03:00]、聞き取り）。同動画は、サブエージェントでの中間処理はメインセッションに渡らず最終結果のみが返るため、メインのコンテキスト寿命が延びると述べている（[23:00]、聞き取り）。

MCPとの関係で実務的に効くのが、**ツール設定を省略するとMCPツールを含む全ツールを継承してしまうため明示指定を推奨する**という指摘である（同動画、[08:00]、聞き取り）。裏返せば、**重いMCPサーバーを特定のサブエージェントにだけ持たせ、メインには載せない**という設計ができる。前掲の55,000トークンを、メインの会話ではなく使う場面だけで払う形にできるということである。

## 判断が難しいケース

- **成否判定が要る長時間処理**: 前掲の比較記事は `codex exec --json` モード（JSONL出力で各フェーズの成功・失敗をプログラム的に判定でき、`thread.started`・`item.completed`・`turn.failed` といったイベントが得られる）を紹介する一方、既知バグとして「exit code 0を失敗時にも返すケース」（Issue #15536）があると注意喚起している。**CLIを選ぶなら、終了コードだけに成否を委ねない**設計が要る。同記事は `--full-auto`（ワークスペース内のファイル読み書き・コマンド実行をOSレベルのサンドボックスで保護しつつ許可）と、失敗時のリトライに使える `codex exec resume <セッションID> --full-auto` / `codex exec resume --last --full-auto`（コンテキストと承認設定を保持したまま再開）も紹介している
- **公式MCPサーバーがある場合**: サービス提供元が公式MCPサーバーを出しているなら、認証まわりが整備されている分だけ有利になりやすい。ただし固定費は変わらないので、常用しないなら軸1が優先する
- **どちらか決めきれない場合**: まずCLIで試すのが安全である。固定費ゼロで、うまくいかなければ捨てられる

## まとめ

| 状況 | 選ぶもの |
|---|---|
| 既存コマンドで足りる | **CLI** |
| 手順・書式を毎回そろえたい | **Skill** |
| 外部サービスに即応で繋ぎたい（CRUD） | **MCP** |
| 長時間・進捗を見たい処理 | **CLI**（手順はSkillに書く） |
| 重いツール群を時々だけ使う | **サブエージェントに隔離** |

**迷ったらコストの安い順（CLI → Skill → MCP）に試す。**これが実務上いちばん外しにくい順序である。
