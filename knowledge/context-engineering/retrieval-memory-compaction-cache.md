# 検索・記憶・圧縮・キャッシュの役割

コンテキストウィンドウが有限なら、すべてを毎回入れる代わりに、外へ保存し、必要なときに選び、長くなったら圧縮し、同じ処理を再利用する。ここで使われるRAG、メモリ、コンパクション、プロンプトキャッシュは、似て見えても目的が異なる。

## 4つの役割

| 機構 | 主な役割 | しないこと |
|---|---|---|
| 検索・RAG | 質問に関係する外部情報を探し、今回の入力へ加える | 正しさ、網羅性、最新性、安全性を自動保証しない |
| 外部メモリ | セッションをまたいで情報を保存し、後で取り出せるようにする | 保存内容を常に読むわけではない。モデルの学習済み知識を直接更新しない |
| コンパクション | 長い履歴や結果を短い状態・要約へ圧縮する | 原文の全情報を無損失で保持しない |
| プロンプトキャッシュ | 同じ入力接頭部の処理を再利用し、速度や費用の負担を減らす | 文脈容量を増やさない。意味を理解して思い出す記憶ではない。出力品質を自動改善しない |

製品ごとの価格、割引率、TTL、保持期間は変わる。本教材では固定値を一般化しない。採用時に公式文書で現在の条件を確認する。

## 検索・RAG

RAG（Retrieval-Augmented Generation）は、外部の知識源から情報を取得し、その結果を生成時の入力に使う構成である。原論文では、モデル内部のパラメトリックな知識と、外部から取得する非パラメトリックな記憶を組み合わせる枠組みとして提示された（[Lewis et al. 2020](../sources/paper-ce-rag-lewis-2020.md)）。

実務では、次の段階を分けて観察する。

1. 問いを検索可能な形にする。
2. 候補を取得する。
3. 関連性、信頼性、鮮度で絞る。
4. 出所ラベルとともにコンテキストへ入れる。
5. 回答の主張を取得元と照合する。

検索結果が悪ければ、生成を工夫しても正しい回答にはなりにくい。逆に、根拠が取得できても、必要箇所が長い断片の中に埋もれることがある。さらに取得文書には悪意ある命令が含まれうるため、RAGを安全策そのものとして扱わない（[Anthropic: Prompt injection defenses](../sources/docs-ce-anthropic-prompt-injection.md)）。RAGは「検索」と「生成」の複合系であり、片方の評価だけで全体を判断しない。

## 外部メモリ

外部メモリは、利用者の好み、過去の決定、プロジェクト状態などをファイルやデータストアへ保存し、必要時に再投入する仕組みである。Anthropicのメモリツールも、エージェントがコンテキストウィンドウ外へ情報を保存し、後の会話で参照するための仕組みとして説明される（[Anthropic: Memory tool](../sources/docs-ce-anthropic-memory-tool.md)）。

保存すべきなのは「会話全文」ではなく、再利用価値があり、更新責任を持てる情報である。

- 確定した決定と理由。
- 現在の進捗と次の作業。
- 継続的な好み。ただし本人が確認・修正できる形。
- 正本への参照、版、取得日。
- 未解決事項と再開条件。

誤った要約を長期保存すると、以後の出力へ繰り返し混入する。削除、訂正、期限切れ、出所確認の仕組みが必要である。Google ADKの設計例も、working context、session、memory、artifactを分け、大きな個別オブジェクトを常駐させない構成を示す（[Google ADK: Context architecture](../sources/article-ce-google-adk-context-architecture.md)）。

## コンパクション

コンパクションは、長い会話やツール結果を短い状態へまとめ、作業を続けられるようにする。単なる文章要約ではなく、次の作業に必要な状態を残す。

- 目的と完了条件。
- 確定事項と根拠。
- 変更した成果物と識別子。
- 未確認事項、失敗、注意点。
- 次の具体的な一手。

ただし圧縮は損失を伴う。微妙な例外、反対意見、数値定義が落ちうる。Anthropicも、長期作業でコンパクションを使う際は重要な情報の取りこぼしに注意し、まず再現率を確保してから不要情報を削る考え方を示している（[Effective context engineering](../sources/article-ce-anthropic-effective-context-engineering.md)）。重要判断では原文へのリンクを残す。

## プロンプトキャッシュ

プロンプトキャッシュは、同一または一致する入力部分の処理を再利用する最適化である。安定した指示や大きな共通資料を入力の前方へ置き、変化する依頼を後ろへ置く設計が対象になりうる（[OpenAI: Prompt caching](../sources/docs-ce-openai-prompt-caching.md)）。

重要なのは、キャッシュが「AIが前回を覚えている」仕組みではないことだ。通常、今回必要なテキストは今回のリクエストにも含まれ、コンテキスト容量も消費する。キャッシュの有無で回答内容が賢くなると仮定しない。

## 組み合わせるときの流れ

```text
正本・履歴・データ
  ↓ 保存（外部メモリ）
質問 → 検索・選別（RAG） → 今回のコンテキスト
  ↓ 作業が長期化
状態を圧縮（コンパクション）＋原文参照を保持
  ↓ 同じ接頭部を繰り返す場合
処理を再利用（プロンプトキャッシュ）
```

4つは競合する選択肢ではなく、異なる問題を解く部品である。ツール検索、結果の集約、コンテキスト編集、cacheも同じ問題を別の箇所から軽くする手段であり、窓を空ける効果が同じとは限らない（[Anthropic: Manage tool context](../sources/docs-ce-anthropic-manage-tool-context.md)）。まず失敗を「見つからない」「残らない」「入りきらない」「繰り返し負担が大きい」のどれかに分ける。

保存・cache・会話状態はデータ境界も異なる。採用時は製品、機能、契約、第三者接続を特定し、現在の公式データ制御文書を確認する（[OpenAI: Data controls](../sources/docs-ce-openai-data-controls.md)）。
