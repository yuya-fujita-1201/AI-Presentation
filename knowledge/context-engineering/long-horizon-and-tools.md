# 長期タスクとツール文脈

短いチャットなら、必要資料を一度に渡して終えられる。数時間から数日にわたる調査・開発・制作では、検索結果、ツール出力、訂正、決定が増え、最初の前提が埋もれる。長期タスクでは「最初に全部入れる」から、**必要なときに必要な粒度で開く**設計へ切り替える。

## 段階的開示

段階的開示（progressive disclosure）は、最初に詳細全文ではなく、仕事を始めるための地図を渡し、必要になった箇所だけ詳しく取得する考え方である。Anthropicは、ファイルパス、リンク、識別子などの軽い参照を持たせ、実行時に必要な情報を取得する方法を説明している（[Effective context engineering](../sources/article-ce-anthropic-effective-context-engineering.md)）。

最初の地図には次を置く。

- 目的、完了条件、禁止事項。
- 正本と索引の場所。
- 現在状態と直近の決定。
- 利用可能なツールと、使う条件。
- 不明点が出たときの確認先。

詳細文書、過去ログ、全ツール仕様は、必要になってから開く。これにより、開始時のコンテキストを小さく保ちながら、情報を捨てずに到達可能にできる。

同じ安定した接頭部を何度も送る場合は、Prompt cacheが処理負担を減らせることがある。ただし、cacheは文脈容量を空けず、対応条件も製品ごとに変わる（[OpenAI: Prompt caching](../sources/docs-ce-openai-prompt-caching.md)）。

## ツールもコンテキストを使う

AIへツールを与えると、通常はツール名、説明、引数などの定義がコンテキストに入る。実行後は結果やエラーも加わる。ツールが多いほど能力が増える一方、似たツールの選択、長い定義、大量の出力が注意を消費する。

Anthropicは、ツール検索、プログラム的な呼び出し、ツール結果の整理、コンテキスト編集などを、ツール関連コンテキストを管理する別々の手段として整理している（[Anthropic: Manage tool context](../sources/docs-ce-anthropic-manage-tool-context.md)）。具体的な機能名や対応範囲は製品ごとに異なるため、次の原則を抽出して使う。

- 今回使う可能性があるツールだけを見せる。
- 説明は用途、入力、危険な副作用、成功判定を明確にする。
- 大量結果は丸ごと会話へ残さず、成果物へ保存して参照する。
- エラーは消さず、試した条件と実際の状態を残す。
- 削除、公開、送信などの外部変更は、承認と独立確認を分ける。

ツールを減らすこと自体が目的ではない。必要な能力へ到達でき、誤選択を検出できることが目的である。

## 状態を会話の外へ出す

長期作業では、会話履歴を唯一の状態管理にしない。次のような小さな状態ファイルを正本として持つ。

```text
# TASK STATE
目的:
完了条件:
対象成果物:
現在の版・識別子:

確定:
- 決定 / 根拠 / 決定者 / 日時

実施済み:
- 操作 / 結果 / 検証方法

未確認:
- 項目 / 影響 / 確認方法

次の一手:
1.
2.

参照:
- 正本へのパスまたはURL
```

状態ファイルには「成功したはず」ではなく、観測した結果を書く。ビルド成功、外部公開、利用者への配信は別の事実であり、それぞれ証拠を残す。Google ADKの設計例にあるsession・memory・artifactの分離も、会話、継続状態、大きな成果物を別の寿命で管理する具体例になる（[Google ADK: Context architecture](../sources/article-ce-google-adk-context-architecture.md)）。

## セッションをまたぐ引き継ぎ

新しいセッションや別エージェントは、前の作業を自動的に知っているとは限らない。引き継ぎは次の順で読むだけで再開できる粒度にする。

1. 何を目指しているか。
2. 何を変更してよいか、触れてはいけないか。
3. どこまで実施し、何で確認したか。
4. どこが未確認・失敗・競合中か。
5. 次に実行する安全な一手は何か。

外部メモリや要約へ保存しても、現在の成果物と一致するとは限らない。再開時は版、ハッシュ、更新時刻など、対象に合った識別子で照合する。

## 長期化したときの整理順

1. 現在の目的と完了条件を再確認する。
2. 正本へ成果と状態を保存する。
3. 履歴から、確定・未確認・不要を分ける。
4. 確定事項を圧縮し、原文参照を残す。
5. 次の段階に必要な資料とツールだけを開く。
6. 出力後に、状態と証拠を更新する。

途中で目的が変わった場合は、古いコンテキストを継ぎ足すだけにしない。新しい目的に対して必要性と十分性を再評価する。

## 5層との関係

状態ファイルやツール環境はハーネス、反復評価はループ、複数担当の依存はグラフとしても説明できる。本教材の5層分類（[5つのエンジニアリングのスコープ差](./five-engineering-scopes.md)）は標準規格ではなく、重なりを許す教材上の地図である。ここでは、それらがモデルへ何を見せるかという**コンテキストの面**に焦点を当てる。
