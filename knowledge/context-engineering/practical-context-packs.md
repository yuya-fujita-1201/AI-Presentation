# 実践コンテキストパック

コンテキストパックは、ある仕事に必要な前提、資料、制約、検証方法をひとまとまりにしたものである。毎回のチャットを長文化するためではなく、**再利用する前提と今回だけの依頼を分け、何が欠けているか確認できるようにする**。

「コンテキストパック」は本教材で使う実践上の呼び名であり、業界標準のファイル形式ではない。テキスト、Markdown、チケット、リポジトリの指示ファイルなど、チームが版管理しやすい形でよい。

## 最小テンプレート

```text
# CONTEXT PACK

## 今回の依頼
やること:
完了条件:
出力形式:

## 目的と読み手
目的:
利用場面:
読み手:
読み手が知っていること / 知らないこと:

## 状況
経緯:
現在地:
確定済み:
未確認:

## 制約
必ず守ること:
してはいけないこと:
対象外:
期限・環境・権限:

## 既存資産
- [正本] 名称 / 版 / 場所 / 用途
- [参考] 名称 / 版 / 場所 / 用途
- [未確認] 名称 / 場所 / 注意

## 情報の選別
必要な根拠:
不足している情報:
矛盾時の優先規則:
対象時点:

## 安全と確認
信頼できない入力:
AIへ渡さない情報:
許可された操作:
人の承認が必要な操作:
最終確認者と確認基準:
```

全部を埋めることが目的ではない。空欄が出たときに、「不要だから空欄」か「まだ分からないから空欄」かを区別する。

## 例：障害報告を役員向けに直す

```text
やること: 障害報告書を役員向け1ページに要約する
完了条件: 影響、現状、次の判断を3分で把握できる
読み手: 技術詳細を追わない役員。サービス名は知っている

状況:
- サービスは復旧済み
- 原因は調査中
- 暫定対策は実施済み、恒久対策は未承認

制約:
- 原因を断定しない
- 顧客名、個人名、認証情報を出さない
- 確定事実と推測を分ける

既存資産:
- [正本] incident-2026-08-13-v3 / 2026-08-14更新
- [参考] タイムラインCSV / 時刻の照合用
- [未確認] チャット要約 / 原文と不一致の可能性

出力:
1. 結論
2. 影響
3. 復旧状況
4. 未確認事項
5. 次の承認事項

人の確認:
- インシデント責任者が時刻と影響範囲を正本で照合
- 広報責任者が対外表現を承認
```

この例では、目的と読み手が「技術説明を減らす」判断を与え、状況と制約が「原因を断定しない」判断を与える。既存資産のラベルにより、詳しいチャット要約より正式報告を優先できる。

## 作る手順

1. **仕事を一文で定義する** — 出力物ではなく、誰が何を判断・実行するためかを書く。
2. **5項目を確認する** — 目的、読み手、状況、制約、既存資産の抜けを探す。この5項目は本教材上の整理で、標準ではない。
3. **資料を4観点で選ぶ** — 必要性、十分性、信頼性、鮮度で採用・保留・不足を分ける。この4観点も教材用チェックリストである。
4. **出所と状態を付ける** — 正本、参考、未確認、版、対象時点を明示する。
5. **安全境界を決める** — 入れてよいデータ、許可された操作、人の承認点を決める。
6. **小さく試す** — 代表例で出力し、抜け、ノイズ、誤解、根拠の追跡可能性を見る。
7. **失敗から更新する** — 毎回追記せず、原因に効く情報だけを追加・修正する。

Microsoftの学習教材も、コンテキストエンジニアリングを指示、知識、ツール、状態などの情報設計として段階的に学ぶ構成を採っている。製品固有の実装へ入る前に、構成要素と評価を分ける参考になる（[Microsoft Learn: Context engineering](../sources/course-ce-microsoft-context-engineering.md)）。

## AIに不足を尋ねさせる

十分な情報が最初からそろわない場合は、AIに推測させず、開始前の質問を許可する。

```text
作業開始前に、結果を大きく変える不足情報だけを最大3問で確認してください。
質問せず進められる項目は、置いた仮定を明示してください。
根拠がない事実は補わず「未確認」としてください。
```

ただし、AIの質問が完全とは限らない。高リスクな領域では、人が必須項目を別に定義する。

## 更新単位を分ける

再利用する情報と今回だけの情報を分離する。

- **安定層** — 組織用語、文体、恒常ルール、承認経路。
- **案件層** — 対象システム、契約、正本、チーム構成。
- **今回層** — 今の依頼、現在状態、期限、直近の資料。

安定層でも永続ではない。所有者、更新日、見直し条件を持つ。古い文脈は、ない文脈より危険なことがある。

## 品質を測る

コンテキストパックの品質は文字数でなく、代表タスクで比較する。

- 重要な前提の取り違えが減ったか。
- 根拠のない補完と断定が減ったか。
- 必要な根拠を引用・追跡できるか。
- 不足時に質問または「未確認」を返せるか。
- 関係のない資料を削っても品質が維持されるか。
- 新しい版へ更新したとき、古い判断が残らないか。

長文に関しては、関連箇所の位置、資料数、ノイズ量を変えた比較も行う。「Lost in the Middle」の位置効果は限定条件で得られた結果である（[Liu et al.](../sources/paper-ce-lost-in-the-middle.md)）。一方、McKinnon (2025) はGemini 2.5 Flash単一モデルの単純factoid QAで同じ位置低下を観測しなかったが、原研究とはモデルと課題が異なる限定的な対照である（[Retrieval Quality at Context Limit](../sources/paper-ce-google-retrieval-quality-context-limit.md)）。研究名から結論を先取りせず、自分たちのモデルと課題で反証可能に測る。

RAGを使う場合は、検索に失敗したのか、取得文書が答えに不十分だったのか、文書は十分だが生成で使えなかったのかを分ける（[Google Research: Sufficient Context](../sources/article-ce-google-sufficient-context-rag.md)）。

失敗したら、まず「指示」「不足情報」「情報過多」「信頼性」「鮮度」「ツール・権限」「検証」のどこに原因があるか分ける。すべてをプロンプトの長文化で解決しない。
