# OKF 運用の実践 Tips

## Obsidian での導入例

note の記事著者は Obsidian 上に 11 ファイルの OKF 導入例を作成している。ポイント:

- `index.md` をエントリーポイントとし、各ファイルに概要（description）を書いてリンクで接続する
- これは既存の Web サイト情報設計と同等の発想で、特別なツールは不要

## AI エージェントとの相性（実証）

OKF 化したフォルダを Claude Code に読ませた実験では、**全ファイルを読まず「補足的な 4 ファイルは必要時のみ参照」と自律判断**した。フロントマターの `description` だけで適切なファイル選別ができることが確認されている。

→ メタデータを丁寧に書くほど、エージェントのトークン消費が減り検索精度が上がる。

## 適用範囲は絞る

- Vault（ナレッジ全体）をまるごと OKF 化するのではなく、**特定フォルダのみに適用**する
- OKF フォルダを専用スキル（エージェントへの参照指示）として呼び出す形にすると、トークン効率と検索精度を両立できる

## AI にナレッジ管理を任せるときの注意

自動化されたナレッジ管理には「AI が無価値な情報を追加する」「統一されない属人的な管理になる」という問題がつきまとう。OKF の統一メタデータと [寛容な消費モデル](./design-principles.md) は、この問題への現実的な落とし所になる。

## 整理作業自体を AI に任せる

既存の書類を手作業でタグ付け・ファイル分割・リンク付けするのは現実的に続かない。次の指示例のように整理作業自体を AI に任せ、人間は結果を確認するだけにするとよい。

- 指示例:「これを OKF の形に整えて、頭にタグをつけて、1件ずつファイルに分けて、関係するものはリンクでつないで」
- AI は中身を読んで種別（議事録か仕様書か等）を判断し、タグ付け・ファイル分割・関連箇所へのリンク付けまで行える。ただし AI による整理結果（タグの取り違えやリンクの過剰生成の可能性あり）は人間が目視確認する工程を省かないこと
- まだ書かれていないファイルへのリンクを貼ってもエラーにはならない（[寛容な消費モデル](./design-principles.md)）ため、最初から完璧に作らず骨組みだけ先に作って後から肉付けする運用でよい
- 新しい書類が増えるたびに同様にタグ付けして AI に渡すだけで書庫を育てていける
- 具体的な操作手順に迷ったら、AI 自身に「OKF の形に整えたいけどどうすればいい?」と聞くのが早い

## スモールスタートの始め方

いきなり全社のナレッジを OKF 化するのではなく、小さく始めることが推奨されている。

- 導入の第一歩の候補として「よくある質問集」「CS の対応ノウハウ集」「開発のオンボーディング資料」「自社のテーブル定義や手順の一部」のいずれかをまず Markdown 化してみる（1 週間で変化を実感できるとの主張）
- 入門ルートとして、仕様書を読むよりも公式サンプルバンドル（GA4 / Stack Overflow / Bitcoin）を GitHub からダウンロードして自分のエージェントに読ませる方が早いという意見がある

## 運用ルールとドメイン知識を分離する

- 運用ルール（AGENTS.md / CLAUDE.md）とドメイン知識（OKF）を分離することで、AI のコンテキストが肥大化するのを防げる
- frontmatter の肥大化には「メタデータを文書冒頭に集約する」「フォルダごとの index.md を目次として使う」「type で絞り込む」という設計方針が仕様に明記されているが、具体的な実装方法は利用側に委ねられている

## 信頼性フィールドを使った絞り込み

[OKF v0.2](./v02-changes.md) の `Verified` 欄の記載（`Human` 付きか機械のみか）を使うと、「役員向け画面には人間確認済みの知識だけ表示する」といった絞り込みが可能になる。

## バンドルの共有・引き継ぎ

OKF バンドルの正体はただのメモのフォルダなので、丸ごと圧縮してチームの共有場所に置いたり、他人に渡したりできる。新しく入ってきた人にこの書庫を AI に読ませるだけで、引き継ぎの一部を済ませられる。

## セキュリティ上の注意

OKF は誰でも簡単に書けるフォーマットである裏返しとして、素性の知れない誰かでも書けてしまう。出所不明の OKF バンドルには、AI を欺くプロンプトインジェクション的な仕掛けが仕込まれているリスクがある。読ませてよいのは、自分のプロジェクトなど中身を把握している、出所がはっきりしたバンドルに限るべきである。

## Marie Haynes の OKF brain 運用例

SEO 専門家 Marie Haynes 氏は、自分専用のナレッジベース（本人は「brain」と呼ぶ）を OKF で構築し、業務に使っている。

- **構築ツール**: Google の Antigravity（AI コーディングエージェント）と、Gemini API 経由の Gemini 3 Flash Preview 系モデルを使用（3.5 Flash よりコストパフォーマンスが良いとの理由）
- **使っている type**: `index` / `log`（エージェントが行った作業の記録） / `concepts` / `entities` / `playbooks` / `references` / `systems`。Google の例を参考にしただけで、実際は自由に決めてよいものと説明。最初に作った OKF は type を作りすぎて失敗したという反省を語っている
- **index.md の役割**: 「progressive disclosure（段階的開示）」の入り口とし、エージェントはまず index を読み、必要なファイルだけを開きに行く
- **playbook の実例1（コミュニケーションボイス）**: クライアント向け提案書でエージェントが「We（当社は）」を使う企業的な口調になってしまったため、「一人称 `I` を使い、カジュアルなトーンで話す」というルールを playbook として保存した
- **playbook の実例2（サイトインパクト分析）**: Google コアアップデート後のサイトインパクト分析のチェックポイント手順を playbook 化するのに数日かかったが、一度作った後は別のクライアントに対して同種の分析を依頼するだけで、数日かかっていた作業が即座にレポートとして得られるようになった
- **ingest（取り込み）の運用**: 新しい記事の URL をエージェントに「ingest this」と渡すと、エージェントが index を読み、実行計画（新しい reference ファイルの作成、既存 concept ファイルへのリンク追加・更新など）を提示する。実行前に承認ボタンを押す運用にしており、エージェントに無断で brain を書き換えさせない設計にしている
- **日次バックアップ**: brain は毎日 GitHub にバックアップし、コンピュータの不具合やプログラムによる上書きに備えている
- **OKF とは別に構築した仕組み**: Google 公式ドキュメントの更新を定期的にチェックし、更新があれば通知が来る仕組みを独自に構築している（本人はこれを OKF の一部ではないと明言）
- **設計上の私見**: サイト全体を 1 ページ 1 ファイルで丸ごと Markdown 化するのではなく、情報を concept 単位に分解することに OKF の強みがあるという私見を述べている
- **今後の展望**: 自身のコミュニティ（community.mariehaynes.com）の投稿を OKF に取り込み、人間のキュレーションを挟んでパーソナライズされたニュースレターを生成する構想を進行中（結果はまだ分からない段階）
- **失敗談**: 最初に作った OKF は実際には内容を Markdown ファイルに保存しておらず表示だけしていた不具合があり、作り直しになった。試行錯誤は前提だと述べている
- **視聴者へのアドバイス**: 自分の OKF を作りたい人は、Google 公式の仕様ドキュメントへのリンクと、このデモ動画のトランスクリプト自体をエージェントに渡し「Marie がやったように作って」と指示することを勧めている。使用エージェントは Claude・ChatGPT（Codex）・Antigravity のいずれでもよく、コーディング未経験でも構築可能だと強調している
