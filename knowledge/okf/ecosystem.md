# OKF と周辺エコシステム

## 他の標準との関係

OKF は既存の AI 関連標準と競合ではなく補完関係にある:

| 標準 | 役割 | OKF との関係 |
|------|------|-------------|
| MCP (Model Context Protocol) | エージェントとツール・データの動的接続 | 補完。MCP は「接続」、OKF は「知識の中身の書き方」 |
| llms.txt | サイトが LLM 向けに知識リソースの場所を示す | 補完。llms.txt が指す先の知識を OKF で書ける |
| AGENTS.md / CLAUDE.md | リポジトリの運用ルールをエージェントに伝える | OKF はこの「Markdown でエージェントに知識を渡す」パターンを一般化・標準化したもの |
| OSI (Open Semantic Interchange) | BI ダッシュボードのメトリクス共通定義 | 補完・並走。OSI は「数字の定義」、OKF は「AI エージェントへのナレッジの受け渡し」で住み分けられる（動画の説明） |

### OSI との住み分け（動画の見解）

2026 年 1 月、Snowflake・dbt・Cube・AtScale・Databricks など 40 社以上が「Open Semantic Interchange (OSI)」というオープン標準を発表していたと紹介されている。OSI も YAML ベースだが、OSI は BI 向けダッシュボードのメトリクス共通定義（dbt・Cube・AtScale・LookML などが同じ陣営）を目指すのに対し、OKF は AI エージェント向けにテーブルや業務手順を文脈として渡すためのナレッジ標準であり、両者は競合ではなく並走する関係にある、という見解が動画で語られている。「BI ダッシュボードは OSI でメトリクスを定義し、AI エージェントには OKF でナレッジを渡す」という両輪運用が最も強いという見解も示されている。OKF は OSI と比べて SDK 不要・ファイル単位で Git 管理できる分、軽量で導入ハードルが低いとされる。

## リファレンス実装（Google 公開）

- **拡充エージェント（Enrichment Agent）**: BigQuery データセットをスキャンして OKF のドラフトを自動生成するプロデューサー。動作は2段階と説明される: (1) テーブル1つ1つにコンセプト文章を下書き、(2) 社内の信頼できるドキュメントを2回目の LLM パスでクロールし、スキーマ・結合パス・サンプルクエリまで拾ってくる。引用元の出典リンクも自動で入るため「追跡可能なドキュメント」になるとされる。GitHub で Apache 2.0 ライセンス公開されており、自社の BigQuery に対してすぐ試せる
- **静的 HTML ビジュアライザー**: バンドルをインタラクティブなグラフとして可視化（バックエンド不要）
- **サンプルバンドル 3 種**: GA4 e コマース、Stack Overflow、Bitcoin の各パブリックデータセット。いずれも参照実装のエージェントが自動生成しリポジトリにコミットされたもの

GitHub: `GoogleCloudPlatform/knowledge-catalog` リポジトリの `okf/` 配下。仕様はバージョン管理され、後方互換性を考慮して成長する設計。Google Cloud の Knowledge Catalog も OKF をサポートするよう更新されており、Google 以外のツール・実装・採用を明示的に歓迎している。

## 3つの活用例（動画の整理）

1. **データチーム向け**: 上記の拡充エージェントによる BigQuery テーブルの自動ドキュメント化。データエンジニアのドキュメント作業が「数日規模から数時間規模に短縮され、抜け漏れも減る」という主張が紹介されている
2. **営業・カスタマーサポート・エンジニア向け**: 商談メモ（スプレッドシート）、CS対応ノウハウ、エンジニアの設計書（Notion）など「別々の場所・別々のフォーマット」に散在した知識を Markdown に統一するという考え方。高価な管理ツールや専用カタログは不要で、Markdown ファイル群を Claude Code や ChatGPT Agent に渡すだけで自社の知識として文脈を理解させられる、と紹介されている
3. **個人でエージェントを使い倒す人向け**: Claude Code / Cursor / Obsidian ユーザーにとって、AGENTS.md・CLAUDE.md・Obsidian Vault は元々 OKF と同じ発想（Markdown をエージェントへの文脈として渡す）であり、OKF はその文化を業界標準にする動きだと位置づけられている。個人が育てた Vault が別のツールでもそのまま読めるようになる「ツールに縛られない」利点が、動画内で OKF が解く「一番大きな課題」として語られている

## Google がこれを公開した狙い（動画の見解）

- 動画は Google の狙いを「サービスを売るのではなく共通言語を作る」戦略と位置づけている。各ベンダーの独自カタログ・独自 SDK による囲い込みへの対抗軸として紹介されている
- Google 一社の提案だが、フォーマット（仕様）であるため他社が賛同しなくても各社が個別に採用できる点が「オープン規格の強さ」として語られている
- 動画時点の情報として、今後は Google Cloud のカタログ製品や Looker でも対応予定とされ、Google 自身もこの標準で自社製品を動かしていく方針だと紹介されている

## ASO（エージェンティック・サーチ・オプティマイゼーション）という見解

動画の一つは、これからは検索エンジンに選ばれるための SEO だけでなく、AI エージェントに選ばれるための対策も必要になるという見解を示し、これを「ASO（エージェンティック・サーチ・オプティマイゼーション）」と呼んでいる。将来ユーザーは検索エンジンを使わず AI に直接尋ねるようになり、自社の専門知識を OKF で構造化している企業だけが AI の世界で発見されるようになる、という見解が語られている。

## AGENTS.md 文化との関係（動画の紹介）

AI 研究者アンドレイ・カーパシー氏が AGENTS.md / CLAUDE.md の文化を高く評価しているという趣旨のコメントが動画で引用されている（「LLM は十数個のファイルを1パスで触ることができ相互参照を忘れることもない」という趣旨、一次ソース未確認）。動画はこれを踏まえ、OKF はこの文化を「組織の成り立ち」まで拡張する標準だと位置づけている。

## 使う前の注意点（v0.1段階ゆえの限界、動画の指摘）

1. まだ v0.1 の初期版であり、完成した標準ではない。`type` の値を中央で登録する仕組みがなく、命名は現場の合意で決めていく形になる
2. エコシステムはこれから育つ段階。書き出す側と読み込む側の両方のツールが揃って初めて価値が出るが、現時点では Google の参照実装が中心で、Claude Code や Cursor のネイティブ対応はこれから（動画公開時点）
3. Markdown は人間にも読めるため、共有先や Git リポジトリの公開範囲を確認し、機密データの取り扱いに注意する必要がある

## エコシステムへの参加ステップ（公式ブログより）
