# 概要

Google Cloud の OKF（Open Knowledge Format）仕様書が、初版公開から約6週間で v0.1 から v0.2 へ大改定されたことを扱う動画。行数は451行からおよそ倍以上に膨らみ、新たに約550行が追加された一方、公式ブログは「足したのは語彙であってルールは足していない」と説明している。動画はその約550行の正体が「AIが書いた知識をどこまで信じてよいかを判定するための専用の記入欄」であることを、仕様書末尾の v0.1/v0.2 比較例に沿って具体的に解説する。

# 要点

## 改定の規模と公式説明
- OKF 仕様書は初版公開からおよそ6週間で v0.1 から v0.2 へ大改定された。
- 行数は451行からおよそ倍以上に増加し、新たに約550行が追加された（具体的な最終行数は動画内で明言されていない）。
- 公式ブログは「足したのはボキャブラリー（語彙）であってルールは足していない」と説明しており、動画はこの発言を最後まで検証する構成になっている。
- 仕様書末尾には、同じ知識ファイルを v0.1 と v0.2 それぞれの書き方で並べた比較例が掲載されている。上半分（種類・タイトル・説明）は共通で、v0.2 で増えた下半分に「誰が書いたか」「誰が確認したか」「いつまで有効か」「何を元にしたか」が並ぶ。

## OKF の基本構造（おさらい）
- OKF は Open Knowledge Format の略で、会社の知識を AI に読ませるための約束事。
- 正体は Markdown ファイルを入れたただのフォルダであり、各ファイルは「YAML frontmatter（メタデータ欄）」＋「普通の Markdown 本文」の2階建て構造になっている。
- 必須項目は type（種類）ただ1つで、これは v0.2 でも変わっていない。
- cat で読める、git clone で配れる、という「タイプさえあれば動く緩い規約」という性格は維持されている。

## なぜ「疑うための欄」が必要になったのか
- 動画は、知識を書く主体が変わったことを理由として挙げる。従来は人間が書き、疑問があれば書いた本人に聞けたが、今のナレッジベースは「AIエージェントが書き、別のAIエージェントが読む」場所に変わりつつあると説明している。
- 公式ブログには、大量の知識ファイルが短時間（一晩）で生成される例が示されており、これを人間が全件チェックするのは現実的でないと動画は述べている。
- そこで v0.2 は「読む側が答えるべき質問」を5つに整理し、それぞれに専用の記入欄を用意した。増えた欄はすべてこの5つの問いのいずれかに対応する。
- 理由として、AI は知識を探す際にほとんどの場合本文までは読まず、読む前に「残すか捨てるか」を判定する。その判定材料を frontmatter（ファイル先頭の欄）に集約したのが v0.2 の設計思想だと動画は説明している。

## 5つの新しい問いと対応する欄

### 1. 何から作られたか（出所）
- v0.2 では、元にした資料を Sources 欄に列挙する。
- 動画は公式の実例バンドル（架空の小売企業のファイル）を使って解説する。資料ごとに Author（誰が作ったか）、UsageCount（期間内に何回使われたか）、LastModified（資料自体の最終更新日）の3つの属性が付与される。
- 例として挙げられた「1240」という数値は「その社内文書が3ヶ月で1240回参照された」という意味で、よく使われ最近も更新されている資料からの知識は信じやすい、と読む側が推測できる仕組みだと説明されている。
- 動画は「最初から信頼度85点のようにスコアで書けばよいのでは」という疑問を投げかけた上で、仕様は信頼度スコアを検討した上で「入れない」と決めたと解説する。理由は、点数は主観的でつけた人の基準に依存し、組織をまたぐと意味が通じず、書いた瞬間から古びていくため。記録するのは「何回使われた」のような客観的事実のみとし、何点と評価するかは読む側がその都度計算すればよい、という割り切りだと動画は述べている。
- 細部の工夫として、本文中の出典参照は番号ではなく Source の ID や名前で行う。エージェントがリストの順序を並べ替えても、名前による参照なら壊れないためとされる。

### 2. どれくらい信じていいか（作成と確認の分離）
- v0.2 は Generated（生成情報）と Verified（検証情報）という2つの欄を意図的に分けている。
- Generated は「この内容を誰がいつ作ったか」、Verified は「その内容を誰がいつ元データと突き合わせて確認したか」を記録する。書いた本人と正しさを保証する人は別であってよい、という考え方。
- 動画の実例では、AIエージェントが書いた内容を翌日に人間が確認している。
- 名前の書き方にも決まりがあり、AI やツールは「名前＋バージョン」、人間は「Human」、自動処理は「Process」という接頭辞を付ける。
- この頭の目印により、読む側は Verified の中身から信頼の段位を機械的に判定できる。Verified がなければ「未確認」、機械の確認のみなら「機械確認済み」、Human が付いた確認が1件でもあれば「人間確認済み」という3段階の判定が可能になる。
- 動画は、この仕組みを使えば「役員向けの画面には人間確認済みの知識だけ表示する」といった絞り込みができると述べており、これは公式が挙げる想定用途でもあるとしている。
- ただし、これはあくまで信頼度の目安であり、アクセス制御そのものとは別物。未確認だからといって表示が拒否されるわけではない、と補足されている。

### 3. まだ本当か（鮮度）
- v0.2 で追加される、いわば「賞味期限」の欄（動画中では ValidUntil に相当する絶対日付として説明される）。
- 例えば「2026年12月31日」のように日付を指定すると、その日以降はこの知識が古い可能性があると判断できる。動画の実例では経理ルールの年次見直しに合わせた日付が使われている。
- 「作成から90日間有効」のような相対的な期間指定ではなく絶対日付を使う理由として、相対日数だと「いつ読んだか」を計算に入れないと有効期限を判定できないが、絶対日付なら今日の日付と比較するだけで、AI にも通常のプログラムにも迷いのない判定ができるためだと説明されている。

### 4. 今の状態は何か（ステータス）
- ファイルの現在の状態（下書き・安定・非推奨といった段階）を宣言する Status 欄が追加される。
- 役目を終えた古い定義は「非推奨」として残し、過去の再現には使えるが新しい仕事には出さない、という運用が想定されている。
- これにより、期限切れや古いバージョンのファイルを本文を開かずに機械的に洗い出せる「知識の棚卸し」がしやすくなると動画は述べている。

### 5. この数字は決められた通りに計算されたか（検算）
- 今回の改定で唯一まるごと新しく登場した知識の種類が Attested Computation（実行が証明された計算、と動画は訳している）。
- 動画は「経営会議で AI に『今年度の売上は』と聞き、AI が金額を算出した」という想定シナリオを提示する。出所の資料がすべて正しくても、AI がその場で自作した SQL で集計していた場合、経理が定めた売上の定義と微妙に異なる式になっている可能性が残る、という問題提起。
- 「その数字が決められた通りの方法で計算されたか」に答えるのが Attested Computation で、動画の実例では会社の計算式そのものを1つの知識ファイルとして固定（封印）する。Runtime が実行環境を表し、実例では BigQuery のパラメータが埋め込まれた形式で、AI が埋められるのはパラメータの数値だけとされる。
- 仕様には、エージェントに許されるのは宣言済みパラメータへ値を入れることのみで、計算式そのものを書くことも直すことも禁止されている、と明記されていると動画は説明する。
- 実行後には検算の工程が続く。実行は実際に走った SQL と結果を「レシート」として返し、それを Attestor と呼ばれる、LLM を一切使わない決定論的なプログラムが検査する。検査内容は (1) 公認の式にパラメータ値を入れたものと実際に走った式が一致するか、(2) 表示しようとしている数字がレシートの結果と一致するか、の2点。
- 一致しなければ不合格となり、テーブル名のすり替え、条件のこっそりした追加、式ファイルの差し替えなどはすべてこの検査で弾かれる。不合格の数字は表示しない、という流れが仕様に描かれていると動画は説明する。

## 検算の仕組みに関する補足（2つの注意点）
- OKF 自身は何も実行しない。記録するのは計算式と検査のやり方までで、実際の実行と検査を行うのは利用側の役割。
- Verified と、この検算（Attested Computation）は別物。Verified は「定義が今も会社のルールに合っているか」の確認でファイルに記録が残るのに対し、検算は「今回の実行が正しかったか」というその都度の確認。両方揃って初めて成立し、定義が正しくても実行がずれていればダメ、実行が正しくても定義が古ければダメ、という関係にあると動画はまとめている。

## v0.1 との後方互換性
- v0.1 で作成済みのフォルダはそのまま読める。今回の変更は「追加が本体」であり、新しい欄をすべて埋めなくても、既存ファイルは v0.1 当時と同じ資格で有効。
- ただし置き換えが2つある。(1) 従来ファイルの最終更新を記録していたタイムスタンプ欄は、新しい Generated 欄の中に統合された。(2) 本文の下に並べていた引用リスト（Citations 相当）の記法は、frontmatter の新しい Sources 欄に統合された。
- この2つの旧記法を使っている古いファイルも読めなくなるわけではない。仕様は「読む側に新しい欄がなければ古い書き方を見に行ってよい」という救済ルールを定めており、公式ブログも「v0.1 のバンドルは無変更でそのまま使える」と明言している。
- 動画が指摘する興味深い点として、同じ2つの変更を仕様書自身は「意図的な破壊的変更」と呼び、公式ブログはより穏やかな表現で呼んでいる（字幕からは正確な訳語が判読できず、本メモでは詳細を保留）。中身は同じでも表現の温度が異なり、仕様書側が自らに厳しい言い方をしている、と動画は評している。

## 動画の結論
- 冒頭の「行数は倍増したのにルールは増えていない」という謎は、必須項目が今も type ただ1つであり、増えた約550行はすべて「使いたい人だけが使う語彙」だったことで説明される、と動画はまとめる。
- v0.2 の追加点は、出所・信頼性・鮮度・状態を記録する欄と、知識の棚卸しのための仕組みに要約できる。信頼度は点数ではなく客観的なシグナルで示し、計算式は固定した上で実行結果を LLM 抜きのコードで検算する、という設計だと動画は総括している。
- 動画は「AI に知識を書かせる時代の答えは、AI を疑える形式にしておくことだ」という見解を述べ、内容と一緒に「信じてよい根拠」を機械が読める場所に置くことが、OKF に限らずこれからの設計思想として持ち帰ってほしい点だとしている。

## 限界・留保事項（動画が明言する範囲）
- 現行版は v0.2 のドラフト（たたき台）は脱したが、1.0 の安定版ではなく、今後も形が変わる可能性があるとされる。
- 検算（Attested Computation）まわりの「レシート」の細かい形式や検査プログラムの実装の詳細は、仕様書が検討した上で先送りしていると明記されており、設計の輪郭はあるが実行部分の詳細は未確定。
- Google が同時に更新したツール群は「参考実装（試作）」の位置づけであり、実際の採用数は公表されていない。
- frontmatter の増加による AI への入力文章の肥大化については、仕様は「メタデータを文書冒頭にまとめる」「フォルダごとのインデックスファイルを目次として使う」「type で絞り込む」といった外部から絞り込む設計を明記しているものの、その実行部分の実装方法自体は仕様の非目標とされ、作る側に委ねられている。実際にどれだけ軽量化できるかを示す数値は、動画の時点ではまだ誰も出していないとされる。
