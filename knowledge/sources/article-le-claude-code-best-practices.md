# 概要

Anthropic公式のClaude Code Docsが公開する「Best practices for Claude Code」は、「Give Claude a way to verify its work（Claudeに自らの作業を検証する手段を与える）」という節で、Claudeに合否を判定できるチェックを持たせることの重要性を解説している。同ドキュメントは、テストやビルド、比較用のスクリーンショットのように「合格」か「不合格」かを返すチェックを与えることで、Claudeが自ら作業・検証・反復を繰り返す自律的なループを回せるようになると述べている。チェックの有無が、人間がつきっきりで監視するセッションと、離れていても任せられるセッションとを分ける差だとしている。

# 要点

## チェックがないと人間が検証ループを肩代わりする

同ドキュメントは、Claudeは作業が「終わったように見える」時点で手を止めると説明している。実行可能なチェックがなければ、この「終わったように見える」という主観的な印象だけが唯一の判断材料になり、結果として人間自身がミスを見つけるたびに介入する「検証ループ」の役割を担うことになると指摘している。これに対し、合格・不合格の信号を返すものをClaudeに与えれば、ループは自動的に閉じると述べている。

> 引用: 「Give Claude something that produces a pass or fail, and the loop closes on its own. Claude does the work, runs the check, reads the result, and iterates until the check passes.」

ここでいう「チェック」とは、会話の中でClaudeが読み取れる信号を返すものすべてを指すとし、テストスイート、ビルドの終了コード、リンター、出力を期待値ファイルと突き合わせるスクリプト、デザインと見比べるブラウザのスクリーンショットなどを例に挙げている。

## Before/After形式の3つの適用例

同ドキュメントは、指示の書き方を「検証基準を与える」「UI変更を視覚的に検証する」「症状ではなく根本原因に対処する」という3つの観点でBefore/After形式の表にまとめている。1つ目は、単に「メールアドレスを検証する関数を実装して」と指示するのではなく、具体的なテストケース(`user@example.com`はtrue、`invalid`はfalse、`user@.com`はfalse)を添えて、実装後にそのテストを実行するよう指示する書き換え例を示している。2つ目は、「ダッシュボードの見た目を良くして」ではなく、スクリーンショットを貼った上でそのデザイン通りに実装させ、結果のスクリーンショットを撮って元のデザインと比較し差分をリストアップして修正させる指示を挙げている。3つ目は、「ビルドが失敗している」という報告だけで済ませるのではなく、実際のエラーメッセージを貼り付けて修正させたうえでビルドの成功を検証させ、エラーを握りつぶすのではなく根本原因に対処するよう求める指示を紹介している。

## チェックの強制力を高める4つの段階

チェックを用意した後は、それがどれだけ強く「停止」をゲートするかを決める必要があるとし、同ドキュメントは4段階の手段を挙げている。1つ目は「単発のプロンプト内で」チェックの実行と反復を同じメッセージの中でClaudeに指示する方法である。2つ目は「セッションを横断して」チェックを`/goal`条件として設定する方法で、別のevaluatorが毎ターン後に再評価し、目標が達成されるまでClaudeが作業を続けるとし、Claudeが行き詰まった場合はClaude Codeが目標未達のまま最終的に実行を停止すると説明している。3つ目は「決定的なゲートとして」Stopフックにチェックをスクリプトとして実行させ、通過するまでターンの終了をブロックする方法で、Claude Codeは8回連続でブロックされるとフックを上書きしてターンを終了させるとしている。4つ目は「セカンドオピニオンによって」検証用サブエージェントや、自らの発見内容を検証するダイナミックワークフローを用いる方法で、作業を行ったのとは別のフレッシュなモデルに結果の反証を試みさせることで、作業したエージェント自身が採点者にならないようにする狙いがあると述べている。

同ドキュメントは、それぞれの段階が「準備の手間」と「必要な注意の少なさ」のトレードオフになっていると述べ、プロンプト版はどんなタスクにもすぐ使える一方、`/goal`版とStopフック版は人間が見ていなくても無人実行が正しく完了することを可能にする手段だとまとめている。

## 成功の自己申告ではなく証拠を提示させる

最後に同ドキュメントは、Claudeに成功を自己申告させるのではなく、テストの出力結果や実行したコマンドとその戻り値、あるいは結果のスクリーンショットといった証拠(evidence)を提示させるべきだと推奨している。証拠を確認する方が自分で検証をやり直すより速く済み、かつ人間が見ていなかったセッションに対しても機能する方法だとしている。
