# 要点

## 用語整理：プロンプト・コンテキスト・ハーネスエンジニアリングの違い

- **プロンプトエンジニアリング**: AIにどのような指示文を与えるかを工夫すること。ChatGPTリリース以降ずっと言われてきた概念で、視聴者にも馴染みが深いはずとしている
- **コンテキストエンジニアリング**: AIモデルに「何を」「いつ」「どれだけ」読ませるかを設計すること。プロンプトが指示文そのものであるのに対し、会話履歴・Web検索・ファイルや資料など、AIエージェントが扱える情報が増えたことで生まれた概念だと説明している
- **ハーネスエンジニアリング**: AIが動く環境を丸ごと設計すること。動画作者の理解では、コンテキストエンジニアリングが「どんなツールやファイルがあるかをテキストとしてモデルに入力する部分」までを指すのに対し、ハーネスエンジニアリングは検索を実行する基盤やファイルを実行する仕組み、AIをループさせる仕組み、読み込ませないファイルの制御など、AIエージェントが動く周辺環境全体を指すとしている。どこまでを指すかは人によって解釈が分かれる、とも述べている
- **人間の仕事に例えた整理**（動画内の比喩）:
  - モデル＝その人の「頭の良さ」。賢いモデルほど同じ指示でも早く正確にこなせる
  - プロンプトエンジニアリング＝仕事の指示をどう伝えるか
  - コンテキストエンジニアリング＝指示以外にどんな資料・情報を渡すか。優秀なモデルで指示が的確でも、必要な情報が欠けたり逆に不要な資料を与えすぎて指示を忘れたりするため、必要十分な情報を見極める設計が重要
  - ハーネスエンジニアリング＝その人が作業する環境丸ごと。プログラマーが良いキーボードや椅子で作業効率が上がるのと同様、AIも動作環境次第で精度が変わる。さらに、AIが勝手にファイルを削除したり大事な情報を外部に送信したりしないかという「権限管理」もハーネスエンジニアリングに含まれる領域として語られることが多いとしている
  - 「モデルの頭さえ良ければすべて解決する」と思われがちだが、実際はモデルが動く環境設計まで含めてどう精度を出すかの研究が進んでいる、という見解を述べている

## ループエンジニアリングとグラフエンジニアリングの違い

- 動画作者は、この2つを先述の3つ（プロンプト・コンテキスト・ハーネス）と同じレイヤーで語る人もいるが、自分は別レイヤーだと考えていると述べている。上の3つが「AIが動くための材料と環境を用意する」ものであるのに対し、この2つは「AIをどう動かすか」を設計するものという整理
- **ループエンジニアリング**＝時間軸でどう回すかの設計。AIが何かを実行→結果を検証→改善、というループを組むことで、AIが自動的に何かを改善し続けられるようにする考え方
  - 具体例として、現在Anthropicに所属しているとされるAndrej Karpathy氏が公表した「オートリサーチ」というプロジェクトが紹介されている（プロジェクト名・所属は聞き取りに不確実性あり。概要欄にはKarpathy氏のXへのリンクが記載されている: https://x.com/karpathy/status/2030371219518931079）。機械学習モデルをAIが自律的に改善する仕組みで、人間が指示しなくてもAIが実験→結果に基づく改善を繰り返すことで精度がどんどん良くなっていくことを示したプロジェクトだとしている
  - 図のイメージとして、AIがプログラムを書いて実行→正答率のスコアが出る→スコアが上がるように改善→再実行、というループを回している例が紹介されている
- **グラフエンジニアリング**＝構造軸でどう組むかの設計。AIをどのような構造で使ってタスクを行わせるかを考えるもの
  - 具体例: 調査レポートを作る場合、単純に1回AIに調べさせるより、いくつかの観点に分けて調べさせる／複数のAIに調査させる→結果を別のAIで集約する→まだ調査が足りなければもう一度調査する、というようにどこにどうAIを配置してタスクを行わせるかを決めるのがグラフエンジニアリング
  - このグラフの中にループエンジニアリングを組み込むこと（調査結果を検証して再調査する、をぐるぐる回すなど）も可能だとしている

## グラフエンジニアリングとワークフローの関係

- グラフエンジニアリングは実はすでにClaudeデスクトップアプリやChatGPTデスクトップアプリにも組み込まれていると説明。Claudeデスクトップアプリでは、エフォートレベルを「ウルトラコード」（トランスクリプトの表記のまま。Claudeの高負荷な思考モードを指していると見られるが聞き取りに不確実性あり）にすると、入力した指示をもとにAI側が勝手にワークフローを組んでくれる。ChatGPTアプリでも推論レベルを「ウルトラ」にすれば同様にAI側が勝手にワークフローを組んで処理してくれるとしている
- ただしループエンジニアリング・グラフエンジニアリングを組むとAIを何度も使うためコストが大きく上がる点を指摘。動画作者個人としては、組み込みのウルトラ機能でワークフローを自動生成させるよりも、自分でその場で指示を出しながらフローを組んで精度を上げる方が普段使いでは多いと述べている
- **動画作者の個人的見解**: グラフエンジニアリングは昔からあった「ワークフロー」のことを別の名前で言っているだけではないかとしている。Difyなどでワークフローを組んだ経験がある人なら「グラフと言えばグラフだし、ワークフローと言えばワークフロー」という感覚だとし、Anthropicも2024年の記事で「エージェントとワークフロー型」という整理を発表しており、その内容は非常に似ている（ほぼ同じ）と述べている
- なぜ今「グラフエンジニアリング」という呼び方で盛り上がっているかについて、動画作者は2つの理由を挙げている
  1. 「グラフ」と言うと1つの技術っぽく聞こえ、「ワークフロー」よりキャッチーで注目が集まりやすいから
  2. 単純にAIの精度自体が上がってきており、以前はワークフローにエージェントを組み込むと変なミスをして微妙だったが、最近の賢いAIなら連携させた方が単一エージェントより明らかに良い出力が得られるようになったから
- 結論として、AIエージェントのアプリを自作する立場ならコンテキスト・ハーネスエンジニアリングも押さえておくべきだが、普通にAIを使う側の視点では、そこまでがっつり勉強する必要はなく「AIを複数使って何かやらせる」というループエンジニアリング・グラフエンジニアリングの発想を押さえておけば十分だとしている

## 検証AIで回答精度を高めるループの仕組み

- AIに何か指示して実行させ、結果が良くない場合に複数のAIを使うのがこの手法。「何でもかんでもループを組めばいい」わけではなく、精度が出ない場合に使うものと説明
- 精度を上げるには必ず「評価」が必要。できたものが良いか悪いかが分からなければ改善の方向が定まらないため、検証の仕組みが必要になる
  - 検証方法は大きく2つ: ①何らかのプログラムを実行して機械的に合否を判定する方法、②言語モデルに検証させる方法
  - プログラムであればテストコードの合否で機械的に検証できるが、例えば議事録のような自由記述の成果物をプログラムで自動検証するのは難しいため、AIに検証・改善をやらせる方法が現実的な解になるとしている
- 「AIに作らせてAIに評価させるなら1体で完結するのでは？」という疑問に対し、動画作者は「言語モデルは自分の作ったものを甘く評価しがちという性質があると言われている」と説明。1つの言語モデルだけで作成と評価を両方行わせると評価が甘くなりやすいため、作成と評価を別のモデル（別のエージェント）に分ける方が経験則的に良い結果になるとしている
- 改善のポイントを適切に抽出することが重要なため、評価専用のモデルだけ性能の高いモデル（Fable、Opusなど）を使い、実行はSonnetを使うといった組み合わせ方も、コスト節約の観点で有効な選択肢として紹介されている

## Claude CodeのLoop・Goalコマンド比較

- Claude Codeには標準で「/loop」コマンドがあり、一見ループエンジニアリングそのものに見えるが、これは単純に「定期的に実行する」ためのものだと説明
- 「AIが実行→結果を検証→再実行」という本来のループを組みたい場合は、「/goal」コマンドの方が正しいアプローチだとしている。スラッシュgoalで達成したい条件を書けば、その条件を満たすまで実行・評価・再実行を繰り返してくれる
- 仕組みとしては、内部でClaudeの「配下のモデル」（トランスクリプトの表記のまま。デフォルトのモデルを指すと見られるが聞き取りに不確実性あり）が評価を担当してループを回す形になっていると説明
- ただし動画作者個人としては、goalコマンドを使うよりも自分でサブエージェントを使ってループを組む方が自由度が高く、普段の仕事で使いやすいと述べている

## Claude Codeサブエージェントの仕組み

- 基本構造として、Claude Codeに話しかけると「メインエージェント」と呼ばれるものが回答を生成する。メインエージェントとはモデルの名前ではなく、ユーザーと会話するAIという分類上の役割を指す（動画作者は現在メインエージェントとしてFable 5を選択している）
- Claude Codeにはメインエージェント以外に「サブエージェント」という概念があり、メインエージェントがサブエージェントを呼び出し、サブエージェントが作業した結果をメインエージェントに返す、という構造が組める
- デモとして、メインエージェントに「サブエージェントに『元気ですか』と聞いてみてください」と指示すると、メインエージェントがサブエージェントを起動・呼び出しを行い、「元気です。気分は快調です」という結果が返ってくる様子を実演している。裏側では別のAIモデルが呼び出され、その結果を受け取ったメインエージェントが最終的な返答を生成している、という仕組みを説明している
- サブエージェントは1体だけでなく複数起動することも可能で、いくつかの役割を与えてそれぞれのサブエージェントに別々の指示を出し、結果を全て回収するといった使い方もできるとしている

## メイン・検証エージェントを使った改善ループの組み方

- 実務での使い方の一例として、メインエージェントに何か（例: 議事録などの成果物）を作らせ、それをサブエージェントにチェックさせる→ダメ出しリストや採点が返ってくる→それを元にメインエージェントが修正して再度成果物を作る、という流れを紹介。理屈上はこれを無限に繰り返して品質を高めることができるとしている（弱点は後述）
- 最近の傾向として、Claude Opus 5クラスの高性能モデルでは「サブエージェントを使った検証は不要」と公式から言われている点に言及。プロンプト内に検証指示が含まれている場合は削除するよう案内されており、Opus 5クラスなら自分で検証できるので明示的な検証指示は不要という趣旨だとしている
- ただし動画作者自身の体感としては、Claude Opus 5でも検証用のサブエージェントがあまり起動してくれないことがあったため、公式の推奨とは異なり、今でもサブエージェントによる検証ステップを使い続けていると述べている。サブエージェントを多用している視聴者に対し、体感やコメントを募っている
- Opus 5を普段使えない人向けには、Sonnet 5などでもこうした検証を組み合わせれば精度が上がるはずだとし、メインエージェントとサブエージェントで別々のAIモデルを使えることを利用して、検証側だけOpusやFableのような高性能モデルを使い、実行はSonnetにするといった組み方もコスト節約の観点で有効だとしている

## 実験：操作マニュアル生成での検証ループ有無の比較

- 題材として、動画作者が執筆中の書籍のために、画面のスクリーンショットに赤枠を付けて操作マニュアルとしてドキュメント化するタスクを使い、検証エージェントを使った場合と使わない場合でどう違うかを比較する実験を行っている
- 実験は独立した2パターンを同時に動かすため、Claude Codeにworktree機能（トランスクリプトでは「ワーク3」と表記。git worktreeを指すと見られる）を使わせている
- **パターンA（左側・検証エージェントなし）**: スクリーンショット画像3枚を渡し、「赤枠の番号付きで分かりやすいマークダウンのドキュメントを作ってください」と単発で指示
- **パターンB（右側・検証エージェントあり）**: 同じ指示に加えて「作成後、検証エージェントを起動してフィードバックループを最大3回回してください」と指示。無限ループを防ぐため上限回数をあらかじめ設定している
- 両パターンともモデルはSonnetを使用。生成には10〜15分程度かかったとしている
- **比較結果**:
  - 手順1: 両方ともほぼ同じ内容だが、単発の方は赤枠が若干切れてしまっている。検証エージェント版は枠自体は綺麗だが、番号の位置が若干ずれている
  - 手順2: 単発版は赤枠が重なってしまっているのに対し、検証エージェント版はきちんとできており、さらに補助線も加えられていてより見やすい仕上がりになっている
  - 手順3: 単発版は手順3・4・5がまとめて1つの説明として書かれている。検証エージェント版も同様にまとめて書かれているが、赤枠の精度については検証エージェント版の方がしっかりできている印象だとしている
- 総括として、検証ループを回すことで図の質が若干向上していると述べ、動画作者自身も普段の使用感として「1回だけで作らせるより、何回か検証させた方が間違いが減る」「AIも人間と同じで、作るより批判する方が簡単」という経験則から、このフローでの品質向上を強くおすすめしている

## 論文（RefineBench）に基づく自己修正と外部フィードバックの精度比較

- 動画作者は「自分が適当に言っているだけではないか」という指摘を見越し、最新の論文結果を紹介している。概要欄に記載の論文は「RefineBench: Evaluating Refinement Capability of Language Models via Checklists」（https://arxiv.org/abs/2511.22173 ）
- 動画内では、韓国のKAIST（トランスクリプトでは「カイスト」）、カーネギーメロン大学、NVIDIA（トランスクリプトでは「NDIA」、聞き取りに不確実性あり）の研究者による論文と紹介されている。AIが自分の回答を自分で修正することで精度が上げられるのかを調べた研究だとしている
- **結論**: 何のフィードバックも与えず自己修正させる「セルフリファインメント」という方法では、多くのモデルでほとんど精度が改善しない。一方、どのような修正が必要かという観点をフィードバックとして与えた場合は精度が大きく向上する、という結果が示されているとしている
- **実験結果の具体的な数値**（動画内で紹介）:
  - 自己修正のみ（評価観点を与えず自分で修正、t=1が1回目、t=5が5回目）: 多くのモデルでt=1とt=5の差（デルタ）がほとんど無く、精度がほぼ上がっていない
  - 別のAIが採点基準・ダメな点をフィードバックとして与えるケース: 5回修正を繰り返すと精度が大きく向上し、Opus 4.1では98.4%まで到達したと紹介されている（伸び率が大きい点を強調）
  - さらに論文では「評価基準を自分自身に持たせた場合」と「他のAIに評価基準を持たせて採点させた場合」も比較されている（論文中の表4に相当）。自己保持の評価基準では5回修正しても75.8までしか伸びなかったのに対し、Gemini 2.5 Pro（トランスクリプトでは「JOMI2.5 Pro」、聞き取りに不確実性あり）などの他のAIにフィードバックさせた場合は94.7まで伸びたと紹介されている
- この結果から、動画作者は「AIは自分で作ったものを自分で正しく評価するのが難しい」という点が分かるとし、サブエージェントに間違いを指摘させる構造にした方が精度が上がりやすいという先述の主張を補強している
- また、この論文が扱っているタスクは数学だけでなく小論文のような自由記述タスクも含んでおり、普段の仕事で扱うようなデータに近い点も評価ポイントとして挙げている

## 検証エージェントを使う手法の弱点：コストと局所最適

- **弱点1: コスト増**。複数のAIモデルを使うため、その分料金と時間がかかる
- **弱点2: 局所最適に陥りやすい**。特定の観点で精度を上げることはできるが、途中で一度スコアを下げないとたどり着けないような停滞的な局面があり、単純にスコアを改善するだけのループではそこそこ良いところで止まってしまうことが結構起きるとしている
- 対策として、最初から1つのプロンプトで進めるのではなく、複数のプロンプトを並列で作って別々に進化させるというやり方を動画作者自身も試したことがあると述べているが、「なかなか奥が深い」として、自動的に最適なプロンプトを設計する方法はまだ自分の中で固まっていないと正直に述べている
- 総括として、ループエンジニアリングは何でも改善できそうに見えるが、実際にはうまくいかないことも多い、と締めくくり、視聴者に同様の実験経験や感想をコメントで募っている
