# 要点

## 「ループエンジニアリング」が急速に広まった経緯

- 2026年6月、AI開発の最先端にいる3人がほぼ同時期に似た主張をし始めたことで火がついたと説明している
- 1人目はピーター・スタインバーガー氏（OpenClaude開発者、現在はOpenAIに所属としている）で、「エージェントにプロンプトを打つな、エージェントにプロンプトを出すループを設計しろ」という趣旨の投稿がバズったとしている
- 2人目はボリス・カーニー氏（Anthropic Claude Codeの責任者としている）で、「私の仕事はループを書くこと」「IDEは半年前に消した」と発言したとしている
- 3人目はDオッマ氏（聞き取り。Googleのエンジニアリングディレクターとしている）で、自身のブログで「ループエンジニアリング」という名前を付けて体系化したとしている

## プロンプト→コンテキスト→ハーネス→ループという段階の変遷

動画は、ループエンジニアリングは突然出てきた概念ではなく、「なんとかエンジニアリング」という呼び名が段階を踏んでパワーアップしてきたものだと位置づけている。

1. **プロンプトエンジニアリング**（〜2024年頃）: 1回の指示の質を上げることが設計の中心だったとしている
2. **コンテキストエンジニアリング**（2025年）: 指示だけでなく、その背景にある情報も含めてモデルに見せる設計だとしている
3. **ハーネスエンジニアリング**（2026年初頭）: ルールや制約、検証をどう設計してAIを走らせるかという段階だとしている。プロンプト・コンテキストの時代がチャットベースだったのに対し、ハーネス以降はAIエージェントがベースになってきたと整理している
4. **ループエンジニアリング**（2026年6月〜）: ハーネスを使って実装させる仕組みそのものを作る段階だとしている

- 重要な点として、これらは「別の概念に切り替わる」乗り換えではなく、前の段階を内包しながらもう1枚ラップしていく関係だと強調している

## ループエンジニアリングの定義と学術的な土台

- ループエンジニアリングとは「指示するのではなく指示する仕組みを作る」ことが根本だとしている
- 従来は人間がプロンプトを打ち、AIが応答し、人間が次の指示を出す、という繰り返しだったのに対し、ループエンジニアリングでは人間がゴールだけを定義し、その仕組みの中でAIが自動的に指示を出し・結果を検証し・次のタスクを決めるということをゴールが終わるまで続けるとしている
- これを人のチームに例えると、従来は自分もプレイヤーとして動く「プレイングマネージャー」型だったのに対し、ループエンジニアリングでは開発フローの仕組み自体を設計し、あとはチームに任せるマネジメント寄りの働き方に近いと説明している
- 思いつきの流行語ではなく、研究上の土台があるとして、**ReAct**（考えて行動して観測してまた思考する、というサイクルを繰り返す考え方）と**Reflection**（失敗を言葉にして記録し次のトライに生かすパターン）の2つを挙げている

## インナーループとアウターループの2層構造

- ループには内側の**インナーループ**と外側の**アウターループ**の2層があるとしている
- インナーループは1つのタスクの中で、編集・テスト作成・テスト実行・失敗検知・修正・再実行というサイクルを、通過するまで繰り返すものだとしている。これにより「完了しました」と言いながら実際には直っていない、という従来のAIコーディングの不満を解消できるとしている
- 検証は何を確認するかを明確にすべきだとし、テストだけでなくセキュリティリスクやコードの品質、仕様との食い違いなど、複数の観点のレビューを重ねるほど検証の精度が上がるとしている
- アウターループは、1つのインナーループ（1機能・1セッション相当）だけでは要件を満たせないため、複数のタスクをまたいでぐるぐる回していくものだとしている。ポイントは、あるタスクでの失敗の教訓を次のタスクに引き継ぐ設計にしておくことだとしている

## ループを構成する「5+1の部品」

- ボリス・カーニー氏（聞き取り）が整理したという「機能するループは5つの部品とプラス1のメモリーでできている」という枠組みを紹介している
  1. **自動化（オートメーション）**: 定期的にタスクを発見しエージェントを起動する、ループのコア部分
  2. **ワークツリー**: 複数エージェントが衝突しないよう作業領域を分離する考え方
  3. **スキル**: プロジェクトの規約を永続化する仕組み
  4. **プラグイン／コネクター**: Slackなど依存ツールと接続し外部世界とつなぐ仕組み
  5. **サブエージェント**: 作る役と検証する役を分離して分業するための仕組み
  6. **＋1 メモリー**: セッションの中ではなく会話の外に状態を永続化する仕組み。完了したタスク・進捗中のタスク・学んだことを書き出すことで、次のループの質が上がっていくとしている

## ルール定義で重要な4つの要素

- ループが「勝手に動くスーパーエンジニア」ではなく「粘り強く動くジュニア」に近いという前提のもと、ルール定義が重要だとして4つを挙げている
  1. **明確なタスク定義**: 完了条件が一言で言えるかどうか
  2. **安全な作業環境**: ワークツリー等で失敗しても全体を壊さない設計になっているか
  3. **視覚的な成功判定**: テスト・リント・型チェックなどで合否を自動判定できるか
  4. **ハードストップ**: 無限ループや暴走を防ぐため、リトライ回数や時間・コストの上限を設け、詰まったら人間に確認する仕組みを入れること

## 自作の実装例：エピックフローと移ロー

- 講師は、アウターループ用のスキル「エピックフロー」と、インナーループ用のスキル「移ロー（聞き取り）」を自作したと紹介している
- **移ロー**（インナーループ）: 実装者が実装 → 別のサブエージェントであるテスターがテスト → 4軸のレビュー（仕様確認担当・コード確認担当・セキュリティ確認担当の3レビューアとしている）を通過 → 実装者に戻してプルリクエストを作成、という流れだとしている
- **エピックフロー**（アウターループ）: 大きな要件を入力すると、まずプランナーが要件をタスクに分解し、依存関係・受け入れ条件・目的を決める → ここで1回人間の承認を挟む → メインエージェントがタスクを1つずつ移ローに渡して実行 → 1タスク完了ごとにエピックのブランチにマージ → 全タスク完了後、最終的な大きなプルリクエストができた時点で再び人間が確認する、という流れだとしている
- プランナーは要件が曖昧な点について質問を返してくるため、要件を詰めてから分解が始まる設計になっており、これが精度の高さにつながっていると説明している

## サブエージェントごとのモデル使い分け

- 計画担当（プランナー）はOpusを使用しているとしている。エピックからのタスク分解、依存関係・受け入れ条件・目的・セキュリティ確認の要否をここで設計するとしている
- 実装担当・テスター・仕様確認担当・コードレビューアはSonnetを使用しているとしている。テスターはPlaywrightを用いてブラウザでの画面確認まで行わせているとしている
- セキュリティ確認担当は重要性からOpusを使用しているとし、コードを書いている時だけ起動するよう設計しているとしている
- 計画フェーズは5〜10分で終わる一方、開発・確認フェーズはタスクの規模次第で時間がかかり、しばしばレート制限に達するとしている
- 必要なスキルとして、ソフトウェア設計（デザインパターンなど）、プロジェクトマネジメント、テスト技法を挙げ、人のチームを動かしてきた経験がループの設計にそのまま生きているとしている
