# 概要

OKF（Open Knowledge Format）を、専用ツール不要でGitとMarkdownだけで成り立つ「AI向け知識共有フォーマット」として紹介する速報解説動画。AI研究者のカーパシー氏が行った先行的な取り組みが発端となり、Google CloudがOKF v0.1として正式な仕様にまとめたと説明されている（まだドラフト段階）。バンドル（ディレクトリ）・概念ファイル（YAML frontmatter + Markdown本文）・相互リンクという3つの要素を、Google Analytics 4の知識バンドルを例に具体的に解説している。

# 要点

## OKFが生まれた背景（動画の主張）
- AIに「売上テーブルの定義は?」と聞くと、定義はデータカタログに、集計ロジックはコードコメントに、JOINのやり方は「誰かの頭の中」に、というように知識の置き場所・形式がバラバラになっている、という課題提起がされている
- AIがこれらを読むには専用コネクターが必要で、どれか一つが壊れると読めなくなる、という問題意識
- OKFの考え方は「サービスを増やすのではなく、形式を1つに決める」こと
- 「フォーマット」と「サービス」の違いとして、サービスは利用にログイン・API・ベンダーの継続稼働が前提になるが、フォーマットは「このファイルはこう書く」という約束事だけで成立する点が強調されている

## OKFの位置づけ
- 発端はAI研究者のカーパシー氏が行った先行的な取り組み（動画中では聞き取りにくい固有名称で言及されており正式名称は不明）で、それをGoogle CloudがOKF v0.1として正式な仕様にまとめたと説明されている
- Google Cloudが公開したばかりでまだドラフト段階の新しい仕様、と紹介されている
- OKFはMarkdownファイルに「こう書きましょう」という規約であり、GitHubに置ける、`cat`で読める、テキストエディタで開ける、専用ツールが不要
- 「Gitがあれば読める／Gitクローンできれば配れる」がOKFのスタックの原則として説明されている

## バンドル（知識のまとまり）の構造
- 知識のまとまりを「バンドル」と呼び、その正体はただのディレクトリ（フォルダ）
- フォルダ1個が1つの知識の塊、という考え方
- バンドルはルート直下に `datasets/` や `tables/` のようなサブディレクトリを持つ構成例が示される
- サブディレクトリ名・ファイル名は基本的に自由（例: `tables/orders.md` があればそれが「orders」という1つの概念を表すファイルになる）
- 例外は `index.md` と `log.md` の2つで、これは予約済みファイル名であり概念定義ファイルとしては使えない
  - `index.md` はそのディレクトリの目次
  - `log.md` は変更履歴
- 配布はGitリポジトリ全体でもサブフォルダ単位でも可能

## 概念ファイルの構造（frontmatter + Markdown本文）
- 概念ファイルは「上がYAML frontmatter、下がMarkdown本文」の2パート構成
- frontmatterにはそのファイルが何を表すかのメタデータ（type、titleなど）を書く
- **必須フィールドはファイル全体で `type` の1つだけ**で、それ以外は任意
- 「不完全な知識でも有効」という設計思想が明言されており、`type` さえ書かれていればOKF準拠とみなされる
- Markdown本文は自由記述で、使用例としては `Schema` / `Examples` / `Citations` の見出しが挙げられ、実際の運用では `Joins` や `Metrics` もよく使われると説明されている
- 概念ファイルで使う仕様フィールドは6つある、と説明されているが、動画内で具体的に名前が挙がったのは以下（残りのフィールド名は言及されていない）
  - `type`: 自由形式。決まった選択肢のリストはなく、BigQueryテーブルでもメトリックでもPlaybookでも自由に指定できる。未知の `type` 値でも読み手はそれを無視・破棄せず保持するよう定められており、それによって未知の値でもクラッシュしない拡張しやすい設計になっている、とされる
  - `title`
  - `description`: 自由テキスト
  - `resource`: 自由テキストではなく **URI** で書く（例: BigQueryやHexの形式）。動画内で「間違えやすい点」として注意喚起されている
- `OKFVersion` フィールドはバンドルルートの `index.md` 専用で、個々の概念ファイルには書かない

## 相互リンクとナレッジグラフ化
- 概念ファイルの中に他ファイルへの通常のMarkdownリンク（テキスト＋パス）を書くことで、バラバラなファイル同士がグラフ構造として繋がる
- リンクのパスはバンドルのルートを起点にスラッシュで始まる絶対パスで書くことが推奨されている
- リンクで繋ぐことでデータセット・テーブル・メトリックのような「知識のネットワーク」ができる、とされる
- 「フォルダという木構造が、リンクによってグラフになる」ことがOKFの核心だと動画は位置づけている
- 概念ID（識別子）はファイルパスから `.md` を除いたもの（例: `tables/orders.md` → `tables/orders`）
- リンク先が存在しない（壊れている）状態でも、そのファイル自体は有効なOKFとみなされる

## 予約ファイル index.md / log.md の書き方
- `index.md` はそのディレクトリに何があるかを一覧にするファイルで、YAML frontmatterは不要、`type` も書かない
- 例外として、**バンドルルートの** `index.md` だけは `OKFVersion: 0.1` のような形でバージョンを書く
- それ以外のディレクトリの `index.md` はfrontmatterなしのMarkdownで目次を書くだけでよい
- `log.md` は変更履歴ファイルで、新しい変更を上に書く。AIが「この知識はいつ更新されたか」を把握するために使われる、と説明されている

## 実例: Google Analytics 4の知識バンドル
- 動画内で実例として、GA4（Google Analytics 4）の知識をOKF化したバンドルが紹介されている
- `metrics/` ディレクトリの下に8個のファイルがあり、コアとなるメトリクスがそれぞれ独立したMarkdownファイルになっている
- 興味深い点として、これらのファイルの `type` は「metric」ではなく「reference」で統一されていることが挙げられている
- これは `type` が厳密な分類ではなく、ファイルを作る人（作成者）が自由に決めてよいものであることを示す例として紹介されている
- 数式や計算ロジックはMarkdown本文側に記述する
- テーブルとメトリクスが別ファイルで管理されているため、AIが必要な概念だけを個別に参照できる、という利点が述べられている

## 準拠基準とフィールドの拡張性
- OKF準拠の基準は「`index.md` と `log.md` 以外の全てのMarkdownファイルに `type` フィールドがあること」の1点のみ、と説明されている
- リンク切れや未知のフィールドがあってもOKF準拠として扱われる
- 独自フィールドは自由に追加してよく、読み手は知らないキーであっても削除せず保持するよう定められている

## 動画のまとめ（動画内で提示された3点）
1. OKFはMarkdownとYAML frontmatterだけで成り立つフォーマットで、専用ツールは不要、Gitクローンでバンドルを配布できる
2. 必須フィールドは `type` の1つだけで、不完全な知識でも有効とみなされ、独自フィールドで自由に拡張できる
3. Markdownリンクで概念同士をつなぐと、フォルダという木構造が知識グラフに変わる。これがOKFの核心だと述べられている
- 出演者の感想として、「Google Cloudが出したばかりの新しい仕様なのにシンプルであること」「フォーマット自体は単純に保ち、仕組みの実現はMarkdownとGitに任せるという割り切りが面白い」という見解が語られている
