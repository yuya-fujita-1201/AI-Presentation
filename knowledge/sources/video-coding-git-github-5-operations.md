# 要点

## GitとGitHubの役割の違い

- Gitは自分のパソコン（ローカル）上で編集の履歴を管理する「バージョン管理機能」であり、要するに今の状態を保存する「セーブポイント」の機能であるとしている
- GitHubはそのGitで作った履歴（セーブポイント）をクラウド上にアップロードし、共有・公開・コミュニケーションを行う場所であるとしている
- Gitだけでもバージョン管理はできるが、業界標準としてソフトウェアエンジニアはGitHub上にセーブポイントをアップロードしてデータを共有していると説明している。GitとGitHubを両方使うことで、手元での作業→保存→クラウドへのアップロード→他のサーバーへの移動によるWeb公開、という一連の流れが実現できるとしている

## 削ぎ落とした5つの操作

- 本来Gitには20個ほどの操作があるが、バイブコーディング超入門講座として削れるところを全部削った上で、ブランチ・コミット・プッシュ・プルリクエスト・プルの5つだけに絞って解説すると述べている
- 「世の中のGit講座の中でも1番削ぎ落としているくらい削ぎ落としている」とし、詳しい人が見れば足りない機能があると思うかもしれないが、ここまで削ぎ落としてもクロードコードやCodexといったAIの支援があれば十分Gitを使いこなせるはずだという見立てを示している

## ブランチ：履歴を枝分かれさせる機能

- ブランチは履歴を枝分かれさせる機能であるとし、ゲームでボス戦の手前でセーブしておき、負けたらそのセーブポイントに戻ってやり直す動作に例えている
- 図の左から右への時間軸上に並ぶ小さな丸をセーブポイントに見立て、通常のソフトウェアと異なりGitでは歴史を複数の経路に枝分かれさせられる点を説明している。例えばゲームで右に行くか左に行くかで枝分かれがあったとしても、それぞれの分岐先での作業を分けて記録できるとしている
- ブランチを切って枝分かれした先での作業は、元のセーブポイントの状態には影響しないとしている。枝分かれした先で作業した結果、良い機能ができれば元の歴史に戻して統合することができ、うまくいった枝分かれを正しい歴史として採用できると説明している

## コミット・プッシュ・プルリクエスト・プル

- コミットは、この小さな丸（セーブポイント）そのものを作る操作であるとし、ブランチを切って編集し、いい感じになったらコミットする、という作業をこまめに繰り返しながら前に進むのがGitでの基本的な作業だと説明している
- プッシュは、手元のパソコン上での作業をGitHubのクラウド上に送信する操作であるとしている
- プルリクエスト（PR）は、自分のブランチで行った新しい作業を、メインと呼ばれる中心の歴史に取り込んでほしいとリクエストする操作であるとしている。GitHub上でプルリクエストの内容を見たりレビューしたりできるとも述べている
- プルは、クラウド上にある最新のメインの状態を自分の手元のパソコンに引っ張ってくる操作であるとしている。複数人で開発している場合、自分と他の人がそれぞれ別のブランチで作業してプルリクエストをマージしても、他の人が加えた変更（例：山田さんの機能）は自分の手元には自動的に反映されないため、プルによって最新状態を取得する必要があると説明している

## コンフリクト：衝突の解消は人間の役目

- コミット・プッシュ・プルリクエスト・プルの一連の流れに加えて重要な概念として、コンフリクト（衝突）を挙げている
- コンフリクトは、複数人が同じ箇所を別々の内容に変更した際に発生するとし、例としてホームページのテーマカラーについて、あるブランチが「赤」に、別の山田ブランチが「青」に変更してそれぞれプッシュ・プルリクエストを送ったケースを挙げている
- コンフリクトが起きるとGit側が単純にはプルリクエストを採用できない状態であることをユーザーに伝えてくるとし、どちらの変更を採用するかは最終的に人間が判断して決める必要があると説明している

## 実演：クロードコードでの5操作の実行

- 講座の締めくくりとして、ブランチを切ってコミットしてプッシュしてプルリクエストを送ってプルしてくるという一連の流れを、実際にクロードコードを使って実演すると述べている
- クロードコードにテキストファイルの作成と最初のセーブポイント（コミット）の作成を依頼し、ファイルが作成されたことを確認している
- 続けて、現在のブランチの状況（ブランチ「メイン」にいること）や、これまでに入ったコミットの一覧をクロードコードに尋ね、意図通りにコミットが作成されていることを確認する様子を見せている
