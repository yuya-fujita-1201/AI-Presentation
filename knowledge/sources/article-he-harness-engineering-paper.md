# 概要

arXivは、"AI Harness Engineering: A Runtime Substrate for Foundation-Model Software Agents" と題する論文を公開している。同論文は、基盤モデル（foundation model）が自動コード生成を一変させた一方で、自律的なソフトウェアエンジニアリングエージェントは現実的な開発環境において依然として信頼性を欠いていると指摘している。この能力ギャップについての支配的な説明はモデルの能力不足にその原因を求めるものだが、同論文はこれとは異なる原因の所在を提案していると述べている。

# 要点

## モデル・ハーネス・環境から成るシステムという捉え方

同論文は、ソフトウェアエンジニアリング能力はモデル単体の性質ではなく、モデル・ハーネス・環境から成るシステムから創発する性質であると論じている。ここでいう「ハーネス」とは、基盤モデルのエージェントがプロジェクトをどう観察し、どう行動し、どうフィードバックを受け取り、変更が完了したことをどう確立するかを媒介するランタイム基盤であると説明されている。この捉え方を、C_system = F(C_model, C_harness, C_environment, T) という式で定式化しており、C_modelは基盤モデルの潜在能力、C_environmentはソフトウェア環境が公開している内容、C_harnessは両者を媒介するランタイム基盤、Tはタスク分布を表すとしている。

この基盤を同論文は「AI Harness Engineering」と呼び、基盤モデルのソフトウェアエージェントを取り囲み、コンテキスト・ツール・プロジェクトメモリ・タスク状態・可観測性・失敗帰属・検証・権限・保守状態を管理するランタイム層であると定義している。

> 引用: 「An AI Harness Engineering is a runtime substrate surrounding a foundation-model software agent that manages context, tools, project memory, task state, observability, failure attribution, verification, permissions, and maintenance state, so that latent model coding capability becomes auditable software-engineering behavior.」

ハーネスこそが、モデルの潜在能力が監査可能なソフトウェアエンジニアリング行動になるかどうかを決定づけるのだと同論文は述べている。

## 11の構成要素の責務

同論文は、この基盤（AI Harness Engineering）を構成する11の責務を特定している。すなわち、タスク仕様（task specification）、コンテキスト選択（context selection）、ツールアクセス（tool access）、プロジェクトメモリ（project memory）、タスク状態（task state）、可観測性（observability）、失敗帰属（failure attribution）、検証（verification）、権限（permissions）、エントロピー監査（entropy auditing）、介入記録（intervention recording）の11項目である。

## H0〜H3の4段階ラダーとトレースベースの評価プロトコル

同論文は、ハーネスが提供するランタイム支援を段階的にエージェントへ開放していく4段階のラダー（H0〜H3）を通じてこの基盤を運用可能にしていると説明している。あわせて、各エージェントの実行を監査可能な「エピソードパッケージ」に変換する、トレースに基づく評価プロトコルを提案している。統制された検証タスクにこの枠組みを適用したところ、エピソードパッケージが持つ証拠の構造はハーネスの段階に応じて体系的に変化したとしている。低い段階では最終的なパッチのみしか得られない一方、高い段階では再現ログ、失敗帰属、決定的な要件チェック、構造化された検証レポートが生成されると報告されている。

## 問いの立て直し

同論文は、この枠組みによって自律的ソフトウェアエンジニアリングの中心的な問いが立て直されると論じている。すなわち、「基盤モデルがパッチを生成できるか」ではなく、「モデル・ハーネス・環境から成るシステムが、検証可能な形で正しく、帰属が明確で、保守可能な変更を生み出せるか」が問われるべきだとしている。そのうえで同論文は、基盤モデルのソフトウェアエージェントが今後必要とするランタイムシステムに関する研究プログラムの概要を示していると述べている。

## 能力ギャップの背景説明

同論文は導入部で、基盤モデルが急速に高性能なプログラミング支援ツールになったと述べている。関数を生成し、ファイルを修正し、コードを説明し、テストを書き、ツールを呼び出し、ソフトウェアリポジトリと対話できるようになったとしている。この進歩は、高レベルの開発タスクを受け取り、実装・テスト・検証・保守まで最小限の人間の監督で遂行する自律的ソフトウェアエンジニアリングエージェントという野心を後押ししたと説明している。

一方で、最近のベンチマークやエージェントシステムは、ローカルなコード生成と完全なソフトウェア作業との間のギャップが現実に存在し、根強く残っていることを示しているとしている。正しいローカルパッチを書けるモデルであっても、誤ったファイルを調べたり、根本のAPIの挙動が壊れたままユーザーインターフェースだけを表面的に修正したり、誤ったテストを実行したり、失敗を誤解釈したり、タスク状態を忘れたり、不要になった成果物を残したり、十分な検証なしに成功を宣言したりして、タスク自体は完遂できないことがあると指摘している。人間が関与し続けているのは、主にすべてのコードを書いているからではなく、関連するコンテキストを特定し、リポジトリ構造を説明し、ツールを選び、フィードバックを解釈し、アーキテクチャ上の境界を強制し、挙動を検証し、残骸を片付けるという、不足しているランタイム支援を提供しているからだと同論文は論じている。

このギャップについての支配的な説明は、モデルの能力不足にその原因を求めるものだと同論文は述べている。この見方では、あるエージェントがソフトウェアタスクに失敗するのは、モデルがコーディング・推論・計画・ツール利用においてまだ十分な能力を持っていないからであり、この分野の課題はより優れたモデルを訓練するか、より洗練されたエージェントループへと組み合わせることだとされる。同論文はモデルの能力が重要であることには異論を唱えないとしつつ、この捉え方は不完全であると主張している。

ソフトウェアエンジニアリングは長期的・状態を持つ・ツールを媒介とした・フィードバック駆動の活動であり、コンテキスト管理・プロジェクトメモリ・ツールインターフェース・実行トレース・検証シグナル・権限・ロールバック・保守の規律に依存していると同論文は述べている。人間の開発者向けに設計された開発環境の中に基盤モデルを置くと、これらの支援の多くはエージェントにとって暗黙的・アクセス不能・不安定なままになるとしている。人間の開発者が社会化・ドキュメント・経験を通じて獲得するこれらの構成要素は、モデルの呼び出しに対して自由には利用可能ではなく、明示的に公開・構造化・トレースされる必要があるとし、そうでない場合エージェントは即興で対処するか、人間にギャップを埋めるよう求めることになると説明している。
