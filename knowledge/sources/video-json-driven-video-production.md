# 概要

「クロノITチャンネル」の運営者（投稿主）が、動画編集ソフトも動画生成AIも一切使わずに解説動画を制作している自作パイプラインを解説する動画。台本・話者・セリフごとの表示スライド・BGM・背景・セクション名など、動画に必要な情報をすべて1枚のJSONファイルにまとめ、それをRemotion（コードで動画を組み立てて出力する技術）ベースの独自システムに読ませることでMP4動画とショート動画を生成し、さらに9言語への翻訳も同じJSON構造のまま行って10か国語分の動画を同時生成している、と述べている。動画上で解説役を務める「しゃりな」「レンカ」という2体のオリジナルキャラクター自身も、この仕組みで生成された存在であり、キャラクター画像はnanobananaで作られていると説明されている。

# 要点

## 全体パイプラインの流れ
- ネタ決め → 音声入力によるマークダウン化（制作のスタート地点）→ AIエージェントによる詳細調査・エビデンスチェック → 構成案の検討・台本作成 → AIレビュー＋投稿主による専用Web UIでのレビュー → セリフに割り当てるビジュアル（スライド・図解）の作成 → 専用TTSモデルによる音声ファイル生成（同時にサムネイル生成）→ 冒頭ダイジェスト・OP/ED・アイキャッチ・背景の設定 → JSON完成 → システムに読ませてMP4として出力、という流れだと説明している
- 本編完成後、同じ仕組みでショート動画（簡易版）も作成し、その後、日本語版の台本を9言語に翻訳して10か国語分の動画を作り、各言語チャンネルへ投稿すると述べている
- 台本作成・ビジュアル作成・動画編集・サムネイル作成・ショート動画作成・多言語化の各工程は、それぞれ専任のAIエージェントが担当し、成果物のチェックもまずAIが行い、その上で人間（投稿主）のレビューを各ステップに適宜挟む構成になっている、としている

## JSON1枚に何を集約しているか
- セリフ、話者（どちらのキャラクターが話すか）、セリフ中に表示するスライド／図解、BGM、背景、セクション名など、動画に必要な情報がすべて1つのJSONファイルに入っており、それをシステムに読ませるだけで動画が組み上がる仕組みだと説明している
- セリフ1件は、話者・表情指定（「驚き」「ドヤ顔」など決まったタイプから選択）・画面に字幕として表示するテキストといった複数のフィールドを持つデータであり、台本作成の段階でこのJSONの元になる部分を作り、後続のビジュアル作成の段階でビジュアル要素のフィールドを追記していく、という二段階の作り方をしていると述べている
- Remotionではシーンごとの長さ（duration）をフレーム単位で厳格に指定する必要があるため、生成した音声ファイルの再生時間からセリフごとのdurationを逆算し、それを頭から積み上げることで各セリフの開始フレームを機械的に決定している。字幕表示・キャラクターの口パク・ビジュアルの切り替えはすべてこのタイミングに同期しており、逆に無言のシーンを作りたい場合は手動でdurationを調整する必要がある、と述べている
- JSONはzod（スキーマ検証ライブラリ）で検証しており、設定忘れや設定ミスをその場で検知できるようにしている。字幕が画面からはみ出していないかを検証するスクリプトも用意しているとしている
- 概要欄に載せるチャプターのタイムスタンプも、各セクション開始時刻が音声長の積み上げから機械的に算出できるため、自動生成しており手書きはしていないと述べている

## ビジュアル生成：AIに自由度を与えず「型」から選ばせる設計
- ビジュアル（スライド・図解画像）作成では、AIに自由に作らせるのではなく、スライド・図解・コードブロック・グラフといったタイプをあらかじめ多数用意しておき、AIはセリフに合うタイプを選んで雛形に最小限の変更を加えてはめ込むだけ、という仕組みにしていると説明している（10分の動画あたり30〜40個程度作成）
- 用意されている型の例として、比較用2列スライド、コードの差分表示、ターミナルの出力画面、Xのポスト表示、GitHubリポジトリの情報カード、スター数推移グラフ、統計カードなどを挙げている。型に収まりにくい図解については、レイアウトや部品のパターンをいくつも用意し、そこから選んで組み合わせる形をとっているとしている
- これらの型は、文字数や書き方でスタイルが大きく崩れないよう人間の目で時間をかけて確認しながら作り込んだ「このシステムの集大成」と位置づけており、AIにゼロから作らせず整備された限られた選択肢の中から選ばせることが品質の安定・向上につながると考えている、と述べている
- 画像生成AIでスライド画像自体を一発生成する手法はあえて使っていないとし、その理由として、その手のスライドは情報を詰め込みすぎてごちゃごちゃした「説明の画としてふさわしくない」デザインになりがちだから、という考えを述べている
- 操作動画やスクリーンショットが必要な場面は、この工程で洗い出した上で人間が撮影するか、任意のページへのスクロールや特定要素のハイライトなどを行う撮影用AIスキルを使い分けて撮影しているとしている
- 全ビジュアルについて別途スクリーンショットを撮影し、専用のレビューエージェントにはみ出しや重なりがないかをチェックさせた上で、投稿主も見た目を確認し、わかりにくい図があれば手直しすると述べている

## 動画編集：Remotionと独自Web UI
- 動画編集の土台はRemotion（コードで動画を組み立てて出力する技術）であり、Remotion付属の編集用UIは使わず、独自に構築したWeb UIにプレビューを組み込んで確認していると説明している
- Remotionは動画を構成する1フレーム1フレームをReactコンポーネントとして描画する仕組みで、コンポーネントには「いま何フレーム目か」という数値が渡ってくる。時間経過で自動的に動く通常のCSSアニメーションは使えず、フレーム番号から毎回位置や透明度を計算する必要があると述べている。背景アニメーション、キャラクターの上下バウンス、字幕やビジュアルの表示切替はすべてこのフレーム番号ベースの計算で動いており、それゆえ音声のタイムラインと完全に同期する、としている
- キャラクター「しゃりな」「レンカ」はnanobananaで生成したオリジナルキャラクターで、数百〜千を超える出力を試した中から気に入ったデザインだけを採用したと述べている。表情差分・口差分の画像を切り替えてアニメーションさせており、口パクは発話中のみ、表情は台本で指定した感情に合わせて切り替わり、話者は上下にゆっくりバウンスして誰が話しているか分かるようにしている。瞬きは表情差分ごとに素材を用意するのが難しくまだ実装できていない、としている
- 背景も静止画ではなく常時動きのあるアニメーションにしており、現在20種類ほど用意していると述べている
- 型を作り込む段階でさまざまな表現を人の目で確認しながら丁寧に調整しておいたため、通常の動画編集ではほぼノータッチで動きが付けられるようになった、としている。BGM・効果音はファイルごとに音量を設定し、キャラクターごとの話速・音量も調整できるようにしていると述べている
- 動画全体の組み立てとして、冒頭のダイジェスト（動画内の重要そうなセリフを4つほどピックアップして本編前に紹介）、オープニング／エンディング、アイキャッチ、動画背景を一定のルールで設置する構成にしていると述べている
- 修正が必要になった場合はJSONを直して書き出し直すだけであり、動画生成AIを使っていないため映像生成自体には課金が発生せず、Claude CodeやCodexといったサブスク型CLIサービスの範囲内で制作が完結しているため、ランニングコストを抑えたぶん内容そのものに集中できている、と述べている

## サムネイル作成
- サムネイルもCanvaやPhotoshopのような画像編集ソフトは使っておらず、画像生成AIでテキストまで含めて一発生成する手法（YouTube自体が持つサムネイル生成機能を含む）も基本的に使っていないと述べている。理由として、その種のサムネはAI生成らしさが出てごちゃごちゃし、何を伝えたいか分からないデザインになりがちで良くないと考えている、としている
- 背景画像はAIで複数パターン生成し人間が一番良いと思ったものを選び、テキストはAIにいくつか候補を挙げてもらった上で最後は人間の目で決めており、AI案を使わずオリジナルの文章を書くことも多いと述べている（サムネの文章は2文までとし、3文以上は詰め込むべきでないと考えている）
- 選んだ背景・テキストにキャラクターを差し込み、文字の配置やレイアウトは独自Web UI上のサムネイルエディタで調整している。最終的なサムネイルのデータ（どの画像にどのテキストをどう配置したか）もすべてJSONにまとまっており、そのおかげで同じ構成のまま他言語版サムネイルも作れる、と述べている（基本は日本語版のみ手作業で作り、他言語は機械的に翻訳して生成しているため、言語ごとにサムネを編集できる機能自体はあまり出番がないとしている）

## ショート動画
- 本編を作り終えたら、その簡易版として縦型のショート動画も毎回作成しており、本編に興味を持ってもらう入口の役割だと述べている。作り方は本編と同じ仕組み（ショート用のJSONを作り同じシステムでレンダリング）だが、縦画面向けに画面構成や進行速度を調整しているとしている
- 台本は本編の台本から見どころを抽出し、「冒頭のつかみ→ハイライト→本編への誘導」という短い構成に組み直しており、これもAIレビューと人間チェックを通していると述べている。ショート需要の高さから台本を何度も作り直すことがあるとしている
- ビジュアルや字幕位置もショート専用に1つずつ定義・目視設計しており、どんな内容が入ってもある程度崩れないようにしていると述べている。ショート用サムネイルも別途生成していると述べている
- ショート動画についてはまだ練り込みが甘いと考えており、技術紹介を端的に伝える適切なフォーマットを今後も模索していきたい、としている
- 本編の簡易版とは別に、毎日のITニュースを紹介するショート動画にも取り組んでいたことがあるが、本編とは別に毎日情報収集して動画を作るのは労力がかかりすぎて厳しかったため、現在は別の形を検討中だと述べている

## 多言語化（10か国語対応）
- 本編とショートを日本語で作り終えたら、英語・中国語・韓国語・ドイツ語・フランス語・ロシア語・ポルトガル語・スペイン語・イタリア語の9言語に翻訳し、10か国語分の動画を制作していると述べている
- 翻訳の対象はセリフだけでなく、ビジュアル内のテキスト、サムネイルの文言、タイトルや説明文まで動画の全要素に及び、これは動画の全要素をJSONで管理しているからこそ実現できる仕組みだと説明している
- 翻訳もAI任せにはせず、キャラクターの口調が保たれているか・訳が自然か・元の意味に忠実か、という観点で専用のレビューを通しており、全言語を人間の目で確認するのは現実的でないためこの部分は仕組みでカバーしている、としている。音声も各言語で生成し、同じシステムでレンダリングして各言語のチャンネルに投稿すると述べている
- 日本語版で人間のチェックを終えた内容だけを翻訳して展開しており、コスト面では、創造性が必要な工程には高性能なAIモデル、翻訳のように決まった作業には軽めのモデルを使い分けていると述べている。また、JSONをまるごとAIに渡すと翻訳と無関係なデータにもトークンを消費してしまうため、翻訳が必要な箇所（セリフや文言など）だけを抜き出して渡すようにしており、プロンプトの骨格は全言語で共通にして言語ごとの差分だけを差し込む作りにすることで、無駄なトークン消費を抑えていると説明している

## 品質改善の仕組み（修正ログの活用）

- 見えてきた傾向は生成用プロンプトやレビューの観点に反映し、同じ直しを人間が二度やらなくて済むよう仕組み自体を改善しているとしている。何か失敗が起きた際もその失敗をレビュー観点に練り込むことで、同じ失敗が起きにくくなるようにしており、AIレビューが何を指摘したかもログに残してレビュー自体の精度改善の材料にしている、と述べている。その結果、回を重ねるごとに人間が直す量は減ってきているとしている

# スライド資料への応用ポイント

この動画自体はスライド資料の話をしていないが、「動画制作の全要素を1枚のJSONで管理する」という設計思想には、スライド資料（HTML/PowerPoint）をJSONパラメータで管理する仕組みに転用できそうな原則がいくつか読み取れる。

- **全要素を1つの構造化データに集約し、レンダラーはそれを読むだけにする**: セリフ・話者・ビジュアル・BGM・背景をすべて1枚のJSONにまとめ、システムに読ませるだけで動画が組み上がる、という発想は、スライドの本文・レイアウトタイプ・配色・強調ポイントなどをJSONパラメータとして持たせ、表示ロジック（HTML/PPT生成）とデータを分離する設計にそのまま転用できる
- **AIに自由度高くゼロから作らせず、整備済みの「型」から選ばせる**: ビジュアル作成でAIに「比較2列」「コード差分」「統計カード」のような既定タイプの中から選ばせ、雛形に最小限の変更を加えてはめ込む方式にすることで品質を安定させている、という考え方は、スライド生成AIにも「あらかじめ用意したレイアウト型の中から選んで中身だけ差し込ませる」設計として応用できる
- **修正はJSONの該当フィールドを直して再出力するだけ**: 「修正したいところが出たらJSONを直して書き出し直すだけ」という運用は、まさにユーザーが目指す「スライドをAI再生成なしに微修正する仕組み」の直接的なモデルケースになる
- **一発生成型の画像/動画生成AIをあえて避ける**: スライド画像自体を画像生成AIで一発生成する手法を、情報過多でごちゃごちゃになりやすいという理由で避けている点は、AI一発生成スライドが陥りがちな崩れたデザイン問題への対策として、構造化データ＋テンプレートレンダリングという方向性の裏付けになる
- **スキーマ検証で設定漏れ・ミスをその場で検知する**: zodによるJSONスキーマ検証は、スライドJSONでも必須パラメータの欠落や型ミスを機械的に検知する仕組みとして応用できる
- **崩れ検出の自動チェック＋AIレビューの二段構え**: 「字幕が画面からはみ出していないか」を検証するスクリプトと、スクリーンショットを専用エージェントにレビューさせる仕組みの組み合わせは、スライドの「テキストがボックスからはみ出していないか」等のレイアウト崩れチェックに転用できる
- **テキストと構造を分離して多言語（多バージョン）展開する**: 全要素をJSONで管理しているからこそ、同じ構造のまま他言語版・他サムネ版を機械的に量産できている、という点は、スライドでも文言と構造を分離しておけば言語差分やトーン差分だけを展開できるという設計原則として参考になる
- **修正ログを溜めてプロンプト・レビュー観点にフィードバックする改善ループ**: 人間の修正パターンをログ化し、繰り返される修正傾向を生成プロンプトやレビュー観点に反映する仕組みは、スライド生成AIのプロンプト・チェックリスト改善にも応用できる
- **AIに渡すデータは全体ではなく必要な箇所だけ抽出する**: 翻訳時にJSON全体ではなく翻訳対象のフィールドだけを抜き出して渡すことでトークンを節約している設計は、スライドの部分修正時に変更箇所の差分だけをAIに渡す設計のヒントになる
