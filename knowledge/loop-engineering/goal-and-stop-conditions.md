# ゴールと停止条件の設計——ループの核心は「止め方」

ループを組むときに最初に気になるのは「何回回すか」だろう。だが資料が口をそろえて言うのは、**設計の中心は回し方ではなく止め方だ**ということである。noteの入門記事はこれを一言で表している（[記事: note](../sources/article-le-note-masawunder-goal-loop-design.md)）。

> 公式が定義した「ループ」の核心は停止条件

同記事の筆者は、ループという仕組みで重要なのは何度回すかではなく、**いつ・どうやって止めるか**だと位置づけている。この記事だけの見立てではない。MindStudioの記事も、ゴールなしではループが無期限に実行されるか恣意的に終了すると述べており（[記事: MindStudio](../sources/article-le-loop-engineering-mindstudio.md)）、Qiitaの実装記事も停止条件を明文化することが暴走防止の鍵になるとしている（[記事: Qiita](../sources/article-le-qiita-syoitu-loop-engineering.md)）。**独立した3本の記事が、同じ場所を設計の急所として指している。**

## まずゴール、次にループ

順番の話から始める。MindStudioの記事は、この方法論における最も一般的な失敗として次を挙げている。

> loop engineering isn't just about automating repetitive tasks. It enables agents to handle tasks where the right sequence of steps isn't known in advance. The most common mistake in loop engineering is starting with the loop and figuring out the goal later.

すなわち、**ループから作り始めてゴールを後から考えることが最もよくある失敗**だという指摘である。ループエンジニアリングの価値は、事前に手順が分かっているタスクを機械的に繰り返すことではなく、事前に正しい手順が確定できないタスクに対して、エージェント自身が観察と評価を通じて手順を見出すところにある——だからこそ、「どこに着けば終わりか」が先に決まっていないと、器だけが空回りすることになる。

まさおAIじっくり解説chの動画も、ループ設計の4ポイントの1番目にゴールの明確化を置き、**計測できる形で**ゴールを設定すべきだとしている（[動画: まさおAIじっくり解説ch](../sources/video-le-loop-design-four-points.md)、聞き取り）。同動画は、LLMジャッジや複数のLLMが合格と判定するまで、といった方式も一例として挙げている。

同動画はさらに、「ゴール」と「ループ」は別の概念だと整理している（聞き取り）。ゴールは条件を満たしているかどうかを判定するものであり、ループは目標から継続条件へと繰り返していくものであって、両者は異なるという。この区別は実装の語彙にも現れていて、MindStudioの記事は繰り返す器を `/loop`、成功条件の定義を `/goal` として分けている（[記事: MindStudio](../sources/article-le-loop-engineering-mindstudio.md)）。

## /goal と /loop は別のものである

Claude Code には両方の名前のコマンドがあり、混同されやすい。noteの記事は両者を次のように定義して区別している（[記事: note](../sources/article-le-note-masawunder-goal-loop-design.md)）。

| コマンド | 定義（同記事より） | 性質 |
|---|---|---|
| `/goal` | 成功基準を先に定義し、達成か最大ターン数で止めるゴール駆動 | 条件を満たすまで続く |
| `/loop` | 指定した間隔でローカル実行を繰り返す時間駆動 | 決められた間隔で回るだけ |

**名前が「ループ」だからといって、それが本記事で言うループエンジニアリングの実装とは限らない。** 成果を検証して改善を重ねたいのであれば、時間駆動の繰り返しではなく成功条件つきの駆動を選ぶことになる。

にゃんたのAIチャンネルの動画も、独立にこの区別を述べている。`/loop` は単純に「定期的に実行する」ためのコマンドであり、「AIが実行→結果を検証→再実行」という本来のループを組みたい場合は `/goal` の方が正しいアプローチだと説明している（[動画: にゃんたのAIチャンネル](../sources/video-ge-nyanta-loop-graph-claude-code.md)、聞き取り）。noteの記事とは別系統の動画でも、同じ「ゴール駆動と時間駆動は別物」という整理にたどり着いている。

noteの記事は、`/goal` を支える仕組みについても説明している（[記事: note](../sources/article-le-note-masawunder-goal-loop-design.md)）。

> Claude が止まろうとするたびに、作業モデルとは別の evaluator が条件を判定します。未達なら作業に戻され、達成するか最大ターン数に達するまで止まりません

作業しているモデル自身が「終わった」と判断しても、別の評価役が判定しなければ作業に引き戻される、という構造である。**作る役と判定する役を分けるという発想**がここに埋め込まれており、この論点は[作る役と採点する役を分ける](./maker-checker-separation.md)で単独に扱う。

なお同記事は、人がどれだけ関与するかの度合いに応じて、ターン駆動・ゴール駆動・時間駆動・自律駆動という4分類を「人がどれだけ横に立つかの階段」として整理している。

## 停止条件を1つにしない

止め方を決めたつもりでも、条件が1本だと抜ける。noteの記事の筆者は、自身の失敗を次のように書いている。

> 停止条件を1つだけにした時は失敗しました。スコアだけを見ると、伸びない時に回り続けます

品質スコアだけを見ていると、スコアが伸び悩んだときにループが空転し続ける。この失敗を踏まえて同記事の筆者が実際に採用した停止条件は、**品質スコアが閾値以上・最大12イテレーション・最大360分という3重構成**である。3つは性質が異なる——1つ目は達成による停止、2つ目は回数による打ち切り、3つ目は時間による打ち切りだ。**達成しなかった場合の逃げ道を2本用意している**点が要点である。

Qiitaの記事も、Claude Code での実装（3ファイル構成の詳細は[ループを支える部品](./loop-parts-and-harness.md)の最小構成を参照）の CLAUDE.md に、達成条件（全チェック通過）・回数上限（最大5回）に加えてもう1種類の停止条件を書いている（[記事: Qiita](../sources/article-le-qiita-syoitu-loop-engineering.md)）。

- 失敗が繰り返された場合の停止基準は「**同じエラー2回連続**」。同一の失敗が2回続いた時点で止める

同記事はさらに、Claude Code 以外の実装例として Mastra フレームワークの Goals 機能にも触れている。judge（別モデルによる採点）・maxRuns（30、空回りの上限）・prompt（完了条件の明記）という3要素は、達成条件・回数上限という上と同じ発想がフレームワークをまたいで現れていることを示す。ただし著者はこの機能について「experimental機能のため将来変わる可能性あり」と注記している。

「同じエラー2回連続」は、回数上限や時間上限とは別の観点である。**上限に達する前に、進んでいないことを検知して止める**という条件で、回数だけを見ていると気づけない空転を拾える。noteの3重構成と合わせると、実務で置くべき条件は次の4種類に整理できる。

| 種類 | 例 | 何を防ぐか |
|---|---|---|
| 達成条件 | 品質スコアが閾値以上／全チェック通過 | 未完成のまま終わること |
| 回数上限 | 最大12イテレーション／最大5回 | 無限ループ |
| 時間・コスト上限 | 最大360分 | 費用の暴走 |
| 停滞検知 | 同じエラー2回連続 | 上限まで空転し続けること |

noteの記事は公式例として、Lighthouse スコアを「90以上にするという検証可能なゴール」に設定する例も紹介している。**達成条件は、人間が読んで判断する言葉ではなく、機械が判定できる数値や合否である**必要がある——これが「計測できる形で」の実際の意味になる。

## ハードストップと、詰まったときの出口

RUNTEQの動画は、ルール定義で重要な4要素の1つとして**ハードストップ**を挙げている（[動画: RUNTEQ](../sources/video-pe-loop-engineering-5plus1-parts.md)、聞き取り）。無限ループや暴走を防ぐため、リトライ回数や時間・コストの上限を設け、**詰まったら人間に確認する仕組みを入れる**ことだとしている。同動画は、ルール定義の1番目に「明確なタスク定義——完了条件が一言で言えるかどうか」も置いている（聞き取り）。

残る2要素のうち**安全な作業環境**——ワークツリー等で失敗しても全体を壊さない設計になっているか——は[ループを支える部品](./loop-parts-and-harness.md)のワークツリーの節で扱う実装と対応し、**視覚的な成功判定**——テスト・リント・型チェックなどで合否を自動判定できるか——は[検証の設計](./verification-design.md)で扱う。

ここで見落とされやすいのが「詰まったら人間に確認する」という後半である。上限に達したときにループがただ黙って止まると、**止まったことに人間が気づかない**。上限は、打ち切りの条件であると同時に人間を呼び出すトリガーとして設計するのが望ましい。

止め方を設計することの効用を、noteの記事は次のようにまとめている。

> プロンプトの美文調整ではなく。品質スコア、最大回数、最大時間を別々に置いたこと。止め方を設計すると、エージェントの賢さを過信しなくて済みます

**モデルが賢くなれば停止条件は要らなくなる、という話ではない**。むしろ逆で、賢さを前提にしないための装置が停止条件だ、という位置づけである。

## 小さく始める

最後に、始め方について。noteの記事は対象を絞り込んでから始めることを勧めており、その具体的な基準と段階的な導入手順は[いつループを使うか](./when-to-use-loops.md)の「小さく始める」で扱う。運用中の確認方法として、同記事は `/usage` で skill・subagent・MCP 別の内訳を見て収束しているかを確認する、という手順も挙げている。

## まとめ

- ループ設計の中心は「回し方」ではなく「止め方」であり、複数資料がこの点で一致している
- ゴールを先に定義し、ループは後から組む。順序を逆にすることが最もよくある失敗とされる
- `/goal`（成功条件で止まるゴール駆動）と `/loop`（時間駆動の繰り返し）は別物であり、混同されやすい
- 停止条件は達成条件・回数上限・時間コスト上限・停滞検知の4種類を多重化して置く。1つだけだと空転する
- ハードストップは打ち切りの条件であると同時に、詰まったときに人間を呼び出すトリガーとして設計する
- 始めるときは対象を絞り込み、小さく回してから範囲を広げる
