# いつループを使うか——適用条件と、小さく始める手順

ここまでの記事は「ループをどう作るか」を扱ってきた。本記事が扱うのは、その手前の問いである。**そもそも、そのタスクはループにすべきなのか。**

これは些細な問いではない。ループは1回で終わる作業を何周も回す仕組みなので、向いていないタスクに適用すると、**得られるものが増えないまま、コストと時間だけが増える**。keitoaiweb の動画も、ループの注意点としてまさにこの点を挙げている（[動画: keitoaiweb](../sources/video-pe-five-engineering-stages.md)、聞き取り）。

## 有効に働く3つの条件

MindStudio の記事は、loop engineering が有効に機能する条件として次の3つを挙げている（[記事: MindStudio](../sources/article-le-loop-engineering-mindstudio.md)）。

1. **タスクが多段階で条件付きである**（次のステップが前のステップの結果に依存する）
2. **完了までの時間が予測不可能である**
3. **人間のレビューがボトルネックになっている**

逆に不向きなのは、**単一の明確なステップで完結するタスク**と、**各ステップで人間の判断が必須となるタスク**だとしている。

この3条件は、並べてみると1本の筋が通っている。いずれも「**手順を事前に書き下せない**」という性質の言い換えである。同記事は loop engineering の本質について、事前に正しい手順が分かっているタスクを機械的に繰り返すことではなく、事前に手順が確定できないタスクに対してエージェント自身が観察と評価を通じて適切な手順を見出していくことにある、と位置づけている。手順が確定しているなら、それはループではなく普通のスクリプトで足りる。

Kilo の記事が別の角度から同じことを言っている。loop engineering は「**最初の回答が不完全でありうる前提**でワークフローを設計する」ものだという整理である（[記事: Kilo](../sources/article-le-kilo-loop-engineering-definition.md)）。裏返せば、最初の回答でだいたい合っているタスクにループを被せても、2周目以降は空回りになる。

## 症状から入る

適用条件を上から当てはめるより、実際には「困っている症状」から入るほうが早い。keitoaiweb の動画は、5つのエンジニアリングを症状別に振り分ける目安を示している（[動画: keitoaiweb](../sources/video-pe-five-engineering-stages.md)、聞き取り）。

| 症状 | 見直す層 |
|---|---|
| 意図と違う結果が返る | プロンプト |
| 前提を忘れる | コンテキスト |
| 手作業の事故が怖い | ハーネス |
| **品質が安定しない** | **ループ** |
| タスクが大きすぎて崩れる | グラフ |

同動画は、最初からすべてを意識するのはやりすぎだとし、**まずは通常のプロンプト・コンテキストの範囲で試し、精度が不十分だと感じた症状に応じて追加の考え方を導入すべき**だと助言している（聞き取り）。

note の記事も独立に同じ立場を取っている。

> すべてのタスクが複雑なループを必要とするわけではない

（[記事: note](../sources/article-le-note-masawunder-goal-loop-design.md)）

出所の異なる2本が「全部をループにするな」と明言していることは、それなりに重い。**ループは上位互換ではなく、特定の症状に効く道具である。** 層の関係そのものは[プロンプトからループまで](./from-prompt-to-loop.md)で扱った。

## 向いているタスクの見分け方——観察源があるか

Kilo は具体的な適用例として5つの実践パターンを挙げている（[記事: Kilo](../sources/article-le-kilo-loop-engineering-definition.md)）。

| パターン | 何を観察するか |
|---|---|
| Test-Driven Agent Loop | テストの失敗から実装修正へ |
| Compiler-Driven Loop | 型チェッカーのエラーを修復リストとして使う（主にマイグレーション） |
| Review-Driven Loop | 人間のレビューコメントを観察源にする |
| Runtime Debugging Loop | ログ・スタックトレース・ブラウザ出力から原因を特定する |
| Product Iteration Loop | UIコピー・状態・レスポンシブ性を反復検証する |

この5つには**共通点がある**。どれも、観察の材料が**すでにその現場に存在している**。テスト結果、コンパイラのエラー、レビューコメント、ログ、画面。ループのために新しく作ったものは1つもない。

ここから、実務的な見分け方が1つ導ける。**手元のタスクに、すでに合否や良し悪しを返してくれるものがあるか。** あるならループにしやすく、ないなら、まずそれを用意するところが仕事になる（[検証の設計](./verification-design.md)）。Kilo が「テストの失敗は単なるエラーメッセージではなく、新しい文脈情報である」と書いているのは、この観察源を軽く見るなという趣旨だと読める。

3つ目の Review-Driven Loop は補足がいる。ここでは人間がレビューコメントを書くので、人間は完全には抜けていない。MindStudio が挙げた「各ステップで人間の判断が必須なタスクは不向き」という条件と矛盾するように見えるが、そうではない。**判断そのものを人間が担い続けたうえで、判断と判断のあいだの往復をループに任せる**という形はありうる。全部を手放すか全部を握るかの二択ではない。

## 小さく始める

適用できると判断しても、いきなり自律運用から始めるべきではない。note の記事は、開始時の基準として対象を絞り込むことを繰り返し推奨している（[記事: note](../sources/article-le-note-masawunder-goal-loop-design.md)）。

> 対象は広げず、1ページ、1テスト、1つの警告まで狭く切る

そして、人がどれだけ関与するかの度合いを、ターン駆動・ゴール駆動・時間駆動・自律駆動という4段階の階段として整理したうえで、次のように勧めている。

> 小さく始めて、完了条件が見えたら/goalに上げる

**完了条件が見えてから自動化を上げる**という順序が肝である。逆順——先に自律で回し始めて、止め方を後から考える——は、MindStudio が「最も一般的な失敗」と呼んだものそのものである（[ゴールと停止条件の設計](./goal-and-stop-conditions.md)）。

最初の1周に何を期待すべきかについても、同記事は現実的な水準を示している。

> 最初の1回は、作業、確認、停止の3点を小さなタスクで見届けられれば上出来です。自律運用はその先の話です

作業・確認・停止の3点。品質が上がったかどうかですらなく、**ループが意図どおり止まったかを見る**のが最初の目標だという水準感である。

## 判断の順序

ここまでを、手元のタスクに当てはめる順序としてまとめる。

1. **症状は「品質が安定しない」か** — 違うなら別の層を見る
2. **手順を事前に書き下せるか** — 書き下せるならスクリプトで足りる
3. **合否や良し悪しを返す観察源があるか** — ないなら、まずそれを作る
4. **人間の判断を各ステップで挟む必要があるか** — 必須なら不向き、往復だけなら候補
5. **対象を1ページ・1テスト・1つの警告まで狭く切れるか** — 切れないなら、まだ切る

4番目までが適用可否、5番目が始め方である。なお、判断材料としての観察源の有無は[Self-Refine と evaluator-optimizer](./self-refine-and-evaluator-optimizer.md)の4条件とも重なるので、そちらのチェックリストも合わせて使うとよい。

## まとめ

- ループが効くのは、多段階・条件付きで、完了時間が読めず、人間のレビューが詰まっているタスク
- 単一ステップで終わるタスクと、各ステップで人間の判断が要るタスクには不向き
- 出所の異なる2本の資料が「すべてのタスクにループが要るわけではない」と明言している。まずプロンプト・コンテキストで試し、品質が安定しないという症状が出てから導入する
- 実践パターン5種はいずれも、テスト・型チェッカー・レビュー・ログ・画面という**既存の観察源**を使っている。観察源があるかが実務的な見分け方になる
- 始めるときは対象を1ページ・1テスト・1つの警告まで狭く切り、完了条件が見えてから自動化の度合いを上げる
- 最初の1周の目標は品質向上ではなく、作業・確認・停止の3点が意図どおり動くのを見届けること
