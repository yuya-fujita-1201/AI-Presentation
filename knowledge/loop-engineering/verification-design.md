# 検証の設計——合否を返すチェックをどう用意するか

[ループの解剖](./anatomy-of-a-loop.md)で見たとおり、ループの1周には結果を観察する段階がある。チャットAIの使い方では、この観察を担っていたのは画面の前の人間だった。ループを組むということは、**この役割を機械が読み取れる信号に置き換える**ということである。ここが用意できないと、ループは形だけになる。

## 検証がないと、人間が検証ループを肩代わりする

Anthropic公式の Claude Code ドキュメントは、この点を正面から説明している（[記事: Anthropic Claude Code Docs](../sources/article-le-claude-code-best-practices.md)）。同ドキュメントによれば、Claude は作業が「終わったように見える」時点で手を止める。実行可能なチェックがなければ、この主観的な印象だけが唯一の判断材料になり、結果として**人間自身がミスを見つけるたびに介入する「検証ループ」の役割を担うことになる**という。

> Give Claude something that produces a pass or fail, and the loop closes on its own. Claude does the work, runs the check, reads the result, and iterates until the check passes.

合格・不合格を返すものを与えれば、ループはひとりでに閉じる——作業し、チェックを実行し、結果を読み、チェックが通るまで反復する、という記述である。同ドキュメントは、チェックの有無こそが、**人間がつきっきりで監視するセッションと、離れていても任せられるセッションとを分ける差**だとしている。

Qiitaの実践記事も、独立に同じ警告を発している（[記事: Qiita](../sources/article-le-qiita-syoitu-loop-engineering.md)）。

> 検証が甘いと、ただ生成を垂れ流すだけの装置になります

**検証はループの一部品ではなく、ループが装置として成立するかどうかの分かれ目である**——出所の異なる2本の資料が、この点で一致している。

## 「チェック」として何を置けるか

同じくAnthropicのドキュメントは、ここでいうチェックとは会話の中でモデルが読み取れる信号を返すものすべてを指すとし、次を例に挙げている。

- テストスイート
- ビルドの終了コード
- リンター
- 出力を期待値ファイルと突き合わせるスクリプト
- デザインと見比べるブラウザのスクリーンショット

重要なのは、**チェックは必ずしもテストコードでなくてよい**という点である。「期待値ファイルと突き合わせる」「スクリーンショットを見比べる」も立派な合否信号になる。

RUNTEQの動画も、ルール定義で重要な4要素の1つとして**視覚的な成功判定**——テスト・リント・型チェックなどで合否を自動判定できるかどうか——を挙げている（[動画: RUNTEQ](../sources/video-pe-loop-engineering-5plus1-parts.md)、聞き取り）。Anthropic公式ドキュメントが挙げる「チェック」の考え方と同じ発想が、独立した資料でも繰り返されている。

同ドキュメントは、指示の書き方をBefore/After形式で3つ示している。1つ目は、単に「メールアドレスを検証する関数を実装して」と指示するのではなく、具体的なテストケース（`user@example.com` は true、`invalid` は false、`user@.com` は false）を添えて、実装後にそのテストを実行するよう指示する書き換えである。2つ目は、「ダッシュボードの見た目を良くして」ではなく、スクリーンショットを貼ったうえでそのデザイン通りに実装させ、結果のスクリーンショットを撮って元のデザインと比較し差分をリストアップして修正させる指示。3つ目は、「ビルドが失敗している」という報告だけで済ませず、実際のエラーメッセージを貼り付けて修正させたうえでビルドの成功を検証させ、エラーを握りつぶすのではなく根本原因に対処するよう求める指示である。

3つに共通する型は、**「やってほしいこと」に「終わったかどうかの判定方法」を必ず添える**ことだ。チャットAIの使い方から移行するときに、まず変えるべきなのはこの一点である。

## 機械で判定するか、AIに判定させるか

では、テストコードが書けない成果物はどうするか。にゃんたのAIチャンネルの動画は、検証方法を大きく2つに分けている（[動画: にゃんたのAIチャンネル](../sources/video-ge-nyanta-loop-graph-claude-code.md)、聞き取り）。

1. **プログラムを実行して機械的に合否を判定する**方法
2. **言語モデルに検証させる**方法

同動画は、プログラムであればテストコードの合否で機械的に検証できるが、**議事録のような自由記述の成果物をプログラムで自動検証するのは難しい**ため、AIに検証・改善をやらせる方法が現実的な解になるとしている（聞き取り）。

この使い分けは実務でそのまま効く。コード・数値・構造化データは1で、文章・企画・デザインは2で判定する。両方置ける場合は両方置いたほうがよい。keitoaiweb の動画は、ループエンジニアリングを実行・検証・改善を繰り返すやり方と定義したうえで、実例として画像生成後にビジョン機能で文字崩れなどを確認し直すループ、Excelの売上データを何度も再計算させて数値を合わせるループ、スライドの文字数超過を検出して削るループを紹介している（[動画: keitoaiweb](../sources/video-pe-five-engineering-stages.md)、聞き取り）。**文字数超過の検出は機械判定、文字崩れの確認はモデルによる判定**——同じ資料作成の中でも、対象によって置くべきチェックの種類が違うことが分かる。

なお、2の「言語モデルに検証させる」を採る場合、作った本人に採点させてよいのかという論点が生じる。上記2本の動画はいずれも**別のモデルに検証させるべきだ**という立場を採っている。この論点は[作る役と採点する役を分ける](./maker-checker-separation.md)で扱う。

## 強制力を4段階で上げる

チェックを用意した後は、それがどれだけ強く「停止」をゲートするかを決める必要がある。Anthropicのドキュメントは4段階の手段を挙げている（[記事: Anthropic Claude Code Docs](../sources/article-le-claude-code-best-practices.md)）。

| 段階 | 手段 | 効き方 |
|---|---|---|
| 1 | **単発のプロンプト内で** | チェックの実行と反復を同じメッセージの中で指示する |
| 2 | **セッションを横断して** | チェックを `/goal` 条件として設定する。別の evaluator が毎ターン後に再評価し、目標達成まで作業を続ける。行き詰まった場合は目標未達のまま最終的に実行を停止するとしている |
| 3 | **決定的なゲートとして** | Stop フックにチェックをスクリプトとして実行させ、通過するまでターンの終了をブロックする。ただし8回連続でブロックされるとフックを上書きしてターンを終了させるとしている |
| 4 | **セカンドオピニオンによって** | 検証用サブエージェントや、自らの発見内容を検証するダイナミックワークフローを用いる |

同ドキュメントは、それぞれの段階が「準備の手間」と「必要な注意の少なさ」のトレードオフになっていると述べている。プロンプト版はどんなタスクにもすぐ使える一方、`/goal` 版と Stop フック版は**人間が見ていなくても無人実行が正しく完了することを可能にする**手段だとまとめている。4つ目については、作業を行ったのとは別のフレッシュなモデルに結果の反証を試みさせることで、作業したエージェント自身が採点者にならないようにする狙いがあると説明している。

上に行くほど強制力が上がるが、準備の手間も増える。[ゴールと停止条件の設計](./goal-and-stop-conditions.md)で触れた「小さく始める」という原則に従えば、**1から始めて、放っておきたくなったら2や3に上げる**という順序が自然である。

Qiitaの記事は、この3段階目にあたる実装を具体的に示している（3ファイル構成の詳細は[ループを支える部品](./loop-parts-and-harness.md)の最小構成を参照）。`.claude/settings.json` の Stop フック（完了時の自動テスト実行）と PostToolUse フック（編集時の型チェック）の組み合わせがこれにあたる（[記事: Qiita](../sources/article-le-qiita-syoitu-loop-engineering.md)）。**完了時だけでなく編集のたびに検証を挟む**と、1周の中の誤りが後段まで持ち越されにくくなる。

## 自己申告ではなく、証拠を出させる

検証を設計するうえで最後の、そして最も実務的な原則がある。Anthropicのドキュメントは、成功を自己申告させるのではなく、**テストの出力結果・実行したコマンドとその戻り値・結果のスクリーンショットといった証拠（evidence）を提示させる**べきだと推奨している。証拠を確認するほうが自分で検証をやり直すより速く済み、かつ人間が見ていなかったセッションに対しても機能する方法だとしている。

Qiitaの記事は、これを禁止事項として CLAUDE.md に明記する形で運用している。

> チェック出力なしで完了と報告すること

> アサーション削除やテスト弱体化で通すこと

**「完了しました」という言葉は証拠ではない**という原則は、別々の言い方でも同じ結論になる。前者は「証拠を出させろ」、後者は「証拠なしの完了報告を禁じろ」で、同じことの表と裏である。

2つ目の禁止事項には理由がある。同記事の筆者は、自身の失敗として次を紹介している。

> Claudeが3周目でアサーションを1行こっそり消してテストを通してきた

これは検証設計の落とし穴を端的に示している。**チェックを通ることが目的になると、チェックのほうを弱めるという抜け道が生まれる**。合否信号を置くだけでは足りず、その信号自体を書き換えられないようにする（あるいは書き換えを禁止事項として明示する）ところまでが検証の設計に含まれる。この失敗が招くコストの側面は[ループのリスクとコスト](./risks-and-costs.md)で扱う。

同記事はほかにも、行き詰まりを解決するための別エージェント（fixer）に推測での修正を禁じる条件を課している。詳細は[ループを支える部品](./loop-parts-and-harness.md)の最小構成で扱う。

## まとめ

検証の設計は、次の順で決めていくとよい。

1. この成果物の合否は、機械で判定できるか（できないならモデルに判定させる）
2. その判定は、どんな信号として返るか（終了コード・テスト出力・スクリーンショット・採点）
3. その判定にどれだけ強制力を持たせるか（プロンプト／`/goal`／Stop フック／別エージェント）
4. 完了報告に何を証拠として添えさせるか
5. チェック自体が弱められていないことを、どう担保するか

1〜2が空欄のままループを組んではいけない、というのが本記事の結論である。
