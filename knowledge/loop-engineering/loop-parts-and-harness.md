# ループを支える部品——5+1のパーツとハーネス

[ループの解剖](./anatomy-of-a-loop.md)で構造を、[検証の設計](./verification-design.md)で合否信号を見た。だが構造と信号が分かっても、それだけではループは回らない。**誰がエージェントを起動するのか。作業が衝突しないのか。前回学んだことはどこに残るのか。** ここを埋めるのが本記事の部品リストである。

## 2本の資料が、ほぼ同じリストを挙げている

面白いことに、出所のまったく異なる2本の資料が、ループを構成する部品としてほぼ同一のリストを提示している。

RUNTEQ の動画は、ボリス・カーニー氏（Anthropic の Claude Code 責任者としている。人物名の表記は資料間で揺れており断定できない）が整理したという「**機能するループは5つの部品とプラス1のメモリーでできている**」という枠組みを紹介している（[動画: RUNTEQ](../sources/video-pe-loop-engineering-5plus1-parts.md)、聞き取り）。

Qiita の入門記事は、Addy Osmani の定義を軸にしながら、ループを支える**6つのパーツ**として Automations・Worktrees・Skills・Connectors/MCP・Sub-agents・Memory を挙げている（[記事: Qiita](../sources/article-le-qiita-syoitu-loop-engineering.md)）。

並べるとこうなる。

| # | RUNTEQ（5+1の部品） | Qiita（6つのパーツ） | 何を解決するか |
|---|---|---|---|
| 1 | 自動化（オートメーション） | Automations | 誰がループを起動するのか |
| 2 | ワークツリー | Worktrees | 複数の作業が衝突しないか |
| 3 | スキル | Skills | 毎回同じ規約を守らせられるか |
| 4 | プラグイン／コネクター | Connectors / MCP | 外の世界に触れられるか |
| 5 | サブエージェント | Sub-agents | 作る役と見る役を分けられるか |
| +1 | メモリー | Memory | 前回の学びが次に残るか |

**中身は一致している。** 違いはメモリーを6つ目に数えるか「＋1」として別格に置くかだけである。日本語の技術記事と英語圏の発信という異なる経路から同じ6項目が出てきているという事実は、このリストが特定の人の思いつきではなく、実際に回している人たちが共通してぶつかる要件だということを示している。

## それぞれが何を解決するのか

### 1. 自動化——ループのコア

RUNTEQ の動画は、自動化を「定期的にタスクを発見しエージェントを起動する、**ループのコア部分**」だとしている（聞き取り）。ここが人間なら、それは[ループエンジニアリングとは何か](./what-is-loop-engineering.md)で見た「プロンプトを打つ人」がまだ残っているということになる。ループの入口を人間が押している限り、ループは半分しか自動化されていない。

### 2. ワークツリー——衝突しない作業領域

複数エージェントが衝突しないよう作業領域を分離する考え方だとしている（聞き取り）。同じファイルを2体が同時に触れば壊れる。地味だが、**並列にした瞬間に必ず必要になる**部品である。これは同時に安全装置でもある——失敗しても全体を壊さない場所で走らせる、という[ゴールと停止条件の設計](./goal-and-stop-conditions.md)で触れた「安全な作業環境」の実装がこれにあたる。

### 3. スキル——規約の永続化

プロジェクトの規約を永続化する仕組みだとしている（聞き取り）。毎回のプロンプトに「命名規則はこう」「この書き方は禁止」と書き足すのをやめ、環境の側に置く。ループは何十周も回るので、**1周あたり数百字の指示の重複が、そのまま何十倍のコストと揺らぎになる**。

### 4. 接続（コネクター／MCP）——外の世界

Slack など依存ツールと接続し外部世界とつなぐ仕組みだとしている（聞き取り）。Qiita の記事は、この部品が欠けた場合の限界を端的に書いている。

> ファイルしか見えないループは、できることが少ない小さなループ

**ループの射程は、接続されている道具の範囲でしか広がらない。** 「エラーを検知して直して push する」という実務的なループを組もうとした途端、ログ基盤・リポジトリ・通知先への接続が要るようになる。

### 5. サブエージェント——分業

作る役と検証する役を分離して分業するための仕組みだとしている（聞き取り）。なぜ分けるのかは[作る役と採点する役を分ける](./maker-checker-separation.md)で扱った。

### +1. メモリー——会話の外に状態を置く

RUNTEQ の動画は、メモリーを**セッションの中ではなく会話の外に状態を永続化する仕組み**だとしている（聞き取り）。完了したタスク・進行中のタスク・学んだことを書き出すことで、次のループの質が上がっていくという説明である。

これが「＋1」として別格に置かれている理由は考えるに値する。1〜5がなくてもループは（貧弱ながら）回るが、メモリーがないループは**毎周ふりだしに戻る**。前述の Reflection——失敗を言葉にして次に生かす——を成立させる物理的な置き場がメモリーである。[ループの解剖](./anatomy-of-a-loop.md)で見たアウターループが機能するかどうかは、ほぼここで決まる。

## 部品を「動き」の側から見る——5つのアクション

Qiita の記事は、部品とは別に、ループを構成する**5つのアクション**として発見・受け渡し・検証・記憶・スケジューリングを挙げている。部品が名詞のリストなら、こちらは動詞のリストである。対応させるとこうなる。

| アクション | 主に担う部品 |
|---|---|
| 発見（タスクを見つける） | 自動化・接続 |
| 受け渡し（エージェントに渡す） | 自動化・スキル |
| 検証（合否を判定する） | サブエージェント・接続 |
| 記憶（学びを残す） | メモリー |
| スケジューリング（いつ回すか） | 自動化 |

同記事は、この中でも検証について特に強く警告している。

> 検証が甘いと、ただ生成を垂れ流すだけの装置になります

部品を揃えることが目的化すると、この一点を見落とす。**道具立てを増やす前に、合否信号があるかを先に確かめる**（[検証の設計](./verification-design.md)）。

## ロングランで走らせるための技術

部品が揃うと、次は「どこまで人間が離れられるか」という話になる。まさおAIじっくり解説ch の動画は、より自律的にエージェントを動かすための技術として次の5つを紹介している（[動画: まさおAIじっくり解説ch](../sources/video-le-loop-design-four-points.md)、聞き取り。同動画はこれをボリス氏の言及として紹介している）。

1. **オートパーミッション（自動承認）** — 権限確認を自動化する仕組み
2. **動的ワークフロー（dynamic workflow）** — Claude Code で effort 設定を入れると呼び出せる仕組みのような、大量のサブエージェントを動かしながらロングランのタスクを高品質にこなすパターンだとしている
3. **ループコマンド** — クラウド版の Claude Code や、ローカルで Amphetamine という Mac 用アプリを併用し、MacBook を閉じても稼働を続ける設定を使う運用を紹介している
4. **自己検証ツール** — エージェント自身が「正しい仕事をしている」という思い込みを裏づけるための検証手段を持たせること。例としてスクリーンショットを撮らせることで、レイアウト崩れなど自分のミスに気づけるようになるとしている
5. **Ralph Loop** — 以前から話題になっている手法で、Claude の公式プラグインにも組み込まれているとしている

このリストは、先の6部品と重なりながら**方向が違う**。6部品が「ループが成立するための要件」であるのに対し、こちらは「**人間が席を離れている時間を伸ばすための要件**」である。1のオートパーミッションが筆頭に来ているのが象徴的で、承認ダイアログが1つでも残っていればロングランは止まる。

同時にここは危うい領域でもある。承認をすべて自動化するということは、[検証の設計](./verification-design.md)で置いた歯止めを外すということでもある。同動画の配信者自身も、モデルが賢くなったから縛らなくていいという意見がある一方で、**少しずつ制約をつけていくことでかえって自律的に動くようになる**と述べている（聞き取り）。自由にするために制約を足す、という順序である。

## これはハーネスエンジニアリングの話でもある

ここまで並べた部品を眺めると、あることに気づく。**そのほとんどが、指示文の話ではなく環境の話である。** 作業領域、規約の置き場、外部接続、権限、状態の保存先——[プロンプトからループまで](./from-prompt-to-loop.md)で見た段階でいえば、これらはハーネスエンジニアリングの領域に属する。

だから、ループを設計するという仕事の実体は、かなりの部分が**環境整備**になる。ループのアルゴリズム（何周回すか、どう評価するか）を考えている時間より、ワークツリーを切り、スキルファイルを書き、MCP を繋ぎ、メモリーの置き場を決めている時間のほうが長い。これは失望ではなく、むしろ朗報である。**どれも一度作れば残る資産**だからである。

## 最小構成から始める

とはいえ6部品を一度に揃えるのは重い。Qiita の記事が示す Claude Code での入門実装は、**3ファイル**で構成されている。

| ファイル | 役割 | 対応する部品 |
|---|---|---|
| `CLAUDE.md` | 停止条件と禁止事項の明文化 | スキル（規約の永続化） |
| `.claude/settings.json` | Stop フックで完了時にテスト、PostToolUse フックで編集時に型チェック | 自動化・検証 |
| `.claude/agents/fixer.md` | 行き詰まりを解決する別エージェント | サブエージェント |

同記事は、`CLAUDE.md` に完了報告の基準として「全チェック通過」、ループ上限として「最大5回」、失敗時の停止基準として「同じエラー2回連続」を書き、禁止事項として「チェック出力なしで完了と報告すること」「アサーション削除やテスト弱体化で通すこと」を明記しているとしている。`.claude/settings.json` の2つのフックは「書きながら即座に直させる」戦略の実装だと説明されている。`fixer.md` には「推測は禁止。失敗パス上のファイルを頭から終わりまで全部読む」という条件を課しているという。

**この3ファイルには、ワークツリーもコネクターもメモリーも出てこない。** それでもループは成立する。部品リストは「全部揃えないと始められないチェックリスト」ではなく、**詰まったときにどこを足せばいいかの索引**として使うのが正しい。ファイルしか見えないループでは足りないと感じた時に接続を足し、毎回ふりだしに戻ると感じた時にメモリーを足せばよい。

## まとめ

- ループの部品リストは、出所の異なる2本の資料がほぼ同一の6項目（自動化・ワークツリー・スキル・接続・サブエージェント・メモリー）を挙げている
- メモリーが「＋1」と別格に置かれるのは、これがないとアウターループが成立しないため
- 動きの側から見ると、発見・受け渡し・検証・記憶・スケジューリングの5アクションに対応する
- ロングラン化にはオートパーミッション等の別系統の技術が要るが、歯止めとのトレードオフになる
- 部品の大半は環境整備＝ハーネスの領域であり、一度作れば資産として残る
- 最初は3ファイル程度の最小構成でよく、リストは「詰まったときの索引」として使う
