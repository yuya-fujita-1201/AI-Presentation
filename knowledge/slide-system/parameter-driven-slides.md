# パラメーター駆動スライドの考え方

## 解決したい課題

AI にスライドを作らせると初稿は速いが、その後の修正で問題が起きる。

- 「5枚目のフォントを少し小さく」のような微修正のたびに AI に再生成させると、トークンと時間を浪費する
- 再生成のたびに他の場所まで変わってしまい、**元のデザインが維持されない**
- 人手で PPTX を直接編集すると、以後 AI との共同編集ができなくなる（ソースが二重化する）

## 設計原則

1. **ソース・オブ・トゥルースは JSON**（`deck.json`）。HTML / PPTX は常に生成物であり、直接編集しない
2. **内容とデザインを分離する**。内容はスライド配列に、デザインは「テーマ（色・フォント）/ レイアウト既定値（配置）/ 個別スタイル（差分）」の3層に持つ
3. **微修正は差分で書く**。既定値を変えずに、該当スライドの `style` にオーバーライドだけを書く。1行の変更が1箇所の変更に対応する
4. **決定論的ビルド**。同じ JSON からは常に同じ HTML / PPTX が生成される。ビルドは1秒未満なので再生成コストはゼロに近い
5. **初稿は AI、微修正はパラメーター**。ベースのドラフト作成（構成・文言・スタイル設計）は AI に任せ、その後の調整は人間か AI が JSON の数値を触るだけにする

## 動画制作の JSON 管理からの応用

参考にした解説動画（クロノITチャンネル）では、台本・話者・ビジュアル・BGM など動画の全要素を1枚の JSON に集約し、編集ソフトを使わず Remotion でレンダリングする制作パイプラインが紹介されている。スライドに転用した原則:

- **全要素を1つの構造化データに集約し、レンダラーはそれを読むだけにする** → deck.json + build_deck.py がこれに相当
- **修正は JSON の該当フィールドを直して再出力するだけ**（AI 再生成なしの微修正のモデルケース）→ `style` オーバーライドとして実装
- **AI にゼロから自由に作らせず、整備済みの「型」から選ばせる**。雛形に最小限の差分を当てはめる方式が品質の安定につながる → 9種のスライドタイプ + レイアウト既定値として実装
- **一発生成型の画像生成 AI をあえて避ける**。情報過多で崩れたデザインになりがちなため、構造化データ + テンプレートレンダリングを選ぶ

### 今後取り入れられる原則（拡張候補）

- スキーマ検証（動画では zod）: deck.json の必須パラメータ欠落・型ミスをビルド前に機械検知する
- 崩れ検出の二段構え: 「テキストがボックスからはみ出していないか」の自動検証スクリプト + スクリーンショットの AI レビュー
- 修正ログのフィードバックループ: 人間の修正パターンを記録し、生成プロンプトやレビュー観点に反映して同じ直しを繰り返さない
- 部分抽出でトークン節約: 修正時に JSON 全体ではなく変更箇所の差分だけを AI に渡す
- 構造とテキストの分離を活かした多言語・多テーマ展開（同じ構成の英語版資料などを機械的に生成）

詳細は [動画ソースの要点](../sources/video-json-driven-video-production.md) を参照。

## この方式の副次効果

- deck.json はテキストなので **Git で差分レビューできる**（OKF と同じ思想）
- テーマ切替が1行（`meta.theme`）。同じ内容を別ブランドの見た目で即座に出せる
- スライド構成データ自体が「発表内容の構造化された記録」としてナレッジになる
