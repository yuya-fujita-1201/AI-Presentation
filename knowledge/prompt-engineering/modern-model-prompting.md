# 最新モデル時代のプロンプト

ここまで、指示を具体的に書く・役割を与える・例を示す・背景を渡す、という積み上げ型の作法を見てきた。ところが最近のモデルをめぐる実践知では、**逆方向の助言**が目立つようになっている。曰く、細かいルールを書きすぎるな。制約を減らせ。検証させようとするな。

一見すると、これまでの内容の否定に見える。だが実際には、何を削り、何は削らないのかという線引きの話である。ここを取り違えると「雑に書いてよい」という誤読になるので、順を追って整理する。

## 積み上げてきた制約は何だったのか

前提として押さえておきたいのは、細かい制約の多くがモデルの弱点を補うための回避策として書かれてきたという点である。

にゃんたのAIチャンネルの動画は、この経緯をはっきり説明している。従来はモデルの精度が低かったため「コメントを書かない」といった強い制約をプロンプトで細かく指示していたが、Claude 5系のモデルでは状況に応じてモデル自身に判断させる設計——たとえば「周囲のコードと同じように読めるコードを書くこと」といった記述——に切り替えることが推奨されていると紹介している（[Opus 5プロンプトのコツ解説動画](../sources/video-pe-opus-5-prompt-tips.md)、auto字幕からの聞き取り）。

この対比は重要である。「コメントを書くな」は**症状への対処**であり、「周囲のコードと同じように読めるように」は**判断基準の付与**である。後者のほうが短いのに、想定外のケースに強い。[なぜ文脈が効くのか](./why-context-matters.md)で見た「理由まで書く」という話が、モデルの性能向上によってさらに効くようになった、と捉えるとつながりがよい。

## 「8割削っても落ちない」という主張

象徴的な数字として、複数の動画が同じ話を紹介している。Anthropic社内でOpus 5やFable 5を使う際の**システムプロンプトを80%除外しても精度への悪影響はほぼなかった**、という社内検証の結果である（[Opus 5プロンプトのコツ解説動画](../sources/video-pe-opus-5-prompt-tips.md)／[Opus 5ベンチマーク解説動画](../sources/video-pe-opus-5-benchmark-tips.md)、いずれもauto字幕からの聞き取り）。

独立した2つのチャンネルが同じ内容を紹介している点は傍証になるが、どちらも動画の自動生成字幕を出所とする紹介であり、削減率の数字を業務判断の根拠にするなら原典（Anthropicのコンテキストエンジニアリング記事）を当たるべきである。ここで受け取るべきは「80%」という数字そのものではなく、プロンプトを短くする方向の変更が精度低下を招かない場面があるという方向性のほうだ。

[Opus 5ベンチマーク解説動画](../sources/video-pe-opus-5-benchmark-tips.md)は関連する助言も紹介している。細かいルールや例文の羅列はむしろ逆効果になり得ること、必要な情報は先回りして教え込むのではなく「聞かれたら渡す」形でよいこと、`CLAUDE.md`のようなプロジェクトドキュメントは200行でも長くもっと短くてよいこと、分厚い説明書よりも視覚情報として解釈できる薄いHTMLのモックを渡すほうがよいという潮流があること、である。

「削る」を実行に移す具体的な手段として、同動画は先回りしてすべてを教え込むのではなく自動メモリに覚えさせる方針を紹介している。また[Opus 5プロンプトのコツ解説動画](../sources/video-pe-opus-5-prompt-tips.md)は、Claude Codeのdoctorコマンドを使うとCLAUDE.mdやスキルの記述から無駄なトークンを削減できる箇所を診断できると紹介しており、「どこを削るべきか」を勘に頼らず洗い出す手段になる。

## 過剰指示が実害になる例

「書きすぎても無駄なだけ」ならまだよい。問題は、書きすぎが害になるケースが具体的に報告されていることである。ここはAnthropicの公式ドキュメントが明快に述べている。

コードレビュー用のプロンプトに「重要度の高い問題だけを報告してほしい」「保守的に判断してほしい」といった指示を含めると、モデルがその指示を文字通り受け取り、報告件数が減ってしまう可能性があるという。同ドキュメントは、まずはすべての問題を報告させたうえで、フィルタリングは別のパスとして分離することを勧めている。運用面では、低いeffort設定でも精度が維持されることを踏まえ、高速な一次パスと、より時間をかけた二次パスという2段構えのレビューを後押ししている（[Prompting Claude Opus 5](../sources/article-pe-claude-opus-5-prompting.md)）。

これは示唆に富む。良かれと思って書いた「ノイズを減らすための指示」が、拾えたはずのバグを取りこぼす原因になる。**指示は効きすぎる**のである。

検証まわりも同様だ。2つの動画が揃って、Opus 5を使う際は検証ステップやサブエージェントによる検証をわざわざ指示に含める必要がなく、含めるとかえって過剰な検証を引き起こしてトークンを浪費すると紹介している（[Opus 5プロンプトのコツ解説動画](../sources/video-pe-opus-5-prompt-tips.md)／[Opus 5ベンチマーク解説動画](../sources/video-pe-opus-5-benchmark-tips.md)、auto字幕からの聞き取り）。[ループエンジニアリング](./loop-engineering.md)で見た「作る役と検証する役を分ける」という設計と一見矛盾するようだが、対象が違う。仕組みとして外側に検証を置くことと、プロンプト内で毎回検証を言い聞かせることは別物である。

同じ理由で、公式ドキュメントは古いモデル向けにプロンプト側で施していたvisionの回避策について、Opus 5ではもはや不要になっている可能性があるため再検証を勧めている。過去の回避策は、放っておくと負債として残り続ける。あわせて、vision性能はモデルが自身の作業を反復的に分析・クロップ・視覚的に検証できるツールを持つ場合にもっとも高く発揮されるとし、thinkingだけに頼るよりtool useの方が費用対効果の高い手段だとも述べている。

## effort——長さではなく思考量のダイヤル

積み上げ型の作法にはなかった、新しい調整軸が effort である。

2つの動画は揃って、effortパラメーターはモデルがどれだけ発言するかではなく、どれだけ思考するか（ファイルをどれだけ読み込むかなど）を制御するものだと整理している。ただし、そこから先の症状別の判断基準は動画によって対応関係が食い違う。[Opus 5ベンチマーク解説動画](../sources/video-pe-opus-5-benchmark-tips.md)は、ファイルを十分に読んでくれないときは effort を上げる、回答が浅いときは effort ではなくモデル自体を見直す、出力が長すぎるときは effort ではなくプロンプト側で簡潔さを指示する、と整理している。一方[Opus 5プロンプトのコツ解説動画](../sources/video-pe-opus-5-prompt-tips.md)は「回答内容が薄い場合はエフォートレベルを、精度そのものが低い場合はモデルのグレードを見直す」としており、「薄い／浅い」という近い表現に対して effort とモデルの対応が逆転している。いずれもauto字幕からの聞き取りであり、この食い違いが字幕の表現揺れによるものか実際の助言の違いかは原典で確認できていない。実務上は、**ファイルの読み込み不足のような明確な原因には effort**、**回答内容の質そのものが不満なときはモデルのグレード**という[Opus 5ベンチマーク解説動画](../sources/video-pe-opus-5-benchmark-tips.md)側の切り分けの方が線引きとして扱いやすい。

モデルのグレードを見直す際、どのモデルを選ぶかにも用途による指針がある。[Opus 5ベンチマーク解説動画](../sources/video-pe-opus-5-benchmark-tips.md)は、数学の論理問題や法律関連など専門性の高いタスクはFable 5、それ以外はOpus 5という使い分けを推奨しており、[Opus 5プロンプトのコツ解説動画](../sources/video-pe-opus-5-prompt-tips.md)も、低品質な案をあえて厳しく評価させたいような用途では引き続きFable 5を使いたいと述べている。

公式ドキュメントの記述も方向は一致している。`low`や`medium`のeffort設定は、より高い設定に比べてごくわずかなトークン数とレイテンシで高品質な出力を生むとし、運用としてはデフォルトの`high`から始めて自社のevalに基づいて調整すること、品質が保たれる範囲では`low`や`medium`をトークンコストと応答速度の主要な制御手段として使うこと、要求の厳しいコーディングやエージェントタスクでは`xhigh`まで引き上げることを挙げている（[Prompting Claude Opus 5](../sources/article-pe-claude-opus-5-prompting.md)）。旧モデルのeffort既定値を引き継いでいる場合は測り直すべきだ、とも述べている。あわせて公式ドキュメントは、Opus 4.8からの移行時にthinkingがデフォルトで有効になる点、thinkingを無効化した場合でもeffortの上限が`high`に制限される点というAPI仕様の変更を挙げている（[Prompting Claude Opus 5](../sources/article-pe-claude-opus-5-prompting.md)）。[Opus 5ベンチマーク解説動画](../sources/video-pe-opus-5-benchmark-tips.md)はeffortを5段階の思考量調整機能だと紹介しており、この段階数と公式ドキュメントの言う「既定は`high`」を重ねると、5段階のうち中間より上の値が既定になっている。

「思っている答えと違う」ときに何を回すべきかを切り分けられることが、ここでの実益である。プロンプト・effort・モデルという3つのつまみを、症状に応じて選ぶ。

## 数値は陳腐化する、構造は残る

これらの動画は性能比較の情報も多く含んでいる。ベンチマーク上の優劣、価格が従来の半額であること、コンテキストウィンドウが100万トークンであること、学習データの新しさ、などである（[Opus 5ベンチマーク解説動画](../sources/video-pe-opus-5-benchmark-tips.md)／[Opus 5プロンプトのコツ解説動画](../sources/video-pe-opus-5-prompt-tips.md)、auto字幕からの聞き取り）。100万トークンのコンテキストウィンドウについては公式ドキュメントも、それがデフォルトかつ最大値であり、そのウィンドウ全域にわたって指示追従・ツール呼び出し・推論の一貫性が保たれると述べている（[Prompting Claude Opus 5](../sources/article-pe-claude-opus-5-prompting.md)）。

ただし**この種の数値は最も速く陳腐化する**。半年後には別のモデルが別の価格で出ている。知識として蓄えるなら、個別の数値ではなく「モデル世代が変わると、価格・文脈長・得意分野・そして適切なプロンプトの書き方が同時に変わる」という構造のほうである。

[Opus 5ベンチマーク解説動画](../sources/video-pe-opus-5-benchmark-tips.md)が実施した、同一プロンプトを複数モデルへ横並びで投げて結果を比較するという検証の型も、数値そのものより長く使える。個々の勝敗は世代交代で入れ替わるが、新しいモデルが出るたびに同じ土俵で比較し直すという手順は再利用できる。

## 「削る」を新人はどう受け取るべきか

最後に、いちばん誤読しやすい点を整理しておく。**「削れ」は「雑に書け」ではない。**

公式ドキュメントは、Claude Opus 5がOpus 4.8向けに書かれた既存のプロンプトに対してもそのままの状態で良好に動作するとしたうえで、紹介するパターンは特にチューニングが必要になりやすい挙動を扱っていると位置づけている。Claude Opus 5は特に長時間にわたるエージェント的タスク（long-horizon agentic tasks）に強みを持ち、スタブや未完成のプレースホルダーを残すことなくタスクを完了させる点が特徴だともしている（[Prompting Claude Opus 5](../sources/article-pe-claude-opus-5-prompting.md)）。さらに、agentic codingではタスクの完全な仕様を最初にまとめて与える形で最も高い性能を発揮するとし、特定のスタイルやテンプレートに従わせたい場合はプロンプト側でその情報を明示的に与えるべきだとも述べている。同ドキュメントはオフィス・文書業務についても触れており、複雑な複数シート構成で単純ではない数式を含むスプレッドシートの生成・操作や、構造がよく整理されたスライドデックの生成に対応できるとしている（[Prompting Claude Opus 5](../sources/article-pe-claude-opus-5-prompting.md)）。

つまり、削る対象はモデルの弱点を補うために積み上げた回避策であって、目的・制約・前提そのものではない。「何をしてほしいか」「なぜそうしてほしいか」「どんな条件下か」は依然として渡す必要がある。むしろ完全な仕様を渡すことが推奨されている。

そして、これらの助言は特定モデルの現時点での特性に対するものである。読者が普段使うモデルが違えば当てはまらないこともある。ただし、この特定モデル依存という性質にも濃淡がある。[Anthropic公式ドキュメント](../sources/article-pe-claude-prompting-best-practices.md)自身は、そこでまとめる「明確で直接的な指示」などのベストプラクティスをFable 5を含む現行の全Claudeモデルに共通して適用できる手法だと位置づけており、モデル固有の調整が要る部分とモデルを問わず効く部分の両方が、同じ公式ドキュメント群の中に混在している。基礎——[明確で直接的な指示](./core-techniques.md)、[必要な前提の共有](./why-context-matters.md)——を身につけたうえで、使うモデルごとに「何が不要になったか」を確かめる。その順序を逆にしないことが、この転換期の実務での立ち回り方である。
