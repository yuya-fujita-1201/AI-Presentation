# プロンプトの構造

[プロンプトエンジニアリングとは何か](./what-is-prompt-engineering.md)で、曖昧な指示が曖昧な答えを生むこと、そして欠けがちなのは「評価基準・前提・出力の形」の3つだと確認した。ではそれをどう埋めるか。答えは単純で、**プロンプトを一文で書くのをやめ、役割の違う要素に分けて組み立てる**ことである。

このファイルでは、プロンプトの構成要素、その並べ方（記法）、そして書けたものをテンプレートとして再利用する方法までを扱う。ここが実務でもっとも費用対効果の高い部分になる。

## そもそもプロンプトとは何を指すか

構造の話に入る前に、用語の範囲を確認しておく。arXivのサーベイ「The Prompt Report」は、プロンプトとは生成AIモデルへの入力であり、その出力を導くために用いられるものだと定義している。プロンプトはテキスト・画像・音声・その他のメディアから構成されうるとし、具体例として「会計事務所向けのマーケティングキャンペーン用の3段落のメールを書いて」というテキスト、「10*179とは何か」と書かれた紙の写真、オンライン会議の録音に添えた「これを要約して」という指示を挙げている（[The Prompt Report](../sources/article-pe-prompt-report.md)）。

つまりプロンプトは「チャット欄に打ち込む文章」に限らない。添付した資料も、貼り付けたログも、すべてプロンプトの一部である。この認識は、後述する「入力データを指示から分離する」という発想の前提になる。

## 4要素——Instruction / Context / Input Data / Output Indicator

[Qiita記事](../sources/article-pe-qiita-kissy24-methods.md)は、NRIのプロンプトエンジニアリングの説明を参照しつつ、プロンプトの入力構造は大きく4要素で構成されると解説している。

| 要素 | 意味 | 具体例 |
|---|---|---|
| **Instruction（命令・指示）** | モデルが実行する指示やタスク。何をしてほしいのかを明確に伝える | 要約して、分類して、翻訳して |
| **Context（背景・文脈）** | 出力の質を高めるために考慮してほしい背景や外部情報。前提条件・目的・専門用語の定義など | 「社内向け資料である」「読者は非エンジニア」 |
| **Input Data（入力）** | 実際にAIに渡すデータやテキスト、質問内容そのもの | 要約対象の議事録本文 |
| **Output Indicator（出力形式）** | 出力してほしい形式・フォーマット | 箇条書き、JSON形式、Markdown |

同記事は、大きくはこの4要素で構成され、場合によっては役割・条件などをきちんと記載することで、精度の高い入力構造を作ることができると総括している。

この4分割の何がありがたいのか。実務的には、**チェックリストとして機能する**点である。出力が思い通りにならないとき、闇雲に文章を書き直すのではなく「4つのうちどれが欠けているか」を見に行けばよい。前提を外した答えが返るならContextが、形式がばらつくならOutput Indicatorが空欄になっているはずだ。なお、この4要素構成そのものを提示しているのは今回参照した資料の中では同記事のみであり、業界標準として統一された分類が存在するわけではない。

## 要素をどう区切るか——記法の3流派

要素に分けると決めたら、次は文章上でどう区切るかである。[Qiita記事](../sources/article-pe-qiita-kissy24-methods.md)は記載の仕方には複数の流派があるとしたうえで、3つのフォーマット例を紹介している。

1. **Gemini for Google Cloudが推奨しているフォーマット** — `[タスク]` `[背景・文脈]` `[入力]` `[出力形式]` のように角括弧の見出しで各要素を区切る
2. **Prompt Engineering Guideのフォーマット** — `### タスク ###` のようにシャープ記号で見出しを囲む
3. **Markdown形式のフォーマット** — `## タスク` のようにMarkdownの見出し記法で区切る

同記事の著者は3つ目のMarkdown形式を勧めている。その理由として、Markdownではなくヘッダを何かで囲うのはLLMがヘッダとコンテンツを認識しやすいからだと推察しつつも、Markdownでコンテキストの読み間違いをしたケースには遭遇したことがないため差は微々たるものだと考えており、プロンプトをmdファイルで書いたほうが管理しやすいためだと説明している。

エンジニア視点で補足すると、この「管理しやすい」は無視できない利点である。Markdownならリポジトリに置いてdiffが読め、レビューにかけられ、履歴が追える。プロンプトをコードと同じ扱いにできるかどうかは、チームで運用する段階で効いてくる。

## XMLタグによる構造化

もう一つ有力な記法が、XMLタグで囲む方式である。Anthropic公式のベストプラクティス集は、XMLタグは指示・文脈・例・変数入力が混在する複雑なプロンプトを曖昧さなく解析するのに役立つとし、コンテンツの種類ごとに `<instructions>`・`<context>`・`<input>` のような専用タグで囲むことで誤解釈を減らせると説明している（[Anthropicベストプラクティス](../sources/article-pe-claude-prompting-best-practices.md)）。

同ドキュメントはベストプラクティスとして、プロンプト全体を通して一貫性のある説明的なタグ名を使うこと、コンテンツに自然な階層構造がある場合はタグをネストすることを挙げている。具体例として、複数の文書を扱う場合は `<documents>` タグの中にそれぞれの文書を `<document index="n">` のようなインデックス付きタグで格納する構成を紹介している。

Markdown記法とXMLタグは対立するものではない。**構造が浅く人間も読む運用ならMarkdown、入力データが長大だったり階層があったりする場合はXMLタグ**、という使い分けが実務的な落としどころになる。とりわけ「指示」と「処理対象のデータ」が混ざると事故が起きやすい——議事録の中に「〜してください」という発言が含まれていれば、それを指示と読み違える余地が生まれる。タグで囲って境界を明示するのは、その種の取り違えを防ぐ手段でもある。

## 書き方のコツ

構造が決まっても、各要素の中身の書き方でさらに差が出る。ここで扱った4要素・記法・XMLタグはあくまで「箱」の設計であり、箱の中身をどう書くかは別の話になる。要点は3つある。

1. **命令・依頼調で、要点を先に書く** — 「〜してください」のような明確な依頼口調にし、強調したいことを文頭に置く
2. **背景を冗長にしない** — 要点→目的→制約の順で簡潔にまとめ、肥大化するなら要素を分けるかプロンプト自体を分割する
3. **AIを「前提知識のない優秀な新人」だと考えて検証する** — 最小限の文脈しか持たない同僚にプロンプトを見せて従ってもらい、その同僚が混乱するならAIも混乱するという「ゴールデンルール」で確かめる

これらQiita記事の5つのコツとAnthropicの「新しく入社した社員」「ゴールデンルール」については、[基本技法](./core-techniques.md)の「土台：明確で直接的に書く」でより詳しく扱っている。

## タスクの型によって構造は変わる

すべてのプロンプトが4要素をフルに使うわけではない。[KDDI記事](../sources/article-pe-kddi-prompt-basics.md)は、プロンプトには主に3つの種類があるとし、状況や目的に合わせて使い分けることでAIとのコミュニケーションがいっそう円滑になるとしている。

- **命令** — 具体的な作業指示。「この情報を教えてほしい」「この文章を翻訳してほしい」など。指示が明確であるほどイメージに近い出力が得られるとしている
- **補完** — 途中まで入力された文章やアイデアの続きを生み出す。「春の公園では桜が満開で、子どもたちは楽しそうに」と入力すると、AIが「遊具で遊んでいる」などと続ける
- **実演** — あらかじめ例を提示し、それをもとに判断や分類を行わせる。「映画Aは感動的」「映画Bはアクション」と例示したうえで映画Cを分類させる

補完型ではInstructionがほぼ存在せず、実演型ではInput Dataの前に例示という別ブロックが挟まる。4要素は固定のテンプレートではなく、タスクの型に応じて使う部品を選ぶための引き出しだと捉えるのが正確である。実演型の設計、すなわちfew-shotの詳細は[基本技法](./core-techniques.md)で扱う。

## テンプレート化して資産にする

最後に、書けたプロンプトを一度きりで捨てないための考え方に触れておく。[The Prompt Report](../sources/article-pe-prompt-report.md)は、プロンプトはしばしば「プロンプトテンプレート」を介して構築されると説明している。プロンプトテンプレートとは1つ以上の変数を含む関数であり、その変数がメディア（多くはテキスト）で置き換えられることでプロンプトが生成される。こうして生成されたプロンプトは、テンプレートの1つのインスタンスとみなせるとしている。

この定式化は、4要素の分解と綺麗に噛み合う。Instruction・Context・Output Indicatorは固定部分（テンプレート本体）、Input Dataは可変部分（引数）にあたるからだ。議事録要約のプロンプトを一度きちんと設計すれば、あとは議事録本文を差し替えるだけで毎回使える。**個人の勘をチームの部品に変える**のがテンプレート化であり、プロンプトエンジニアリングが「エンジニアリング」と呼ばれる所以もここにある。
