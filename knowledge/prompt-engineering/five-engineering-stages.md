# 5つのエンジニアリング

YouTubeチャンネル「keitoaiweb」の解説動画は、画像生成プロンプトに3色ルールのカラーコード指定や角丸禁止・グラデーション禁止といった細かい指示を書き込む例を挙げ、これを「プロンプトエンジニアリング」の実例だとしている。同動画はこの例を入り口に、コンテキストエンジニアリング、ハーネスエンジニアリング、ループエンジニアリング、グラフエンジニアリングという隣接領域を並べて見せる——半年ごとに新しい「〇〇エンジニアリング」が現れているように見える状況を、一枚の地図として整理する試みである。

このとき起きがちな誤解が2つある。ひとつは「プロンプトエンジニアリングはもう古い、次はループだ」と乗り換えようとすること。もうひとつは「用語が多すぎて追えない」と全部を諦めることである。どちらも、これらが**互いに置き換わる関係ではない**という点を見落としている。

## 違うのは目的ではなくスコープ

出発点として有効な整理がある。同動画は、5つの「〇〇エンジニアリング」の目的はすべて共通しており、AIの回答の質を上げることだとしている。違うのは目的ではなく**スコープ（範囲）**であり、次のように対応すると整理している（[5つのエンジニアリング解説動画](../sources/video-pe-five-engineering-stages.md)、auto字幕からの聞き取り）。

| 層 | 何を設計するか | 人間の仕事に例えると |
|---|---|---|
| プロンプト | 指示を磨く | 仕事の頼み方 |
| コンテキスト | 渡す情報を選ぶ | 渡す資料選び |
| ハーネス | 動く環境を整える | 職場・権限・道具の整備 |
| ループ | 時間軸で動きを回す | 赤ペン添削のサイクル |
| グラフ | 構造で組む | チームでの分業 |

同動画は、前半3つ（プロンプト・コンテキスト・ハーネス）を**材料と環境**に関わる部分、後半2つ（ループ・グラフ）を**動きの設計**に関わる部分だと分類している。この二分は覚えておくと便利である。前半は「AIに何を持たせるか」、後半は「AIをどう動かすか」の話だからだ。

## それぞれが何を設計するのか

**プロンプト**は最も内側の層で、AIへの指示そのものを磨く。曖昧な指示は曖昧な回答しか生まないため、役割・条件・形式を具体的に渡すことが重要だと同動画は説明している。詳しくは[プロンプトエンジニアリングとは何か](./what-is-prompt-engineering.md)と[プロンプトの構造](./prompt-anatomy.md)で扱う。

**コンテキスト**は、何を・いつ・どれだけAIに読ませるかの設計である。1回ごとの指示文の外側にある、参照情報全体が対象になる。→ [なぜ文脈が効くのか](./why-context-matters.md)

**ハーネス**は、AIが動く環境そのものを設計する層である。同動画は、道具（何を実行し何と接続するか）・制限（触れてはいけない領域）・権限（フルオートか承認フローを挟むか）・ルール（毎回読み込むべきコンテキスト）の**4つの観点**で環境を整えるものだとしている（[プロンプトの構造](./prompt-anatomy.md)で扱ったプロンプトの4要素とは別の切り口である）。語源は馬具のハーネスで、装備が整っているからこそ安定して動ける、という比喩だと説明している。

別チャンネル「安野貴博の自由研究」の動画も同じ層を挙げ、より具体的な例を示している。「テストが通らなければ先に進めない」といった仕組みはプロンプトでの依頼ではなくAIが作業する環境側の設計だとし、`AGENTS.md`や`CLAUDE.md`のようなルールファイル、テスト、リンター、ログ・履歴管理、判断に迷った際の人間へのエスカレーション機構などがハーネスに含まれるとしている（[ループエンジニアリング解説動画](../sources/video-pe-loop-engineering-overview.md)、auto字幕からの聞き取り）。

この例は分かりやすい。「バグを入れないでください」とプロンプトに書くのがプロンプト層の発想だとすれば、**テストが通らなければマージできない仕組みを用意する**のがハーネス層の発想である。SI実務でいうCI/CDやコードレビュー規約の整備に近い。

[5つのエンジニアリング解説動画](../sources/video-pe-five-engineering-stages.md)自身の実例としては、Claude Code自体がハーネスエンジニアリングの土台になっているとし、ファイルの読み書き権限、CLAUDE.mdやメモリの自動読み込み、削除や外部送信時の承認フローなどを挙げている。

**ループ**は、実行・検証・改善を繰り返させる時間軸の設計である。同動画は実例として、画像生成後にビジョン機能で文字崩れなどを確認し直すループ、Excelの売上データを何度も再計算させて数値を合わせるループ、スライドの文字数超過を検出して削るループを挙げている。→ [ループエンジニアリング](./loop-engineering.md)

**グラフ**は構造軸の設計で、「誰に何を任せるか」を分けて任せ、後から束ねて仕上げる考え方だと[5つのエンジニアリング解説動画](../sources/video-pe-five-engineering-stages.md)は定義している。同動画は、最も賢い（高コストな）モデルには段取りとチェックの責任だけを持たせ、実作業はより安価なモデルに任せることで、コストを抑えながら質の高い成果物を得るという運用を紹介している。実例として、AI活用事例を100個まとめる書籍執筆で調査・検証・執筆・デザインを別のAIに分業させる「AI100ライター」スキルや、構成案作成・画像生成・コーディングを並列で分業させることで生成スピードを上げる「LPビルダー」スキルを挙げている。

この「賢いモデルに段取り、安価なモデルに実作業」という原則を具体的な役割分担に落とし込んだ例として、[ループエンジニアリング5+1解説動画](../sources/video-pe-loop-engineering-5plus1-parts.md)が紹介する自作ループの構成がある。計画担当（プランナー）と、重要性の高いセキュリティ確認担当には上位モデル（Opus）を割り当てる一方、実装担当・テスター・仕様確認担当・コードレビューアには下位モデル（Sonnet）を割り当てているという。段取りと最終チェックだけ高コストなモデルに絞り、量の多い実作業を安価なモデルに回すという、グラフ層の考え方がそのまま人員配置になっている例である。

## 4段階か5段階か

ここで注意しておきたいことがある。**数え方はソースによって違う**。

[5つのエンジニアリング解説動画](../sources/video-pe-five-engineering-stages.md)は5つ（プロンプト／コンテキスト／ハーネス／ループ／グラフ）を挙げるが、[ループエンジニアリング解説動画](../sources/video-pe-loop-engineering-overview.md)は「プロンプト→コンテキスト→ハーネス→ループの4段階と言われている」としてグラフを含めていない。RUNTEQの動画も同じ4段階で整理し、さらに各段階におおよその時期を割り当てている——プロンプトが2024年頃まで、コンテキストが2025年、ハーネスが2026年初頭、ループが2026年6月〜、という見立てである（[ループエンジニアリング5+1解説動画](../sources/video-pe-loop-engineering-5plus1-parts.md)、auto字幕からの聞き取り）。

3つとも動画の自動生成字幕を出所とする紹介であり、業界で確定した標準用語ではない。区切り方も時期の割り当ても発信者ごとの整理だと理解しておくべきだ。同じ5段階を別の資料群から扱っている[用語の系譜と5段階](../graph-engineering/term-lineage-and-layers.md)とあわせて読むと、この用語の揺れの実態がさらにつかめる。

一方で、独立した3つのソースが**プロンプト→コンテキスト→ハーネス→ループという順序**では一致している点は意味がある。用語の細部より、この「内側から外側へ広がる」方向のほうが本質に近いということだ。

## 乗り換えではなく入れ子

もっとも重要な論点がこれである。

[ループエンジニアリング5+1解説動画](../sources/video-pe-loop-engineering-5plus1-parts.md)は、これらは「別の概念に切り替わる」乗り換えではなく、**前の段階を内包しながらもう1枚ラップしていく関係**だと強調している。[5つのエンジニアリング解説動画](../sources/video-pe-five-engineering-stages.md)も同じ結論に達しており、グラフエンジニアリングの1マスの中にプロンプトとコンテキストエンジニアリングが含まれ、そのマス同士をループが回し、全体をハーネスが環境として支えるという入れ子構造で捉えるべきだとしている。

つまり、ループを設計する人がプロンプトを書かなくなるわけではない。ループの各マスの中身は依然としてプロンプトである。むしろ、自動で何十回も回るループの中に置かれるぶん、1つのプロンプトの質は**人間が毎回目視で直せた頃より重要になる**。「プロンプトエンジニアリングはもう古い」という言い方が誤解を招くのはこの点である。

## いつ何を意識するか

では、新人がいきなり5層すべてを設計すべきかというと、そうではない。

[5つのエンジニアリング解説動画](../sources/video-pe-five-engineering-stages.md)は、最初からすべてを意識するのはやりすぎだとし、まずは通常のプロンプト・コンテキストエンジニアリングの範囲で試し、精度が不十分だと感じた症状に応じて追加の考え方を導入すべきだと助言している。同動画が挙げる症状別の目安は次のとおりである。

- **意図と違う結果**が返る → プロンプトを見直す
- **前提を忘れる** → コンテキストを見直す
- **手作業の事故が怖い** → ハーネスを見直す
- **品質が安定しない** → ループを見直す
- **タスクが大きすぎて崩れる** → グラフを見直す

この対応表は、地図として実用的である。問題が起きたときに「プロンプトの書き方が悪かったのか」と内側だけを疑い続けると、いつまでも解決しないことがある。前提を毎回忘れるなら、それは指示文をいくら磨いても直らない——足りないのは外側の層だからだ。

チャット型AIを使っている段階の読者にとって、当面の実務範囲はプロンプトとコンテキストの2層である。残り3層は「うまくいかないときに疑う先」として頭の片隅に置いておけば十分だ。

## この先にあるもの——配信者独自の予測とおまけ

動画はここまでの5層の外側にも触れている。ハーネスエンジニアリングの実例として、配信者自身が構築しているAIキャラクターのスタッフが各アプリケーションに接続された仮想オフィス「AI工房」を、ハーネスエンジニアリングの「最終形態」だと位置づけている。さらに動画終盤では、時刻やWebhook、環境変化をトリガーとして判断軸も含めてAIに持たせ、人間の介在なしに自律的にタスクを開始・実行させる設計思想を「AGIエンジニアリング」と呼び、今後こうした考え方が出てくるだろうという配信者独自の予測を示している。おまけとして、雑に音声入力した内容を「ナチュラルジャパニーズ」のようなリライト用スキルで一度整形してからループ・グラフエンジニアリングに渡す「音声入力プロンプトエンジニアリング」という運用方法も紹介している。AI工房・AGIエンジニアリング・音声入力プロンプトエンジニアリングのいずれも、動画内で体系化された用語ではなく配信者個人の実践・予測である点は割り引いて読む必要がある（[5つのエンジニアリング解説動画](../sources/video-pe-five-engineering-stages.md)、auto字幕からの聞き取り）。
