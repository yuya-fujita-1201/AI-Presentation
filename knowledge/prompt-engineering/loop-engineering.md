# ループエンジニアリング

2026年半ば、AIコーディングの第一線にいる人々が奇妙なことを言い始めた——「**プロンプトを書くのはやめよう**」。

プロンプトの書き方を学ぼうとしている最中にこれを聞くと、はしごを外された気分になる。だが実際の主張は「プロンプトは不要になった」ではない。手で1回ずつ指示する働き方から、**指示する仕組みそのものを設計する**働き方へ重心が移った、という話である。

## 誰が何と言ったのか

安野貴博氏の動画は、この転換を象徴する2つの発言を紹介している。OpenAIのピーター・バーガー氏がXで、コーディングエージェントに直接プロンプトを打つのはやめて**エージェントにプロンプトを打つループを設計すべき**だと投稿したこと、そしてAnthropicで当時Claude Codeの開発に携わっていたボリス・チェルニー氏が、もう直接プロンプトは打たず、ループを走らせてそれがClaudeに指示をする、**自分の仕事はループを書くことだ**と述べていることである（[ループエンジニアリング解説動画](../sources/video-pe-loop-engineering-overview.md)、auto字幕からの聞き取り）。

RUNTEQの動画も同じ2人を挙げ、2026年6月に3人がほぼ同時期に似た主張をしたことで火がついたと説明している。3人目としてGoogleのエンジニアリングディレクターがブログで「ループエンジニアリング」という名前を付けて体系化したことを挙げている（[ループエンジニアリング5+1解説動画](../sources/video-pe-loop-engineering-5plus1-parts.md)、auto字幕からの聞き取り）。

ただし**人名の表記は2つの動画で食い違っている**（前者は「ピーター・バーガー」「ボリス・チェルニー」、後者は「ピーター・スタインバーガー」「ボリス・カーニー」）。いずれもauto字幕からの聞き取りであり、同一人物を指していると見られるが、氏名を引用する場合は原典で確認すべきである。

一致しているのは中身のほうだ。**人間はループの外に出て監督する**——この点で両動画の紹介は完全に重なっている。

## Human in the Loop から Human on the Loop へ

この移行を一語で言い表したのが、前置詞の違いである。

[ループエンジニアリング解説動画](../sources/video-pe-loop-engineering-overview.md)は、ループとは人間が作業しAIが出力したものを人間が判断してレビューし、その結果を踏まえてAIが次の作業を行い、また人間が確認する、という**螺旋状に繰り返される流れ**だとしている。このループの中に人間がいてレビューや指示を行っている状態が **"Human in the Loop"（HITL）**、AIがここまで賢くなった以上ループ内部に人間が常にいる必要はなく、外側から方向がずれた時にだけ介入して監督すればよいという考え方が **"Human on the Loop"（HOTL）** だと説明している。「in」と「on」の一語の違いだが、この違いが非常に重要だとしている。

チャット型AIの使い方は、定義上すべてHITLである。1回聞いて、読んで、次を打つ。この往復から出ていないうちは、AIの稼働時間は人間の手が空いている時間に縛られる。

## 定義と、その学術的な土台

[ループエンジニアリング5+1解説動画](../sources/video-pe-loop-engineering-5plus1-parts.md)は、ループエンジニアリングの根本を「**指示するのではなく指示する仕組みを作る**」ことだとしている。従来は人間がプロンプトを打ちAIが応答し人間が次の指示を出す繰り返しだったのに対し、ループエンジニアリングでは**人間がゴールだけを定義**し、その仕組みの中でAIが自動的に指示を出し・結果を検証し・次のタスクを決めることをゴールが終わるまで続ける、という整理である。

同動画はこれを人のチームに例え、従来は自分もプレイヤーとして動く「プレイングマネージャー」型だったのに対し、ループでは**開発フローの仕組み自体を設計してあとはチームに任せる**マネジメント寄りの働き方に近いとしている。SIでプロジェクトマネジメントを経験した人には、この比喩がいちばん通りがよいはずだ。

思いつきの流行語ではなく研究上の土台があるとして、同動画は **ReAct**（考えて行動して観測してまた思考する、というサイクルを繰り返す考え方）と **Reflection**（失敗を言葉にして記録し次のトライに生かすパターン）の2つを挙げている。

## インナーループとアウターループ

ループは1種類ではない。[ループエンジニアリング5+1解説動画](../sources/video-pe-loop-engineering-5plus1-parts.md)は2層に分けて説明している。

**インナーループ**は1つのタスクの中で、編集・テスト作成・テスト実行・失敗検知・修正・再実行というサイクルを、通過するまで繰り返すものだとしている。これにより「完了しました」と言いながら実際には直っていない、という従来のAIコーディングの不満を解消できるという説明である。検証は何を確認するかを明確にすべきだとし、テストだけでなくセキュリティリスク・コードの品質・仕様との食い違いなど、**複数の観点のレビューを重ねるほど検証の精度が上がる**としている。

**アウターループ**は、1つのインナーループ（1機能・1セッション相当）だけでは要件を満たせないため、複数のタスクをまたいで回していくものだとしている。ポイントは、あるタスクでの失敗の教訓を**次のタスクに引き継ぐ設計**にしておくことだとしている。

安野貴博氏の動画は、AI研究者のアンドリュー・ン氏による**3種類の入れ子ループ**という整理も紹介している。①仕様とテスト用データを渡すとエージェントが実装・テスト・修正を数分刻みで繰り返す最速のループ、②数十分から数時間おきに人間が介入して方向性を修正する監督ループ、③短くて数時間・長ければ数週間かかる外部フィードバックループ（友人やユーザーに見せる、本番でABテストする）である（[ループエンジニアリング解説動画](../sources/video-pe-loop-engineering-overview.md)、auto字幕からの聞き取り）。

同動画は、ン氏が人間がループに残る理由について述べたという仮説も紹介している。「人間のセンスという貴重な資源があるから」ではなく、**ユーザーや製品が使われる状況についてAIが知らない情報を人間が持っており、その情報量の差を埋めているに過ぎない**、というものである。人間の価値を情報の非対称性に還元するこの見方は、居心地の悪さも含めて考える価値がある。

## ループを構成する5+1の部品

[ループエンジニアリング5+1解説動画](../sources/video-pe-loop-engineering-5plus1-parts.md)は、機能するループは**5つの部品とプラス1のメモリー**でできているという枠組みを紹介している。

1. **自動化** — 定期的にタスクを発見しエージェントを起動する、ループのコア
2. **ワークツリー** — 複数エージェントが衝突しないよう作業領域を分離する
3. **スキル** — プロジェクトの規約を永続化する
4. **プラグイン／コネクター** — Slackなど依存ツールと接続し外部世界とつなぐ
5. **サブエージェント** — 作る役と検証する役を分離して分業する
6. **＋1 メモリー** — セッションの中ではなく会話の外に状態を永続化する。完了したタスク・進捗中のタスク・学んだことを書き出すことで、次のループの質が上がっていくとしている

5番目の「作る役と検証する役の分離」は、独立した複数のソースが揃って重視している点である。[5つのエンジニアリング解説動画](../sources/video-pe-five-engineering-stages.md)は、AIは**自分の生成物に対する採点が甘くなりがち**であり、背景コンテキストを持たない別のサブエージェントにダメ出しさせることで精度が大きく向上すると説明している。Anthropicの公式ドキュメントも、Claude Opus 5がサブエージェントのチームを適切に調整でき、効果的な **writer-verifierパターン**を構築できると述べている（[Prompting Claude Opus 5](../sources/article-pe-claude-opus-5-prompting.md)）。動画側の「別のAIに検証させる」という経験則と、モデル提供元がパターンとして名前を付けて言及している事実が、ここでは一致している。

## 部品が組み上がった一例：エピックフローと移ロー

5+1の部品は抽象的な分類だが、[ループエンジニアリング5+1解説動画](../sources/video-pe-loop-engineering-5plus1-parts.md)の講師は、これらを実際に組み合わせた自作スキルとして**エピックフロー**（アウターループ用）と**移ロー**（インナーループ用、聞き取り）を紹介している。

**移ロー**（動画内の呼称。自動字幕による聞き取りのため表記に不確実性あり）は、実装者が実装 → 別のサブエージェントであるテスターがテスト → 4軸のレビュー（動画では仕様確認担当・コード確認担当・セキュリティ確認担当の3レビューアとしている）を通過 → 実装者に戻してプルリクエストを作成、という流れである。作る役（実装者）と検証する役（テスター・レビューア）をサブエージェントとして分離している点は、上で触れたwriter-verifierパターンの具体形にあたる。

**エピックフロー**は、大きな要件を入力するとまずプランナーが要件をタスクに分解し、依存関係・受け入れ条件・目的を決める → ここで1回目の人間の承認を挟む → メインエージェントがタスクを1つずつ移ローに渡して実行 → 1タスク完了ごとにエピックのブランチにマージ → 全タスク完了後、最終的な大きなプルリクエストができた時点で2回目の人間の確認、という流れである。プランナーは要件が曖昧な点について質問を返してくるため、要件を詰めてから分解が始まる設計になっており、これが精度の高さにつながっているという。

このモデルの使い分け（プランナーとセキュリティ確認に上位モデル、実装・テスト系に下位モデル）が「賢いモデルに段取り、安価なモデルに実作業」というグラフ層の原則の実例になっている点は、[5つのエンジニアリング段階](./five-engineering-stages.md)のグラフの節で扱った。

## 暴走を止める側の設計

自動で回る仕組みには、止める設計が要る。[ループエンジニアリング5+1解説動画](../sources/video-pe-loop-engineering-5plus1-parts.md)は、ループが「勝手に動くスーパーエンジニア」ではなく「**粘り強く動くジュニア**」に近いという前提のもと、4つのルール定義を挙げている。

1. **明確なタスク定義** — 完了条件が一言で言えるか
2. **安全な作業環境** — 失敗しても全体を壊さない設計か
3. **視覚的な成功判定** — テスト・リント・型チェックで合否を自動判定できるか
4. **ハードストップ** — 無限ループや暴走を防ぐため、リトライ回数や時間・コストの上限を設け、詰まったら人間に確認する

上限を設けるという発想は、公式ドキュメント側にもある。Anthropicは、コストに敏感なワークロードにおいては**サブエージェントへの委譲に上限を設けること**を推奨している（[Prompting Claude Opus 5](../sources/article-pe-claude-opus-5-prompting.md)）。

コスト面の注意も見落とせない。[5つのエンジニアリング解説動画](../sources/video-pe-five-engineering-stages.md)は、1回で終わる作業を何周も繰り返すためコストと時間がかかると指摘している。ループは無条件に得ではなく、**品質のばらつきをコストで買う**取引だと理解しておくべきだ。

## 新人にとっての意味

チャット型AIしか使っていない段階で、いきなり自作のループを組む必要はない。ただし、この地図を知っているかどうかで**同じツールの見え方が変わる**。

「テストが通るまで直して」と一言添えるのは、素朴だがインナーループの発想である。前回の失敗をメモに残して次の依頼に添えるのは、メモリーの発想だ。別のチャットに成果物を貼って「厳しくレビューして」と頼むのは、writer-verifierの手動版にあたる。**部品の名前を知っていれば、手作業のうちから同じ形をなぞれる**。

そして、ループは既存の層を捨てるものではなく前の段階を内包する入れ子構造だという点は[5つのエンジニアリング](./five-engineering-stages.md)で詳しく扱った。

ループの発想はソフトウェア開発に限らない。[ループエンジニアリング解説動画](../sources/video-pe-loop-engineering-overview.md)は、秘書業務での日程調整を例に挙げている。「特定の時間以降は予定を入れない」といったルール違反を検出するハーネスを用意しておけば、AIによる自動日程調整を信頼できるようになるという。また、会議終了後にAIが自動で立ち上がり、文字起こしから発生したタスクを洗い出してカレンダー招待を送るという具体例も紹介している。コードのテストとリントの代わりにルール違反の検出を検証手段にすれば、同じ「自動化→検証→次へ」の構造が非開発業務にもそのまま持ち込める、ということである。
