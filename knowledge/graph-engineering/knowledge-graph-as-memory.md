# もう1つのグラフ——記憶としてのナレッジグラフ

「グラフエンジニアリング」の「グラフ」は、実は1つのものを指していない。**エージェントが今どこまで作業を進めたかを示す「実行の地図」**と、**世界についての事実がどうつながっているかを示す「知識の地図」**は、見た目こそ似た図でも別物であり、混ぜると設計そのものが壊れる。このコンセプトでは、後者——エージェントの記憶を永続化する**ナレッジグラフ**の作られ方と、前者である**実行構造(DAG)**とを分けて捉えるべき理由を解説する。

## 「グラフ」という言葉が指す複数の意味

- 入門解説動画は、「グラフ」という同じ言葉で実は3つの異なるものが語られており、これを混ぜると初心者は確実に迷子になると警告している。挙げられているのは、①**実行の地図**(仕事の手順と分岐をつないだ段取り表)、②**ループの網**(持ち場同士が声をかけ合う関係)、③**知識の地図**(レシピ帳同士のつながり＝相関図)の3つである
- 別の解説動画は、Turing Postの記事を引用する形で、より広い業界の語りの中に4つの異なる意味が混ざっていると指摘している: **コントロールグラフ**(処理順を表す)、**ナレッジグラフ**(知識の関係を表す)、**エグゼクショントレース**(実際に通った経路を表す)、**インプルーブメントループ**(改善が巡回するループ)
- この2本の整理は語彙が完全には一致しないが、重なりは見て取れる——「実行の地図」「コントロールグラフ」「エグゼクショントレース」はいずれも**エージェントが何をどの順で行ったか**を指し、「知識の地図」「ナレッジグラフ」は**世界についての事実の関係**を指している。この対応関係を踏まえて、以下ではこの2系統を意識的に分けて記述する
- 5段階の用語系譜(プロンプト・コンテキスト・ハーネス・ループ・グラフ)そのものの解説は [term-lineage-and-layers.md](./term-lineage-and-layers.md) を、ノード・エッジ・DAGといった基本語彙の定義は [graph-primitives.md](./graph-primitives.md) を参照

## 出発点: autoresearchの自律研究ループ

- ある解説動画は、あるAIエージェントが2日間でおよそ700回もの実験を自律的に回し、20個ほどの具体的な改善を達成した事例——アンドレイ・カルパシーの自律研究エージェント実験「autoresearch」——から解説を始めている。この間、人間の介入はほとんどなかったとしている
- このシステムの中心コードは全体でたった630行と説明されている。構成ファイルは大きく3つで、データ準備用ファイル(prep.pyに相当すると推測、聞き取りに不確実性あり)、モデル学習の実験台となるファイル(train.pyに相当すると推測、聞き取りに不確実性あり)、そして「1番重要」とされる3つ目のファイル(.mdファイルに相当すると推測、聞き取りに不確実性あり)から成るとしている。3つ目のファイルには研究の進め方・守るべき制約・人間にいつ相談するかという振る舞いのルールが自然言語で書かれており、自然言語による制約がエージェントの動作をプログラムしていると説明している
- エージェントが実際に行っているのは機械的なループだとしている: (1)現在の状態と履歴を読み込んで変更を1つだけ提案する、(2)5分間の訓練を走らせて検証スコアなどの指標を測る、(3)スコアが良ければ変更を残し、悪ければ元に戻す

### 自律性が成り立つ4つの条件

この自律性は「決して魔法ではなく厳格な条件のもとで成り立っている」と強調され、以下の4条件が挙げられている。

1. 結果が数字で出る、検証可能な出力があること
2. 失敗しても巻き戻せる(元に戻せる)行動であること
3. フィードバックがすぐに得られる、短い実験サイクルであること
4. 行動範囲が限定された、区切られた環境のガードレールがあること

これらが揃っていない場所で自律性を与えるのはリスクが高い、という注意が添えられている。

## GitHubのマージ前提モデルからAgentHubへ

- 1人ぼっちの研究ループを、数千のエージェントが非同期に動く規模にスケールアップしたときに何が起こるかが第2幕として展開される
- 普段使うGitHubのようなリポジトリは、最終的に1つのメインブランチへマージすることを前提に設計されている。しかし数千のエージェントが探索を行う「AgentHub」ではほとんどの結果がマージされない
- 失敗した試行の記録すら「この方向は行き止まりだった」という重要な道しるべになる。つまり合意形成のための記録ではなく、**探索のための地図**として機能すると説明している
- 数千規模のエージェントを展開したとき、真っ先に機能しなくなるのは人間向けの前提だとして、以下の4つが挙げられている: ①単一のメインブランチへの集約、②人間のペースでのコードレビュー、③会話ログだけに頼った記憶、④マージを中心とした協調作業。大規模並列探索の世界では、これら4つの前提は最初から成り立たないとしている

### DAGによる探索ナビゲーション

- この探索の地図として使われるのがDAG(有向非巡回グラフ)だとしている。エージェントたちはこの地図をナビゲートするために、結果の先に何が試されたかを探る「children」、まだ誰も手をつけていない最前線を探す「leaves」、ここまでどうやってたどり着いたかを確認する「lineage」といったコマンドを使うと説明している(これらのコマンド名は聞き取りに基づく推定で、不確実性あり)
- コミットは一直線ではなく、網の目のような系譜を描いていくとしている

## 知識グラフ構築の役割分担と名寄せ

- 動的なオーケストレーションの裏側を支えているのが知識グラフだとし、現代の知識グラフ構築は明確な役割分担で行われると説明している
  - まず**高速なモデル**が、大量の文書から人物や組織といったエンティティとその関係性を抽出する
  - 次に、**より賢いモデル**がそれを受け取り、複雑な論理が必要な「名寄せ」(統合)を行う
  - こうして出来上がったグラフから、必要な情報だけを選択的に取り出す
- 名寄せの具体例として、「エドウィン・オルドリン」と「バズ・オルドリン」が挙げられている。文字列だけを比較すればほとんど重ならないが、賢いモデルは周囲の説明文などの文脈を手がかりに、この2つが同一の宇宙飛行士を指していると判定し、1つのエンティティとして統合する
- 名寄せに失敗すると別人が1つのエンティティに束ねられ、以後の検索結果が汚染されるリスクがある。この失敗パターンとその歯止めは [risks-and-safeguards.md](./risks-and-safeguards.md) で扱う

## コミットDAGと知識グラフを混ぜてはいけない

- エージェントの行動を記録する「**コミットのDAG**」と、事実を記録する「**知識グラフ**」はまったくの別物として扱う必要があると強調されている
- DAGは「**何が変わったか**」という仕事の系譜であり、知識グラフは「**どんな関係があるか**」という世界についての知識である。この2つはシステム内で接続することがあっても、決して混ぜてはいけないと説明している
- 上記の「グラフが指す複数の意味」に照らすと、コミットDAGは「実行の地図」「コントロールグラフ」「エグゼクショントレース」の系列に、知識グラフは「知識の地図」「ナレッジグラフ」の系列にそれぞれ対応する、という整理ができる。エッジ(接続)の設計原則そのものは [graph-primitives.md](./graph-primitives.md) にまとめている

## エージェントは忘れる、グラフは忘れない

- ここが核心部分だとして、「エージェントは忘れる、グラフは忘れない」と強調されている。会話のコンテキストウィンドウは実行が終わればリセットされて消えるが、グラフとして構造化された情報は永続する。これがあるからこそ、長期的な計画の実行や失敗からの復帰、さらには誰が何をどの根拠で主張したかという厳密な検証が可能になると説明している
- ここまで登場したアーキテクチャの特徴を1つの表に整理し、それぞれが異なる運用上のボトルネックをシステムの外部に切り出していると述べている

| アーキテクチャ | 担うボトルネック |
|---|---|
| ループ | 反復と評価 |
| チェーン | 手順 |
| スワーム | 並列の役割分担 |
| DAG | 実験の系譜 |
| グラフ | 事実やセッションをまたぐ記憶 |

## バイブコーディング→エージェンティックエンジニアリング→グラフエンジニアリング

エージェント設計の進化は3つの段階で捉えられると整理されている。

1. **バイブコーディング**: 人間が意図を伝え、モデルに書かせる段階
2. **エージェンティックエンジニアリング**: 仕様を決めて検証を行う段階
3. **グラフエンジニアリング**: 一時的な記憶から永続的な状態へと哲学がシフトし、共有される状態を持つ段階

この進化はAI特有の目新しい話ではないと位置づけられ、人間の歴史を振り返れば、帳簿・カルテ・公開日誌など、個人の頭の中にある記憶を超越するために常に記録と検証の仕組み(台帳)を使ってきたと述べている。グラフエンジニアリングへの移行も、アーキテクチャとしての必然的な進化の形だとしている。
