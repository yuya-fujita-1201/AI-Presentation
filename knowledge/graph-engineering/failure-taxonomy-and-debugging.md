# 失敗の分類とデバッグ

複数のエージェントをつないだシステムが期待通りに動かなかったとき、最初に困るのは**「どこが悪いのか分からない」**ことである。単体のエージェントなら出力を見れば良し悪しが分かるが、10個のノードが順に受け渡した末に出てきた変な答えは、どのノードのせいなのかが自明でない。

この「切り分けの難しさ」は感覚的な愚痴ではなく、研究の対象になっている。本稿では、失敗を体系的に分類した2つの論文——**MAST**（マルチエージェントシステムの失敗分類）と**AgentErrorTaxonomy**（エージェント個体の失敗分類）——を紹介し、それを実地の失敗報告と突き合わせる。

なお[リスクと歯止め](./risks-and-safeguards.md)は「グラフ化すると失敗も組織化される」という増幅のメカニズムとその歯止め（アンカー、人間承認）を扱っている。本稿はそれと相補的に、**起きてしまった失敗をどう分類し、原因をどう特定するか**という診断の側を扱う。

## なぜ分類が要るのか

MAST論文は、マルチエージェントLLMシステムが一般的なベンチマークで僅少（minimal）な性能向上にとどまっているにもかかわらず、**これまで失敗パターンの体系的理解が欠けていた**という空白を研究の出発点に置いている（[MAST論文](../sources/article-ge-mast-multi-agent-failures.md)）。

分類がないと何が困るか。「うまくいかなかった」という報告が全部同じ1つの箱に入ってしまい、次に何を直せばいいのかが決まらない。医者が「体調が悪い」を症状ごとに分けるように、失敗にも名前が要る、というのがこの研究群の共通した動機である。

## MAST: 3カテゴリ14の失敗モード

MAST（Multi-Agent System Failure Taxonomy）は、7つの人気マルチエージェントフレームワークにまたがる**1,600件以上の注釈付きトレース**からなるデータセットMAST-Dataを基盤としている。分類体系そのものは、そのうち**150件のトレースを専門家アノテーターが分析**して構築されたもので、アノテーター間一致度は**kappa=0.88**という高い値を記録したと著者らは述べている。

分類は3つの主要カテゴリに整理され、その下に合計14の失敗モードが置かれている。

| カテゴリ | 中身（論文が挙げる例） | 直す場所 |
|---|---|---|
| (i) **システム設計上の問題** | 役割定義の曖昧さ、終了基準の欠如 | グラフを描く段階。誰が何を担当し、いつ終わりとするか |
| (ii) **エージェント間の非整合** | 情報フローの破綻、エージェント間の前提の衝突、不完全な文脈伝播 | エッジ。何を渡し、何が渡っていないか |
| (iii) **タスク検証** | 誤った受理基準の適用、誤ったエージェントによる時期尚早なタスク終了 | 検証レイヤー。誰が合格を出すか |

この3分割は、実務上そのまま**問診の順番**として使える。おかしな結果が出たとき、(i)そもそも役割と終了条件を決めていたか →(ii)必要な情報は本当に届いていたか →(iii)合格判定は正しい相手が正しい基準で出していたか、と順に潰していけばよい。

著者らはさらに、評価をスケールさせるために人間アノテーションで確立した分類をもとに**LLM-as-a-Judgeパイプライン**を構築し、失敗モードの自動判定を可能にしたとしている。実験対象のモデルはGPT-4・Claude 3・Qwen2.5・CodeLlama、タスク種別はコーディング・数学・一般的なエージェントタスクにまたがる。データセット・分類体系・LLMアノテータツール一式は公開されていると述べられている。

**注目したいのは、14モードのうち少なくとも2カテゴリ分が「モデルの賢さ」とは無関係だという点である。** 役割定義の曖昧さも、終了基準の欠如も、文脈伝播の不完全さも、より賢いモデルに差し替えれば直るものではない。これらは配線の問題であり、まさにグラフエンジニアリングが扱う領域にある。

## AgentErrorTaxonomy: カスケード失敗と5領域

もう1つの論文「Where LLM Agents Fail and How They can Learn From Failures」は、視点をエージェント個体の内部に向ける（[AgentDebug論文](../sources/article-ge-agent-error-taxonomy-debug.md)）。著者らの課題認識は、LLMエージェントが計画・メモリ・反省・ツール使用を統合する一方で、**単一の根本原因エラーが後続の判断へ波及していく「カスケード失敗」に脆弱である**という点にある。

この論文は3つの成果物を提示している。

1. **AgentErrorTaxonomy** — 失敗モードを **Memory（メモリ）/ Reflection（反省）/ Planning（計画）/ Action（行動）/ System-level operations（システムレベル操作）** の5領域に体系化した分類
2. **AgentErrorBench** — ALFWorld・GAIA・WebShopという3環境での実エージェント軌跡を体系的にアノテーションしたベンチマーク。著者らは実環境の軌跡から構築された初の大規模失敗軌跡データセットと位置づけている
3. **AgentDebug** — 失敗の根本原因を特定したうえで矯正フィードバックを提供し、反復的な改善を可能にするデバッグフレームワーク

効果として著者らは、AgentErrorBench上で**全正解精度（all-correct accuracy）24%の向上**、**ステップレベル精度17%の向上**を達成し、3ベンチマーク全体では**タスク成功率が最大26%の相対改善**を示したと報告している。

### カスケード失敗という考え方が効く理由

「1つの根本原因が後続へ波及する」という見立ては、グラフを扱ううえで実用的な意味を持つ。**最後に見えた症状と、直すべき場所は別のノードにある**ということだからである。

たとえば最終レポートの結論がおかしいとき、レポート執筆ノードのプロンプトを直したくなる。しかし原因が3つ前の調査ノードの記憶（Memory）にあったなら、執筆側をいくら磨いても症状は消えない。AgentDebugが「根本原因の特定」を明示的な工程として置いているのは、この取り違えを防ぐためだと読める。

MASTが**システム全体の配線**を分類しているのに対し、AgentErrorTaxonomyは**個々のノードの内部**を分類している。2つを組み合わせると、「どのノードか」（カスケードを遡る）と「そのノードの何か」（5領域のどれか）の2段階で位置を特定できる。

## 実地の失敗はどう分類されるか

分類体系は抽象的に見えるが、公式に報告された実地の失敗例を当てはめると具体性が出る。Anthropicは自社のマルチエージェント研究システムの開発（[Anthropic公式記事](../sources/article-ge-anthropic-multi-agent-research-system.md)）と、並列Claudeによるコンパイラ開発実験（[Building a C compiler](../sources/article-ge-anthropic-building-c-compiler.md)）の双方で直面した問題を率直に記録している。以下は両記事の報告に、上記2つの分類を筆者が対応づけたものである。

| 報告された失敗 | 対処 | 対応する分類 |
|---|---|---|
| 単純なクエリに対して**50個ものサブエージェント**を生成してしまった | 複雑度に応じたスケーリングルールを組み込んだ | MAST (i) システム設計（役割・規模の定義） |
| サブエージェント間で**調査が重複**した | 詳細なタスク説明と役割分担の明示 | MAST (ii) エージェント間の非整合 |
| 低品質な**SEO最適化コンテンツを優先**して選んでしまった | ソース品質のヒューリスティックを追加 | AgentErrorTaxonomy: Action（行動選択） |
| **十分な結果が得られても探索を継続**してしまった | ― | MAST (i) 終了基準の欠如 |
| ツールの説明が不明瞭で、未知のツールに遭遇すると全く誤った経路へ進んだ | Claude自身にプロンプト改善を提案させ、ツール説明を改善（タスク完了時間40%短縮） | MAST (ii) 不完全な文脈伝播 |
| 単一タスクに固定すると**全エージェントが同じバグで停止**してしまった | ― | MAST (i) システム設計（タスク分割の多様性の欠如） |

こうして並べると、**失敗の大半が「指示・定義・境界の書き方」に帰着している**ことが見えてくる。同記事はサブエージェントへの委譲において目的・出力形式・ツール指定・境界を明示する必要があるとし、「research the semiconductor shortage」のような短く曖昧な指示では不十分だと述べている。MASTのカテゴリ(i)(ii)が示すものと同じ結論である。

## デバッグを設計に組み込む

以上から、実務で持ち帰れる指針は次のようになる。

1. **失敗を「うまくいかなかった」で片付けず、カテゴリ名を付ける**。設計（役割・終了条件）／伝達（何が渡っていないか）／検証（誰が合格を出したか）のどれかを毎回決める
2. **症状の出た場所と原因の場所を分けて考える**。カスケード失敗を前提に、最後のノードから遡る
3. **終了基準を最初に書く**。MASTが(i)に「終了基準の欠如」を、Anthropicが「十分な結果が得られても継続する」を挙げているのは同じ問題である。いつ止めるかを決めていないグラフは、止まらないか、早すぎるところで止まる
4. **トレースを読めるようにしておく**。MASTもAgentDebugも、分析の前提はトレース（実行の記録）である。記録が残っていないシステムは、そもそも分類の対象にならない
5. **本番相当の環境で再現してから直す**。Anthropicはプロンプトエンジニアリング上の教訓として、Consoleでプロンプトとツール環境を正確に再現するシミュレーション駆動開発を第一に挙げている（[Anthropic公式記事](../sources/article-ge-anthropic-multi-agent-research-system.md)）。再現環境がなければ、上記のカテゴリ分けも原因特定も推測の域を出ない

4点目に関連して、[マルチエージェント化の損益分岐点](./multi-agent-break-even.md)で触れたOpenAIの4条件に「trace legibility（トレースの可読性）」が含まれていたことを思い出したい。トレースの読みやすさは、性能とは別立てで**エージェントを分けてよい理由**に数えられている。デバッグ可能性は後から足す機能ではなく、分割の動機そのものになりうるということである。

検証を誰にどう担わせるかという設計は[検証レイヤーの設計](./verification-and-testing.md)、失敗が組織化されて増幅するメカニズムと歯止めは[リスクと歯止め](./risks-and-safeguards.md)を参照。
