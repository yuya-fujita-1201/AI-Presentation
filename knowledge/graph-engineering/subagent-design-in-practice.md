# サブエージェント設計の実務

ここまでの議論は「どう分けるか」「誰が所有するか」という設計の話だった。本稿は**それを実際に何で作るか**を扱う。グラフの1つのノードは、現在のツールでは多くの場合「サブエージェント」として実装される。

注意点を先に述べる。サブエージェントの細かい仕様は製品のバージョンで変わりうる領域であり、本稿の記述には**公式ドキュメントに基づく部分と、解説動画のauto字幕からの聞き取りに基づく部分が混在する**。後者は「〜としている（聞き取り）」と明示するので、重要な判断に使う前には手元のバージョンのドキュメントで確認する必要がある。

## 公式が保証している範囲

Anthropic公式のClaude Code Docs「Agent SDK overview」は、Claude Codeを強力にしている要素はすべてSDKでも利用できると述べ、機能を列挙している（[Agent SDK overview](../sources/article-he-agent-sdk-overview.md)）。そこに含まれるのは次のようなものである。

- **Subagents** — 焦点を絞ったサブタスクのために**専門特化したエージェントを派生させる**機能
- **Permissions** — どのツールが自動実行され、どのツールが承認を必要とするかを制御する
- **Sessions** — 複数回のやり取りにわたってコンテキストを維持し、後から再開したり分岐させたりできる
- **Hooks** — エージェントのライフサイクルの重要な地点でカスタムコードを実行する
- **MCP** — Model Context Protocol経由で外部のツールやデータソースを接続する

同文書はまた、Agent SDKがClaude Codeを支えているのと同じツール群・エージェントループ・コンテキスト管理をPythonとTypeScriptでプログラム可能な形で提供するライブラリだとしている。つまり**サブエージェントは対話ツールの便利機能ではなく、プログラムから組み立てられる構成要素**である。グラフを自分で組む場合の土台がここにある。

## 定義の仕方: マークダウン1ファイル

以下は[サブエージェント完全ガイド前編の動画](../sources/video-ge-subagent-overview-basics.md)の説明に基づく（auto字幕からの聞き取り）。

同動画は、サブエージェントとは**メインセッションから独立して動作する、特定タスクに特化したエージェント**であるとし、定義方法はマークダウンファイルの先頭にフロントマターでエージェント名・説明・使用ツール・使用モデルなどを記述するシンプルな形式だとしている。主な設定項目として同動画が挙げているのは次のとおりである。

| 項目 | 説明（同動画による） |
|---|---|
| name（必須） | 小文字とハイフンによる一意な識別子 |
| description（必須） | Claudeが自動起動を判断する材料になるため特に重要 |
| model | 省略するとメインセッションから継承される |
| tools / disallowedTools | 許可リスト・拒否リスト。**両方指定した場合は拒否リストが優先される** |
| skills | 指定したスキル本文をコンテキストに読み込む。**メインで使っているスキルは自動継承されない** |
| mcpServers | 接続するMCPサーバーを指定する |
| hooks | エージェントのライフサイクルの節目でコマンドを実行する。公式ドキュメントの例として、読み取り専用DBクエリの許可や、書き込み・更新・削除系コマンドのブロックが挙げられている |
| memory | 永続メモリー。ユーザー・プロジェクト・ローカルの3スコープ |
| color | ターミナル表示色。書き込み系は赤、読み取り専用は青などリスクの可視化に使う |

**ツール設定を省略すると、MCPツールを含む全ツールを継承してしまう**ため明示指定を推奨する、というのが同動画の助言である（聞き取り）。これは実務上かなり重要で、「調査だけさせるつもりのサブエージェントが書き込みツールを持っている」という事故はここから起きる。colorでリスクを色分けするという運用は、その事故を目視で捕まえるための工夫といえる。

呼び出し方は4通りあるとしている。①descriptionに基づく自動判断、②自然言語での明示的な指示、③@メンションからの選択、④CLIフラグによるセッション全体での起動。descriptionに「use proactively」というキーワードを含めると自動起動されやすくなるテクニックがあるとも紹介している（聞き取り）。

実行モードには**フォアグラウンド**（完了までメインが待機し、都度権限確認が入る）と**バックグラウンド**（並行して別作業ができ、権限確認は事前にまとめて行う）の2つがあり、Ctrl+Bで切り替えられるとしている。サブエージェントは再開可能で、過去のセッション状態から続きを起動できるとも述べている（聞き取り）。

## コンテキストの独立性——何が渡り、何が渡らないか

サブエージェント設計で最も本質的なのはこの一点である。同動画は、サブエージェントは**メインセッションとは別の固有のコンテキストを持ち**、ツールアクセスや権限周りの設定もメインとは個別に設定できるとしている（聞き取り）。

そして、サブエージェントがメインから受け取る情報は次の5つに限られ、**メインの会話履歴は一切受け取らない**としている（聞き取り）。

1. エージェント定義
2. タスク指示
3. 作業ディレクトリ等の環境情報
4. skillsフィールドで指定したスキル内容
5. 永続メモリ

逆向きも同様で、サブエージェントでの中間処理（ファイル読み込みや途中経過）はメインには渡らず、**最終結果のみが返る**。この設計によりメインのコンテキスト寿命が延び、汚染も防げると説明している（聞き取り）。

この非対称性が、設計上2つの帰結を生む。

**帰結1: 前提は明示的に渡すしかない。** 「さっき話した仕様で」は通じない。必要な背景はタスク指示に書き下す必要がある。ここは[グラフの基本要素](./graph-primitives.md)で扱った「エッジは何を運ぶか」の問題そのもので、エッジの中身を書き忘れたノードは前提なしで動き出す。

**帰結2: コンテキストの節約が主目的になりうる。** 中間処理がメインに返らないということは、10万トークンの探索をさせてもメインには要約だけが返るということである。分業の動機は「速さ」や「賢さ」だけでなく、**メインのコンテキストを汚さないこと**でもある。

## 分ける動機: 品質と速さ

同動画は、サブエージェントに分ける動機として品質面と速度面の2つの実例を挙げている（聞き取り）。

- **品質: 役割分離による自己評価バイアスの回避** — Anthropic公式エンジニアリングブログを引用し、プランナー・ジェネレーター・エバリエイターの3役割に分離した方が単一エージェントより高品質な出力を生むと報告されているとしている。単一エージェントで品質が頭打ちになる最大の理由として、自分の成果物を採点する際に一貫して甘めに評価してしまう自己評価バイアスを挙げ、生成役と評価役を分離することでこれを回避できると説明している。この3役割は、[役割分担とオーケストレーション](./roles-and-orchestration.md)で扱ったManager/Worker/Verifierの三役分担と対応関係にある——プランナーがマネージャー（配る役）、ジェネレーターがワーカー（作る役）、エバリエイターがベリファイア（通す役）に相当し、役割名は違っても「作る役と通す役を同一人物にしない」という設計原則は同じである
- **速さ: 並列分割による実測の短縮例** — 海外のブログコミュニティで紹介された事例として、テストスイートを4つのサブエージェントに分割して並列実行した結果、従来8分かかっていた作業が3分未満に短縮されたという報告があるとしている

## 3つの制約

同動画が挙げる制約は次の3つである（いずれも聞き取り）。

- **ネストできない** — あるサブエージェントが別のサブエージェントを生成することはできない仕様であり、これは無限にサブエージェントが生成されることを防ぐための設計上の制約だとしている
- **横のつながりがない** — サブエージェント間でメインの会話履歴や他のサブエージェントの出力は共有されない
- **同一ファイルへの並列編集は競合する** — 注意が必要

**ネスト不可は、グラフの形を直接制約する。** 深い階層のツリーは組めず、実質的に「メイン → サブエージェント群」という2階層に収まる。3階層以上の分業をしたければ、メイン側が段階を分けて呼び直すか、[つなぎ方の型カタログ](./workflow-patterns-catalog.md)で扱ったダイナミックワークフローのような上位の編成機構に任せることになる。制約と聞くと不便に思えるが、無限増殖を止める安全装置でもある——単純なクエリに50個のサブエージェントを生成してしまった事例（[失敗の分類とデバッグ](./failure-taxonomy-and-debugging.md)参照）を思えば、上限のある構造にはそれなりの理がある。

なお、同動画は前掲の「両方指定した場合は拒否リストが優先される」「ネストできない」といった仕様をauto字幕経由で伝えており、パーミッションモードの種類やCLIフラグ名など一部は字幕の誤変換で正確な語が特定できていないと台帳側で注記されている。実行制御系の設定としては、パーミッションモード（プラン・アクセプトエディット等の6種類、聞き取り）、バックグラウンド実行（デフォルトtrue）、アイソレーション、エフォート（推論努力の度合い、Opus使用時のみ選択可能）が挙げられている。仕様の細部は公式ドキュメントで確認する前提で読むべき箇所である。

## サブエージェントとエージェントチームの使い分け

同動画は、Claude Codeの機能を「実行主体」「能力」「ルール・環境」の3つに整理する私見を示し、メインセッション・サブエージェント・エージェントチームを実行主体に位置付けている（聞き取り）。そのうえで、サブエージェントとエージェントチームの違いを次の4点で説明している（聞き取り）。

- **セッション**: サブエージェントは同一セッション内で動くが、エージェントチームは別セッションで動く
- **結果の返り方**: サブエージェントの結果はメインに返るが、エージェントチームの結果は返らない
- **情報の流れ**: サブエージェントは一方通行（メインからの指示のみ）だが、エージェントチームは双方向
- **コスト**: エージェントチームの方が圧倒的に高い

同動画はこれを踏まえ、よほどのことがない限り基本的にはサブエージェントを使う方がよいという私見を述べている。

## 使うべき場面・避けるべき場面

同動画はAnthropic公式ブログが示す基準として、**10以上のファイルを探索する必要がある時・3つ以上の独立した作業がある時・偏りのないセカンドオピニオンが必要な時**にサブエージェントの利用が適していると紹介している（聞き取り）。逆にアンチパターンとして、**順序が重要な作業**（AをやってからB）、**同一ファイルへの並列編集**、**オーバーヘッドが利点を上回る小さなタスク**を挙げている。

この整理は、[にゃんたのAIチャンネルの動画](../sources/video-ge-subagent-when-to-use.md)が挙げる3つの実践的な活用法とも重なる（聞き取り）。①タスクを並列分割できる調査・作業、②忖度を避けたい客観評価、③自動的な作成検証ループ、の3つである。同動画は、シングルエージェントで十分な精度が出るタスクにマルチエージェントを使うと**コストが上がり精度も下がりうる**と総括している。定量的な目安（単体精度45%という損益分岐点）は[マルチエージェント化の損益分岐点](./multi-agent-break-even.md)を参照。

3つの推奨場面のうち②③はいずれも「評価役を分ける」話であり、これはコンテキストが独立していることの直接の帰結である。**自分の作業履歴を知らない相手だからこそ、率直な評価が返る。** 詳しくは[検証をゲートにする](./verification-gates-and-evidence.md)で扱う。

## 実装前のチェックリスト

1. **ツールを明示指定したか** — 省略するとMCPを含む全ツールを継承する（聞き取り）。読み取り専用で足りるなら書き込みは渡さない
2. **descriptionは自動起動の判断に耐えるか** — ここが曖昧だと、呼ばれるべき時に呼ばれず、呼ばれるべきでない時に呼ばれる
3. **必要な前提をタスク指示に書き下したか** — 会話履歴は渡らない
4. **skillsを明示指定したか** — メインで使っているスキルは自動継承されない（聞き取り）
5. **同じファイルを触る並列がないか** — あるなら担当範囲を分割するか、[所有権の設計](./handoffs-and-ownership.md)で扱ったロック方式を採る
6. **そもそも分ける必要があるか** — 小さなタスクではオーバーヘッドが利点を上回る
