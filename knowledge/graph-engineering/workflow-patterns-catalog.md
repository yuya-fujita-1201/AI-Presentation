# つなぎ方の型カタログ

[グラフの基本要素](./graph-primitives.md)でノードとエッジの語彙を押さえ、[ループかグラフか](./loop-vs-graph-decision.md)でグラフ化すると決めた次に来るのは、どうつなぐかという問いである。つなぎ方はすでに複数の型として整理され、名前が付いている。

本稿は、その型を2つの系統で並べる。1つはAnthropicが公式に公開した**5つのワークフローパターン**（設計者が自分で組む型）、もう1つはClaude Codeのダイナミックワークフローが持つとされる**6つの編成型**（ツールが自動生成する型）である。最後に、型を人が選ぶのではなく機械に最適化させるという研究の方向も紹介する。

なお、Anthropicの5パターンは[役割分担とオーケストレーション](./roles-and-orchestration.md)でも「2023年当時はなぜ実用化しなかったか」という歴史的文脈で名前だけ触れているが、本稿は各型の中身と選び方に踏み込む。

## 前提: WorkflowとAgentは別物である

型の話に入る前に、用語を1つ整理しておく必要がある。Anthropic公式記事「Building Effective AI Agents」は、WorkflowとAgentを定義で区別している（[Anthropic公式記事](../sources/article-ge-anthropic-building-effective-agents.md)）。

> Workflows are systems where LLMs and tools are orchestrated through predefined code paths, while agents are systems where LLMs dynamically direct their own processes and tool usage.

つまり**Workflowは「あらかじめ決められたコードの経路」でLLMとツールが動かされるシステム**、**Agentは「LLM自身が自分の手順とツール使用を動的に決め続ける」システム**である。同記事は使い分けの指針として、Workflowは予測可能性と一貫性を提供し、Agentは柔軟性とモデル主導の意思決定が大規模に必要な場合のより良い選択肢だとしている。

この区別が効いてくるのは、グラフを描いたときに「この線は誰が引いたのか」が問われる場面である。設計者が事前に引いた線ならWorkflow、実行中にモデルが引いた線ならAgentであり、後者の方が柔軟だが、どこを通ったかを後から追いにくい。

同記事はまた、エージェント的システムの基本的な構築ブロックは**検索・ツール・メモリなどで拡張されたLLM（augmented LLM）**であるとし、WorkflowもAgentもこの土台の上に組み立てられると位置づけている。ノードの中身は「素のLLM呼び出し」ではなく「道具を持ったLLM」だ、ということである。

## Anthropicの5つのワークフローパターン

同記事が挙げるWorkflowの構築パターンは5種類である。以下、各型の内容と公式記事に挙げられた適用例を示す。

| # | 型 | 何をするか | 公式記事の適用例 |
|---|---|---|---|
| 1 | **Prompt chaining** | タスクを固定順のサブタスクに分解し、各LLM呼び出しが前段の出力を処理する | マーケティングコピーを生成してから別言語へ翻訳する／アウトライン作成→基準確認→本文執筆 |
| 2 | **Routing** | 入力を分類し、特化した後続タスクへ振り分ける | 顧客問い合わせを一般質問・払い戻し・技術サポートに分類する／簡単な質問はHaiku、難しい質問はSonnetへ回してコストと速度を最適化する |
| 3 | **Parallelization** | 独立サブタスクを並行実行する(Sectioning)、または同一タスクを複数回実行して多様な出力を得る(Voting) | コードの脆弱性レビューを複数プロンプトで並行検証する／コンテンツの適切性を複数インスタンスで投票判定する |
| 4 | **Orchestrator-workers** | 中央のLLMが動的にタスクを分解し、複数のワーカーLLMへ委譲して結果を統合する | 複数ファイルにまたがるコーディング変更。必要なサブタスクが事前に予測できない複雑なタスクに適する |
| 5 | **Evaluator-optimizer** | 一方のLLMが応答を生成し、もう一方が評価とフィードバックを返すループ | 文学翻訳でのニュアンス改善。評価基準が明確で、反復的な改善が測定可能な価値を生む場合に有効 |

型を眺めると、**2と4はどちらも「上位が振り分ける」型だが、決定的な違いがある**ことに気づく。Routingは行き先の選択肢が事前に決まっており分類するだけだが、Orchestrator-workersはサブタスクの中身自体を実行時に作り出す。事前に選択肢を列挙できるならRouting、できないならOrchestrator-workersという分かれ方になる。

同様に、**3(Parallelization)と5(Evaluator-optimizer)は「複数の目で見る」点は同じでも、時間軸が違う**。Parallelizationは同時に見る（横に広げる）、Evaluator-optimizerは順に見て直す（縦に回す）。前者は速さ、後者は品質を買う型である。

### 型よりも先に来る原則: 最も単純な解から始める

Anthropicは記事の冒頭で、自社が観察した中で最も成功した実装は複雑なフレームワークを使っていたのではなく、**シンプルで組み合わせ可能なパターンで構築されていた**と述べており、これを記事全体の基調としている。実装上の推奨としても「find the simplest solution possible, and only increase complexity when needed（可能な限り最も単純な解を見つけ、必要になったときだけ複雑さを増やす）」という原則を掲げ、フレームワークは開発初速には有効だが、本番段階では抽象化層を減らして基礎コンポーネントで組み直すことを躊躇しないよう述べている。

型カタログを読むと全部使いたくなるが、記事自身が最初に釘を刺しているのは「使わない」という選択肢の方である。この点は[ループかグラフか](./loop-vs-graph-decision.md)の「困り事が先、道具は後」という原則と同じことを、公式ドキュメント側から言っているものと読める。

あわせて同記事は、ツール設計（Agent-Computer Interface）にプロンプト全体と同程度の労力を割くべきだとも指摘している。ノード間の線をどう引くかと同じくらい、ノードが握る道具の使い勝手が結果を左右するということである。

## Claude Codeのダイナミックワークフロー: 6つの編成型

上の5パターンが「設計者が組む型」だとすれば、それをツール側が自動生成する方向の機能も登場している。Claude Codeの「ダイナミックワークフロー」がそれにあたり、[みにこーへいのAI活用チャンネルの動画](../sources/video-ge-dynamic-workflows-six-patterns.md)は、これをタスクごとに台本を書いてサブエージェントの編成を自動生成する仕組みだと説明し、6つの型を紹介している。ただし同動画は99秒という短い尺で各型を一文ずつ紹介する速報的な構成であり、**内容はいずれも自動字幕からの聞き取りに基づく**（台帳側でも一部の型名は誤変換が多いと注記されている）。以下は同動画の説明である。

1. **分類して振り分け** — まず分類エージェントがタスクの種類を見極め、それぞれ最適なルートに流す型だとしている（聞き取り）。上表のRoutingに対応する
2. **ファンアウト** — タスクを分割して並列で処理し、最後に結果を1つに統合する型で、「大規模な調査の定番」だとしている（聞き取り）。Parallelizationに対応する
3. **敵対的検証** — 出てきた答えを反論役のエージェントが本気で潰しにかかり、それでも生き残った結論だけを採用する型だとしている（聞き取り。台帳では「反薬」等の誤変換から文脈で「反論」と判断したと注記されている）
4. **生成して篩い落とす** — 案を多めに作り、評価基準で絞り込む型で、一発勝負より質が安定するとしている（聞き取り）
5. **トーナメント** — 複数の案を1対1で比較し、勝ち抜き戦で絞り込む型。同動画は、絶対評価が苦手なAIでも比較形式であればかなり正確に評価できると説明している（聞き取り）
6. **終わるまで回す** — 新しい発見がゼロになるまで探索を回し続ける型で、バグ調査の取りこぼしを潰す用途に向いているとしている（聞き取り）

ここで注目したいのは**3〜6の4つが、すべて「評価の型」だという点**である。5パターン側で評価に関わるのはEvaluator-optimizerの1つだけだったのに対し、ダイナミックワークフロー側は評価の作法を4通りに分けている。特に5(トーナメント)が言う「絶対評価より相対評価の方が精度が出る」という性質は、点数を付けさせるのではなく2案を比べさせるという実務上の工夫につながる。

### 呼び出し方とトークン予算

同動画は、6つの型の紹介に続けて使い方にも触れている（いずれも聞き取り）。

- **起動方法**: プロンプトに「ウルトラコード」と書くだけだとしている。ディープリサーチ用途では検索を並列展開し、出典まで検証した引用付きレポートが得られると説明している
- **出典検証の構成**: レポートの検証を行う場合は、主張を全て洗い出した上で1つの主張につき1エージェントが出典をチェックし、さらに別の検証役のエージェントが出典の品質そのものを見張る構成になっていると紹介している
- **編成の保存**: 気に入ったエージェント編成は「S」で保存し、スキルとしてチームに配布できるとしている
- **トークン予算**: 「1万トークンで」と頼むだけで上限がかかると説明している

なお、ダイナミックワークフローという機能自体はAnthropicの公式ドキュメント側にも登場する。Agent SDKの入門文書は、次のステップとして案内するリソースの中に「Claude Codeチームがダイナミックワークフローを使ってサブエージェントを大規模にオーケストレーションする手法を解説した『Agent harness design』というブログ記事」を挙げている（[Agent SDK overview](../sources/article-he-agent-sdk-overview.md)）。また公式のベストプラクティス文書も、チェックの強制力を高める4段階目の手段として「検証用サブエージェントや、自らの発見内容を検証するダイナミックワークフロー」を挙げている（[Best practices for Claude Code](../sources/article-le-claude-code-best-practices.md)）。**機能の存在と用途は公式側で裏が取れるが、6つの型という数え方と個々の型名は上記動画の聞き取りに依存している**、という確度の差は押さえておきたい。

## 型を人が選ぶのをやめる方向: トポロジーの自動最適化

ここまでは「人が型を選ぶ」話だった。研究の側には、その選択自体を最適化問題として解こうという方向がある。ICML 2024に採録されたGPTSwarmの論文は、単一エージェントもエージェント群（スワーム）も**有向非巡回グラフ（DAG）として統一的に表現**し、ノードのプロンプトとエッジ（通信トポロジー）の両方を自動最適化できると主張している（[GPTSwarm論文](../sources/article-ge-gptswarm-optimizable-graphs.md)）。

- 単一エージェントをDAG `G=(N,E,F,o)` として定義する。ノードNはLLM推論・ツール使用・関数呼び出しなどの操作、エッジEはノード間の情報フローを表し、入力に対してトポロジカルソート順に各ノードを実行して、先行ノードの出力を後続ノードの文脈として使うとしている
- 最適化は2段階からなる。**エッジ最適化**では各潜在エッジに実数パラメータθ∈[0,1]を割り当て、確率θでエッジを含めるサンプリングを行い、REINFORCEアルゴリズムで勾配推定してAdamで更新する。**ノード最適化**では各ノードの入出力ペアを履歴に蓄積し、OPRO等の既存手法でプロンプトを反復改善するとしている
- 評価では、GAIAベンチマークでGPT-4-Turbo単体の平均9.70%、AutoGPTの4.85%に対し、GPTSwarm（7×Tree of Thought構成）が平均18.45%を記録したと報告している。HumanEval（164問）ではノード最適化なしの0.76からオンライン学習で0.88まで改善したとしている

実務上ここから持ち帰るべきなのは、最適化アルゴリズムそのものよりも**「エッジは設計者の主観で引く固定物ではなく、良し悪しを測って調整できる変数だ」という見方**である。どのノードとどのノードをつなぐべきかを議論だけで決めるのではなく、つないだ場合とつながない場合を実際に測って比べる余地がある、ということになる。ただしこの数値はいずれも論文が設定したベンチマーク内の比較であり、手元の業務でそのまま再現する保証はない。ベンチマーク上の改善率をそのまま持ち出す危険については[リスクと歯止め](./risks-and-safeguards.md)の「独り歩きしがちな数字への注意」を参照。

## 型の選び方——まとめ

以上を実務の判断順に並べ直すと、次のようになる。

1. **そもそも型が要るか**を先に決める。Anthropic公式の「最も単純な解から始める」という原則が最初のゲートになる
2. **サブタスクを事前に列挙できるか**で分岐する。列挙できるなら型1〜3、実行時にしか決まらないなら型4 Orchestrator-workers。ただし**型4も公式の分類ではWorkflowに属する**——中央のLLMが分解の中身を動的に決めるだけで、「分解して委譲し統合する」という経路自体はコード側が定義しているためである。冒頭に引いた定義でいうAgentは、LLM自身が手順とツール使用を決め続ける系を指し、ここで挙げた5つの型のいずれとも別の区分にあたる
3. **買いたいものが速さか品質か**で分岐する。速さならParallelization／ファンアウト、品質ならEvaluator-optimizer／敵対的検証・篩い落とし・トーナメント
4. **評価させるときは絶対評価より比較**を検討する。点数付けよりトーナメント形式の方が精度が出やすいとされている（聞き取り）

なお、ここで挙げた評価系の型がなぜそこまで必要とされるのか——作った本人に採点させると甘くなるという性質については[検証レイヤーの設計](./verification-and-testing.md)を参照。
