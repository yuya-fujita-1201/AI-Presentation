# 最終回答を誰が所有するか

エージェントを2つ以上つなぐ場合、**ユーザーに返る最終的な回答を誰が書くか**という設計判断が必要になる。

これは些細な実装の違いに見えて、実際にはシステムの性格を決める。OpenAI公式の「Orchestration and handoffs」は、マルチエージェントワークフローは専門家が仕事の異なる部分を所有すべき場合に有用だとしたうえで、各分岐点で**「最終的なユーザー向け回答の所有権を誰が持つか」を決める設計判断こそがオーケストレーションの本質**だと述べている（[OpenAI公式記事](../sources/article-ge-openai-orchestration-handoffs.md)）。

[役割分担とオーケストレーション](./roles-and-orchestration.md)では「誰が何をやるか」を扱った。本稿はその一段手前にある「**誰が最後に喋るか**」を扱う。役割が同じでも、この一点が違えば別の設計になる。

## 2つのパターン: 引き渡すか、握り続けるか

同記事は、所有権の所在という軸から2つのパターンを対比している。

### Handoffs: 所有権そのものを引き渡す

Handoffsパターンでは、トリアージ役のエージェントが特化したエージェントへ**会話の所有権そのものを引き渡す**。実装例として `Agent.create({ name: "Triage agent", handoffs: [billingAgent, handoff(refundAgent)] })` のような形が示されており、引き渡した後は制御フローも応答の所有権もスペシャリスト側へ移る。同記事は、**専門家が次の応答を所有すべき場合にHandoffsが最も明確に適合する**としている。

窓口が「これは返金の話ですね」と判断して返金担当に代わり、以後は返金担当がユーザーと直接やり取りする——電話の取り次ぎに近い構図である。

### Agents as Tools（Managerパターン）: 所有権はマネージャーに残る

対照的にAgents as Tools（Managerパターン）では、中央のマネージャーエージェントが会話の制御を保持したまま、専門化されたエージェントを**ツールとして呼び出し**、その結果を統合して最終回答を自ら合成する。実装例は `main_agent = Agent(name: "Research assistant", tools: [summarizer.as_tool(tool_name: "summarize_text")])` のように、サブエージェントを `.as_tool()` でラップする形で示されている。同記事は、この方式は**マネージャーが最終回答を合成すべき場合に通常より適したフィット**だとしている。

こちらは取り次ぎではなく、担当者が席を立たずに専門部署へ内線で問い合わせ、返ってきた答えを自分の言葉でユーザーに返す構図にあたる。

### 比較

| | Handoffs | Agents as Tools（Manager） |
|---|---|---|
| 制御フロー | スペシャリストへ移る | 常にマネージャーに残る |
| 応答の所有権 | スペシャリストへ移る | 常にマネージャーに残る |
| 適合する場面 | 専門家が次の応答を所有すべき場合 | マネージャーが最終回答を合成すべき場合 |
| ユーザーから見た相手 | 途中で代わる | 最後まで同じ |

## 実例はどちら側か

公開されている構成を、この軸で読み直すと性格がはっきりする。

**Anthropicの研究システムはマネージャー型である。** 同社の記事によれば、処理フローはユーザークエリ→リードエージェント→複数のサブエージェント→結果統合→引用エージェントによる最終処理という順に進む（[Anthropic公式記事](../sources/article-ge-anthropic-multi-agent-research-system.md)）。サブエージェントはリードに結果を返すのであって、ユーザーに直接返答するわけではない。リードエージェント（Claude Opus 4）が戦略を立て、サブエージェント（Claude Sonnet 4）が並列に探索し、統合はリード側で行われる。所有権は最後までリードにある。同記事はまた、コンテキストウィンドウの超過に備え、リードエージェントが立てた計画をメモリ層に保存する仕組みも実装していると述べている——所有権を1箇所に集めるマネージャー型では、その1箇所が長時間の委任に耐えられるよう状態を持たせておく必要がある、という実装上の注意点になる。

**Claude Codeのサブエージェント機構も、同じくマネージャー型として説明されている。** [サブエージェント完全ガイド前編の動画](../sources/video-ge-subagent-overview-basics.md)は、サブエージェントでの中間処理（ファイル読み込みや途中経過）はメインセッションには渡らず、**最終結果のみが返る**設計だとしている（聞き取り）。ユーザーが対話しているのは常にメインセッションであり、サブエージェントが表に出てくることはない。

こう並べると、実運用で広く使われているのは圧倒的にマネージャー型だとわかる。Handoffsは、ユーザーとの対話が継続する顧客サポートのようなドメインで自然に適合するパターンだと考えるのが実態に近い。

## 所有権はもう1種類ある: 作業対象の所有権

ここまでは「回答の所有権」の話だった。並列度が上がると、もう1種類の所有権が問題になる。**同じファイルを誰が触ってよいか**である。

Anthropicが16個のClaudeインスタンスで約2週間・約2,000セッションにわたりRust製Cコンパイラを開発した実験では、各エージェントが `current_tasks/` ディレクトリ内のテキストファイルで**ロックを取得してタスクを担当する**方式が採られた（[Anthropic公式記事](../sources/article-ge-anthropic-building-c-compiler.md)）。同記事は競合回避について次のように説明している。

> If two agents try to claim the same task, git's synchronization forces the second agent to pick a different one.

2つのエージェントが同じタスクを主張した場合、Gitの同期機構そのものが2番目のエージェントに別のタスクを選ばせる、という設計である。同期は「upstreamからpull → 他エージェントの変更をマージ → 変更をpush → ロックを削除」という手順を踏むとしている。つまり**分散システムの排他制御をそのまま持ち込んでいる**。

この設計が必要になる理由は、前掲の動画も裏側から説明している。同動画は、サブエージェント間でメインの会話履歴や他のサブエージェントの出力は共有されないため、必要な情報はタスク指示に明示的に含める必要があるとし、**同一ファイルへの並列編集は競合が発生しうる**ため注意が必要だとしている（聞き取り）。互いの作業が見えない者同士を同じ対象に向けたら壊れる、という当たり前の帰結である。

**2種類の所有権は独立して設計する必要がある。** 回答の所有権をマネージャーが握っていても、作業対象の所有権を決めていなければ並列ワーカーは衝突する。逆にファイルロックが完璧でも、誰が最終回答を書くか決まっていなければ出力は継ぎ接ぎになる。

## 分けるか分けないかの判断

所有権の設計以前に、そもそも専門家を追加すべきかという判断がある。同じOpenAI公式記事は、専門家を追加してよいのは4条件のいずれかを実質的に改善する場合に限るとし、結論として「Start with one agent whenever you can（可能な限り、まずは単一エージェントから始める）」を示している。この4条件の内訳と、性能面から見た損益分岐点については[マルチエージェント化の損益分岐点](./multi-agent-break-even.md)で詳しく扱っている。

追加の指針として同記事は、各スペシャリストは**狭い職務スコープ**を持つべきこと、`handoff_description` は簡潔かつ具体的に書くべきこと、**次の分岐が本当に異なる指示・ツール・ポリシーを必要とする場合にのみ**エージェントを分割すべきことを挙げている。`handoff_description` が重要なのは、それがトリアージ役の判断材料そのものだからである。渡し先の説明が曖昧なら、取り次ぎ先の選択が曖昧になる。

## 実務でのチェック

設計を始める前に、次の4点を先に決めておくと迷いが減る。

1. **最後に喋るのは誰か** — マネージャーが合成するのか、専門家が直接返すのか。ここが決まらないまま実装すると、統合処理の置き場所が定まらない
2. **渡すときに何を渡すか** — サブエージェントはメインの会話履歴を受け取らない。必要な前提はタスク指示に明示的に含める
3. **同じ対象を触る可能性があるか** — あるなら排他制御を設計する。ファイルロックか、担当範囲の事前分割か
4. **その分割は4条件のどれを改善するか** — どれにも当たらないなら、分けない

なお、所有権をマネージャーに集めた場合に固有の弱点がある。Anthropicは同記事で、現状の実行フローは同期実行（リードエージェントがサブエージェント群の完了を待ってから次に進む）であり、これが**情報フローのボトルネックを作る**という課題があるため将来的な非同期化が検討されていると述べている。ただし非同期化は結果の調整や状態の一貫性を複雑にする点が課題だとしている。握り続けることには、待ち時間という対価がある。
