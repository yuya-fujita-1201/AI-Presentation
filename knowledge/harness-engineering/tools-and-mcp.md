# 道具の設計——組み込みツール・MCP・WebMCP・スキル

ここからハーネスの4要素の具体に降りる。最初は「道具」——**エージェントに何を実行させ、何に接続させるか**である。[11責務](./harness-responsibilities-and-ladder.md)でいえばツールアクセスにあたる。

チャット型AIしか使ったことがないと、AIの性能はモデルの賢さで決まると感じやすい。しかし業務でAIに何ができるかを実際に左右するのは、**そのAIが手として何を持っているか**である。どれだけ賢くても、社内の見積書ファイルを開けなければ見積書は直せない。この章では道具を4つの層に分けて整理する。

| 層 | 何をするものか | 誰が用意するか |
|---|---|---|
| 組み込みツール | ファイル操作・コマンド実行・Web検索 | AIツールの提供元 |
| MCP | 外部サービス・データソースへの接続 | 接続先の提供元、または自分 |
| WebMCP | Webサイト側がAI向けの操作口を公開する | サイト運営者 |
| スキル | 繰り返し作業の手順を定型化する | 使う側（社内の担当者） |

## 層1: 組み込みツール——手の基本セット

[Anthropic公式の「Agent SDK overview」](../sources/article-he-agent-sdk-overview.md)は、そもそもエージェントを次のように定義している。

> 引用: 「An agent is an application that completes a task by planning its own steps and calling tools that read files, run commands, or edit code.」

**自ら手順を計画し、ファイルを読み・コマンドを実行し・コードを編集するツールを呼び出してタスクを完了させるアプリケーション**、というのが定義である。ここで注目したいのは、定義の中に最初からツールが組み込まれていることだ。ツールを呼べないものはこの定義ではエージェントではない。同文書はAgent SDKの提供機能として、ファイルの読み取り・書き込み・編集、コマンド実行、Web検索を行う「Built-in tools（組み込みツール）」を挙げている。

なぜこの基本セットがそれほど効くのか。[PIVOTの体験企画動画](../sources/video-he-claude-code-4hour-agent.md)は、Claude Codeが一気に注目を集めた最大の理由は**パソコンの中に住み込んだ上でファイルを探し出せる点**にあるとしている。同動画はさらに、ホワイトカラーの仕事はWord・PDF・Excel・CSV・パワーポイント・画像・動画・設定ファイルなど結局のところほとんどがファイルの編集であり、ファイル操作能力の高いAIこそが最強のAIになり得ると説明している（いずれもauto字幕からの聞き取り）。

同動画は、人間が日本語で「フォルダーを作って」と依頼すると裏側で `mkdir` コマンドが実行される、という形でその仕組みを解説している。またクラウド上のチャット型AIとの違いとして、それらはパソコンのファイルの中身を直接読みに行けないため資料のアップロードが都度必要になり、ローカルデータを踏まえたビューアー作成のような操作もできないと指摘している。つまり**同じモデルでも、手の届く範囲が違えばできる仕事が違う**。これは[why-harness-matters.md](./why-harness-matters.md)で見た「環境が公開している内容（C_environment）」の話そのものである。

## 層2: MCP——外部サービスにつなぐ

組み込みツールは自分のパソコンの中に閉じている。社内システム、カレンダー、チケット管理、データベースといった外部に手を伸ばすための仕組みが**MCP（Model Context Protocol）**である。前掲のAgent SDK文書は、MCPを「外部のツールやデータソースを接続する」機能として挙げている。

イメージしやすい例として、前掲の体験企画動画では、Claude CodeとGoogleカレンダーをMCPと呼ばれる仕組みを通じて連携させ、その日のスケジュールを読み上げさせる様子が実演されている（auto字幕からの聞き取り）。

MCPの設計上の意味は、**接続を1件ずつの作り込みではなく共通の規格にしたこと**にある。接続先ごとに専用の実装を書いていては、社内システムの数だけ開発案件が生まれる。共通プロトコルであれば、接続先が対応した時点でどのエージェントからも同じ形で使える。SIの文脈でいえば、個別インターフェース開発をやめて標準I/Fに寄せる話に近い。

## 層3: WebMCP——サイト側がAI向けの窓口を用意する

MCPが「エージェント側から外部につなぐ」仕組みだとすると、逆向きの発想が**WebMCP**である。[Cloudflareの提供開始を扱った解説動画](../sources/video-he-webmcp-cloudflare-guide.md)は、WebMCPを**サイトにおけるAI専用の窓口であり、AIが訪れたらまず操作可能なメニュー表を渡す仕組み**だとしている（auto字幕からの聞き取り。同動画独自の言い換えを含む）。

同動画が挙げている課題設定は分かりやすい。従来のAIによるブラウザ操作は、画面を目視しながらボタンの位置をその都度推測してクリックする方式であり、処理が遅く間違いも起きやすかったとしている。レストランの比喩では、WebMCPがない状態は「メニューを見ずに店内をうろうろする客」、ある状態は「メニュー表を渡され正確に注文できる客」にあたると説明されている。

効果について同動画は、処理時間が約8割カットされる点と操作の正確さが1〜2割アップする点を挙げている（auto字幕からの聞き取り。**測定条件や出典は動画内で示されておらず、本教材でも確認できていないため、数値は目安としても扱わないほうがよい**）。方向性——画面を見て推測するより、構造化された操作口を叩くほうが速く確実になる——は理解の助けになるが、数値そのものを社内資料に転記するのは避けるべきである。

サイト運営者側にも意味がある。同動画は、AIエージェントによる無断アクセスではなくMCP経由の正式な窓口としてアクセスをデータで把握できるようになる点をメリットとして挙げている。エージェント時代における「AI向けの受付を作り、そこを通ってもらう」という発想である。導入面では、Cloudflareの管理画面でWebMCP（β）を有効化しツールパックを選ぶだけでコードの書き換えは不要だったとし、配信者自身はエンジニアではないが管理画面の操作だけで有効化できたと述べている。なおWebMCPはGoogleとMicrosoftが標準化を進めている新しい規格で現時点ではベータ版の位置づけだとしており、**本番業務の前提に置く段階ではない**と読むのが妥当だろう。

## 層4: スキル——手順を道具にする

最後の層は少し性質が違う。ツールが「手」だとすれば、スキルは**その手をどう動かすかの手順書**である。前掲の体験企画動画は、プログラムが人間からパソコンへの指示書であるのに対し、**スキルはAIに対して人間が作る業務マニュアルに相当し、繰り返し作業を同じクオリティで実行できるようにするもの**だと説明している（auto字幕からの聞き取り）。同動画では、週21時間かかっていた情報収集を10分程度に短縮し得るニュース収集スキルを作る過程が紹介されている。

面白いのは、この層3と層4が接続する使い方である。前掲のWebMCP解説動画は、自作のAIエージェントスキルをWebサイト上に公開してWebMCP化することで、URLをコピー&ペーストするだけで誰でもスキルをセットアップできる状態を作れたと述べている。メリットとして、スキルを更新すればサイト側の更新だけで接続している全員に反映される点と、ローカルファイル配布に比べセットアップの難易度が大きく下がる点を挙げ、社内展開の例として**AIに詳しい担当者がスキルを作り込み、秘密鍵付きURLとして社内メンバーにのみ共有する**運用を想定できるとしている（auto字幕からの聞き取り）。

社内でAI活用を広げるときの典型的な詰まりどころ——「作った人しか使えない」「配ったが誰も更新に追随できない」——に対する、道具の側からの答えになっている点は押さえておきたい。

## 道具設計の3原則

層を並べたところで、設計する側の判断基準を整理しておく。

**1. 道具を増やすことは、事故の面積を増やすことでもある。**
ファイルを書き換えられる手は、間違ったファイルを壊せる手でもある。外部に接続できる口は、社外に情報を出せる口でもある。したがって道具の設計は必ず[権限の設計](./permissions-design.md)とセットで行う。「何ができるか」だけを決めて「何をさせないか」を決めない道具追加は、ハーネスの整備ではなく単なるリスク追加になる。

**2. 重要な操作には、道具の側に承認を埋め込む。**
前掲のWebMCP解説動画は、購入など重要な操作についても、AIが操作を準備した上で**最終的に人間が画面で確認・承認してから実行する**フローを設定できるとしている。ツールを提供する側が「準備までは自動、実行は人間」という切れ目をあらかじめ用意しておく設計は、利用側の設定に頼るより堅い。

**3. 人間が担う部分とAIに任せる部分は、人間の知識で切り分ける。**
前掲の体験企画動画は、Claude Codeが最初に提示した実行計画をそのまま採用するのではなく「AIに任せすぎない」ことが重要であり、人間が担うべき部分とAIに任せる部分を人間の知識で切り分けることがコツだとしている（auto字幕からの聞き取り）。道具を渡す前に、業務のどこを渡すのかを人間側が決めておく必要がある、という指摘である。

## まとめ

- エージェントの定義そのものにツール呼び出しが含まれている。手を持たないAIにできる仕事は、チャットの範囲を出ない
- 道具は4層で捉える。組み込みツール（手の基本セット）／MCP（外部への接続）／WebMCP（サイト側が用意する受付）／スキル（手順の定型化）
- ローカルファイルに直接触れるかどうかという環境差が、同じモデルでもできる仕事を大きく変える
- WebMCPは標準化が進行中のベータ段階であり、効果として語られる数値は出典が確認できない。方向性の理解にとどめる
- 道具の追加は必ず権限設計とセットにする。重要操作は道具の側に人間の承認を埋め込む
