# プロジェクトメモリとルールの設計——CLAUDE.mdを「長期記憶」として設計する

ハーネスの4要素——道具・制限・権限・ルール——のうち、[道具](./tools-and-mcp.md)・[権限](./permissions-design.md)・[制限](./sandbox-and-isolation.md)を見てきた。最後が**ルール**である。[keitoaiweb動画](../sources/video-pe-five-engineering-stages.md)はこれを「毎回読み込むべきコンテキスト」と説明し、Claude CodeにおけるCLAUDE.mdやメモリの自動読み込みを実例として挙げている（auto字幕からの聞き取り）。

ここまでの3要素が「何ができるか／できないか」を決めるものだったのに対し、ルールは**「何を知った状態で作業を始めるか」**を決める。エージェントを新しくチームに入った人だと思えば、道具はアカウント発行、権限はアクセス権付与、制限は入室できない部屋の設定、そしてルールは**着任初日に渡す引き継ぎ資料**にあたる。

## 論文における位置づけ——プロジェクトメモリという責務

[ハーネスエンジニアリングの論文](../sources/article-he-harness-engineering-paper.md)は、この要素を11責務のひとつ「プロジェクトメモリ（project memory）」として明示している。ハーネスの定義そのものにも組み込まれている。

> 引用: 「An AI Harness Engineering is a runtime substrate surrounding a foundation-model software agent that manages context, tools, **project memory**, task state, observability, failure attribution, verification, permissions, and maintenance state, so that latent model coding capability becomes auditable software-engineering behavior.」（強調は引用者）

なぜこれが必要なのか。同論文の議論が、本ファイル全体の理由づけになっている。同論文は、**人間の開発者が社会化・ドキュメント・経験を通じて獲得するこれらの構成要素は、モデルの呼び出しに対して自由には利用可能ではない**と述べる。それらは明示的に公開・構造化・トレースされる必要があり、そうでない場合エージェントは即興で対処するか、人間にギャップを埋めるよう求めることになる、としている。

これは日常の実感と一致する。「このプロジェクトではmainに直接pushしない」「このテーブルは論理削除だから物理削除してはいけない」——人間なら数週間で自然に身につくこの種の知識を、エージェントは**毎回のセッションでゼロから始める**。[why-harness-matters.md](./why-harness-matters.md)で見た「人間が無自覚に埋めているランタイム支援」の、最も身近な現れがここである。

実装としては、[Anthropic公式のAgent SDK文書](../sources/article-he-agent-sdk-overview.md)が「Skills, commands, and memory」という機能を挙げ、これらがプロジェクトの `.claude/` とホームディレクトリの `~/.claude/` から**自動的に読み込まれる**と説明している。仕組みは用意されている。問題は、そこに何をどう書くかである。

## 最大の落とし穴——「コンテキスト汚染」

ここで多くの人が逆方向に踏み外す。**書けば書くほど良いと考えてしまう**のである。

CLAUDE.md運用のベストプラクティスを整理した[Zennの記事](../sources/article-he-claude-md-best-practices.md)は、この失敗を「コンテキスト汚染」と呼ぶ。同記事の筆者は、良かれと思って増やしたルールがかえってAIを混乱させ、指示が無視される状態を招くと指摘し、よくある失敗パターンとして次の3つを挙げている。

1. 情報量が多すぎてLLMが処理しきれない
2. 実務に関係ない「好みのコードスタイル」まで全部詰め込んでいる
3. `/init` などで自動生成した、誰もメンテしない長文ドキュメントになっている

筆者は、**LLMは一度に安定して扱える「ルールの数」に限界があり、指示が増えれば増えるほど守られない指示が出てくる**と述べ、「なんか最近Claudeの精度が悪いな」と感じたらまずCLAUDE.mdを疑ってみる価値があるとしている。

分量の目安として、同記事は次の数値を示している。

> 引用: 「推奨されるのは、できるだけ小さい CLAUDE.md です。目安は 300 行以下。指示としては 150〜200 個程度に収める。」

この300行・150〜200指示という数値は同記事の筆者が示す目安であり、公式仕様として定められた上限ではない点は押さえておきたい。ただしその背景にある理屈——**コンテキストウィンドウは人間の作業メモリ（ワーキングメモリ）に似ており、不要な情報で埋め尽くすと本当に重要なタスクに割けるリソースが減る**——は、コンテキストエンジニアリング一般の考え方と一致している。同記事は、`/init` ベースの自動生成は冗長でノイズの多いドキュメントになりやすく「全部書いてあるけど、どれも守られない」状態を招くとして、基本的に避けたほうがよいとも述べている。

## 何を書き、何を書かないか

では書くべきは何か。同記事の主張は明確である。

筆者は、CLAUDE.mdにはコードスタイルではなく「プロジェクト固有の知識・罠・運用ルール」を書くべきだと主張している（同記事の要約）。

インデントは2スペース、シングルクオートを使う、import順序はこう——といったフォーマット・スタイルの指示は、**Lint・Formatter・Git hooks（pre-commit / post_tool_useなど）で機械的に強制する方が確実**だと同記事は指摘する。

これは[権限の設計](./permissions-design.md)で見た原則とまったく同じ構造である。**確実に守らせたいものは、AIへのお願いではなく機械的な強制で実装する。** ハーネスにおける「書き場所の選択」は、次の3層で考えるとよい（CLAUDE.mdとdenyルールの性質は[権限の設計](./permissions-design.md)の対比表で扱った内容そのものなので、ここではLint/Formatter/hooksという3つ目の層を加えた形で示す）。

| 手段 | 性質 | 向いている内容 |
|---|---|---|
| **CLAUDE.md に書く** | 確率的なお願い（詳細は[権限の設計](./permissions-design.md)の対比表を参照） | プロジェクト固有の知識・罠・運用ルール |
| **Lint / Formatter / hooks** | 機械的な強制。書式や構文の逸脱を自動で直す・止める | コードスタイル、フォーマット |
| **deny ルール** | 機械的な禁止（詳細は[権限の設計](./permissions-design.md)の対比表を参照） | 絶対に起きてはいけない操作 |

CLAUDE.mdに書くべきなのは、**機械が判定できない、しかしこのプロジェクトを知らないと踏む地雷**である。

### 有効に機能する3要素

同記事は、どんなプロジェクトでも効きやすい要素として次の3つを挙げている。

**1. プロジェクトを一行で説明する。** 例として「Next.jsで実装された顧客向け決済ポータル」「社内向けのドキュメント検索ツール」が挙げられている。リポジトリ全体を読む前に全体像を掴める一文があると、タスク理解が安定するという。

**2. 頻繁に使うものに絞ったコマンド。** 起動・ビルド・テスト・Lint、DBマイグレーションなど。「よく使うものだけ」という限定が重要である。

**3. 罠の共有——ただし「トリガー」と「アクション」のセットで。** ここが最も実践的な指摘である。同記事は次の対比を示している。

| | 例 |
|---|---|
| 悪い例 | 「schema.prismaの直接編集は禁止」 |
| 良い例 | 「schema.prismaを変更したいときは、必ずschema/*.prismaを編集してからpnpm build:schemaを実行すること」 |

**いつ（トリガー）・何をするか（アクション）**をセットで書き、具体的な行動指示（Actionable）にすることで遵守率が劇的に向上すると筆者は述べている。禁止だけを伝えると、エージェントは代替手段を自力で探して別の事故を起こす。**やってはいけないことではなく、代わりにやるべきことを書く**——これは人間への引き継ぎ資料でも同じである。

## 段階的開示——全部書かない設計

CLAUDE.mdにすべてを書ききる必要はない、と同記事は述べる。

筆者は、詳細情報は別ファイルに分離し、CLAUDE.mdには場所だけ案内する「段階的開示」の設計が推奨されると述べている（同記事の要約）。

DBスキーマは `docs/schema.md`、APIドキュメントは `docs/api.md`、複雑なドメインルールは `docs/domain-rules.md` のように詳細を別ファイルへ分け、CLAUDE.mdにはその場所と概要だけを書いてタスクに応じて追加のファイルを開かせる——これが progressive disclosure（段階的開示）である。

**常時読ませるものと、必要なときだけ読ませるものを分ける。** 前者は毎回コンテキストを消費し、後者はしない。この切り分けが、限られた枠の中で情報量を確保する方法になる。

あわせて同記事は、配置順にも意味があると指摘する。Claude Codeのシステムメッセージには「CLAUDE.mdの文脈はタスクと無関係な場合がある」という前提が含まれており、Claudeが状況によって一部を意図的に無視することがあるという。さらにLLMは入力の**先頭と末尾を強く重み付ける**傾向があり、先頭はシステムメッセージとCLAUDE.mdの冒頭、末尾は直近のユーザープロンプトに当たる。この特性を踏まえ、**本当に守ってほしいことは冒頭に書き、「IMPORTANT」「Read this first」などで明示的に強調する**のが有効だとしている。

## 長期記憶として育てる

同記事が示す整理の中で、最も本ファイルの主題に近いのが記憶の対比である。`/clear` コマンドで会話履歴をリセットするとチャットログ（**短期記憶**）は消えるが、CLAUDE.md（**長期記憶**）は読み直される。短期記憶はタスクごとに使い捨てられ不安定になりやすい一方、長期記憶は常に維持される唯一の拠り所だという。

そこから導かれる運用指針が実に的確である。**「毎回同じことを説明しているな」と感じたら、それは短期記憶にしか情報がない証拠**なので、すぐに長期記憶へ書き込むべきだ、と。

同記事はまた、CLAUDE.mdは一度書いて終わりの静的なドキュメントではなく、開発とともに育てるものだと主張する。誤ったフレームワークやAPIを選んでしまった、新しい罠に気づいた、ワークフローやコマンドが変わった——といったタイミングで、**その都度一行追加するぐらいの軽さ**で継続的にメンテするのが理想だという。ハーネスは作って終わりではなく、運用の中で更新され続ける対象である。

### 置き場所の使い分け

配置についても同記事は具体的である。Claude Codeがプロジェクトルートだけでなく**親・サブディレクトリのCLAUDE.mdも自動で探索する**特性を利用し、モノレポではリポジトリルートに全体共通のルール、各パッケージ配下にそのサービス固有のルール・罠を配置する構成が紹介されている。また個人用の設定はリポジトリにコミットせず `claude.local.md` に書いて `.gitignore` に入れるか、ホームディレクトリの `~/.claude` に書いて全セッションに適用する運用も挙げられている。

この「チーム共有か個人用か」「このリポジトリか全体か」という切り分けは、[設定の4スコープ](./settings-scopes-and-governance.md)で見た構造とまったく同じである。**ルールも設定も、同じ2軸で配置を考える**と覚えておけばよい。

## 論文の視点に戻る

最後に、冒頭の論文の主張に戻っておきたい。同論文は、これらの構成要素が**明示的に公開・構造化・トレースされる**ことによって、モデルの潜在能力が監査可能なソフトウェアエンジニアリング行動になると論じていた。

CLAUDE.mdを書くという行為は、単なる指示書の作成ではない。**それまで人間の頭の中にしかなかった暗黙のプロジェクト知識を、明示的なランタイム資産に変換する作業**である。書かれていないルールは、エージェントにとって存在しないルールと変わらない。そしてそれは、次に来る新入社員にとっても同じことである。

## まとめ

- ルール＝毎回読み込ませる前提知識。論文の11責務では**プロジェクトメモリ**にあたり、実装としては `.claude/` と `~/.claude/` から自動読み込みされる
- 人間が社会化・経験で得る知識は**モデルの呼び出しには自由に利用可能ではない**。明示的に公開・構造化しなければ、エージェントは即興するか人間に頼る
- 最大の落とし穴は**コンテキスト汚染**。増やすほど守られない指示が増える。記事筆者の目安は300行以下・150〜200指示
- **コードスタイルは書かない。** 機械で強制できるものはLint・hooksへ、絶対禁止はdenyルールへ。CLAUDE.mdは「機械が判定できないプロジェクト固有の知識・罠」のための場所
- 罠は**トリガー＋アクション**で書く。「禁止」ではなく「こうしたいときは、こうする」
- **段階的開示**——詳細は別ファイルに置き、場所だけ案内する。重要なものは冒頭に置く
- CLAUDE.mdは**長期記憶**。同じ説明を繰り返していると気づいたら書き込む。一度きりではなく育てる

これでハーネスの4要素——道具・権限・制限・ルール——が揃った。全体像と読む順番は[what-is-harness-engineering.md](./what-is-harness-engineering.md)、責務と成熟段階の枠組みは[harness-responsibilities-and-ladder.md](./harness-responsibilities-and-ladder.md)を参照のこと。
