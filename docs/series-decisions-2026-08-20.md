## 判断1: 02 の本編の例が開発者向けに偏っている（最重要・構成に関わる）

**何が起きたか**
採点者3名中2名（第1周）が大〜中で指摘。02 の本編（特に第2章と活用事例）は、具体例のほとんどが Claude Code 固有の道具立てでできている。可視スライドで Claude Code／CLAUDE.md／npm 等が出るのは本編 12 枚:

> slide-13 「ルールファイル：繰り返し使う前提を置く場所」
> slide-14 「本プロジェクトの CLAUDE.md 抜粋」（code スライドで CLAUDE.md の実物を見せる）
> slide-15 ルールファイルの書き方（「npm test」「コミット」が推奨例の中に登場）
> slide-24 「『置いてある』のに効かない時」（確認手順が /context・InstructionsLoaded hook）

第1・2周の maker は「初出の用語に（ ）説明を足す」ところまでは直した（いまは読める）。しかし **例そのものが開発の話** である点は構成変更になるため deferred にした。想定読者を「チャットAIしか触ったことがない業務担当者」に置くなら、この読者は自分の CLAUDE.md を持っていない。

**選択肢**
- **A. このまま**（説明済みなので読める。02 は「AIを使い込む人向けの回」と割り切る）— 作業ゼロ
- **B. 各章に非開発の並走例を1つずつ足す**（例: ルールファイル＝「議事録の書式ルールを毎回貼らずに済ませる」、メモリ＝「前回の決定事項」）。既存スライドの bullets に「エンジニア以外なら〜」の行を足す軽量版 — 半日・回帰リスク小
- **C. 第2章・第4章の例を業務例主体に差し替え**（Claude Code は「実物の一例」に降格）— 数日規模・再採点必須

**推奨: B**。第1周採点の findings（m2）は C を求めていたが、02 は既にユーザーレビュー済みの正本であり、C は正本の性格を変えてしまう。B なら正本の構成を保ったまま「置いていかれる読者」を減らせる。

→ あなたの判断: **B**（非開発の例スライドを1枚追加。見て不要なら消す）→ 実施済み: slide-20「エンジニア以外の仕事に置き換えると」を挿入（72→73枚）

## 判断3: rubric 項目5「notes に話者の実感・迷い」を正本 01/02 に要求するか

**何が起きたか**
全3周・全採点者が 01/02 に対して繰り返し指摘（毎回 中）:

> 「53枚の notes を通読しても『だと思います』『正直』のような話者の迷い・実感を示す表現が一切なく、すべてが整理・断定調」

これは私が rubric v2 の項目5 に「notes に話者の実感・迷いがあり、全部が断定と整理で構成されていないか」と書いたため。出どころは 05 のループで「notes の言い淀みが高評価だった」という学び。実物の比較:

> 01 slide-09 notes（事実列挙型）: 「Anthropic公式は、AIを『優秀だが新しく入った社員』と考える例を示しています。仕事はできても…」
> 05 slide-19 notes（言い淀み型）: 「…これは、人に仕事を頼むときにもそのまま使える話だと思います。」

つまり **正本 01/02 の notes スタイル（事実列挙・出典明示）と、rubric の要求（語り・実感）が矛盾**している。maker は正本保護で毎回 deferred にしており、放置すると今後の採点で毎回同じ減点が出続ける。

**選択肢**
- **A. rubric を直す**: 項目5 の「言い淀み」を必須から外し、「断定の連打で読み上げ原稿として不自然な場合のみ減点」に緩める。01/02 のスタイルを正とする — 15分・デッキ変更なし
- **B. 01/02 の notes に言い淀みを足す**: 各デッキ5〜10箇所、章の変わり目に一人称の語りを足す — 半日・正本の文体変更
- **C. 折衷**: rubric は「章扉と closing の notes にだけ語りを求める」に限定し、01/02 はその数枚だけ直す

**推奨: A**。差異分析でも「事実列挙型 notes（100〜160字）に言い淀みだけ足しても効果は薄い」と出ている。05 のような長い語り型 notes は 05 の個性として維持し、rubric 側を直すのが筋。

→ あなたの判断: **A**（言い淀みは足さない。スライドは自信を持って断定、間違いは後で訂正）→ rubric 項目5 と例外欄に反映済み。loop-learnings の当該学びも撤回済み

## 判断5: rubric v2 の重み（大25/中5/小1・合格80）と「初心者」の読者像

**何が起きたか（データ）**
- 重み: 大1件で項目75＝不合格。実際に 05 が第2周で「定義が slide-09（8枚目基準超え）」の大1件だけで落ちた。修正は結果的に良くなったが、「大の定義」を採点者がどう解釈するかに合否が乗る
- 読者像: 「初心者への適合」は毎周いちばん割れた項目。02 第1周は 45/94/65、第3周も 60/95/100。差の原因は「npm test が読めない読者を想定するか」「（ ）説明があれば読めると見なすか」の解釈差

**選択肢（重み）**
- **A. 現状維持**（大25/中5/小1・合格80。大=1発アウトは「読者を止める欠陥」の定義どおり）
- **B. 大を20に**（大1件＋中3件までは通る。「大の解釈ブレ」の影響を緩和）

**選択肢（読者像）**
- **C. rubric の読者定義を具体語で固定**: 「エクセルと社内チャットは使うが、ターミナル・Git・コードは触らない。npm test・コミット・フック・schema は読めない読者」と明記 — 割れの最大要因を潰す
- **D. 読者を「SE新人まで」に引き上げ**（03 のような技術寄り回を楽にする）

**推奨: A + C**。大=1発アウトは今回機能した（05 の定義前出しは明確に良化）。割れは重みでなく読者像の曖昧さから来ているので、C で固定する方が効く。

→ あなたの判断（重み / 読者像）: **B + C（表現は汎用化）**。大は 20 点に（一発アウトは緩和。注: 合格は 80 以上なので大1件のみ＝ちょうど80で辛うじて合格）。読者像は「Excel と社内チャットは使うが、ターミナル・Git・コードは触らない。プログラムが読めない。コマンドラインを実行できない」で固定（npm test 等の個別列挙はしない）→ rubric と aggregate_findings.py に反映済み

## 判断6: 文言リントの警告を「落とすゲート」に昇格させるか

**何が起きたか**
`tools/lint_deck_text.py` は現在、closing 22字超・Markdown 残留・存在しないページ参照だけで落とし、以下は**件数を出すだけ**:

| 指標 | 01 | 02 | 03 | 04 | 05 | 備考 |
|---|---|---|---|---|---|---|
| 「ではなく」 | 5 | 3 | 13 | 3 | 4 | 03 は 19→13 に改善済み |
| 丸数字①〜 | 19 | 44 | 23 | 0 | 4 | 01/02 は体系的連番として使用 |
| AI定型句 | 0 | 0 | 0 | 0 | 0 | 全デッキ解消済み |
| ダッシュ | 0 | 0 | 0 | 9 | 5 | 04/05 は notes 内のみ（投影されない） |

正本 01 にも「ではなく」5回・丸数字19個あるので、単純な件数閾値は正本を落とす。

**選択肢**
- **A. 警告のまま**（採点者の減点材料として使う。現状）
- **B. 密度閾値で落とす**: 1枚あたり密度が正本01の2倍を超えたら不合格（例: 「ではなく」53枚で5回 ≒ 0.094/枚 → 閾値 0.19/枚。03 の 13/66 ≒ 0.197 はギリギリ不合格）
- **C. AI定型句だけ「1件でも不合格」に昇格**（現在全デッキ0なので回帰防止として安全）

**推奨: A + C**。定型句ゼロは今夜達成した状態なので、回帰防止ゲートにする価値がある。「ではなく」は文脈依存（対比説明として正当な使用がある）なので警告のままが安全。

→ あなたの判断: **A + C**（警告は警告のまま。AI定型句のみ1件でも不合格に昇格）→ lint_deck_text.py に反映済み（現在全デッキ0件で全ゲート緑）

## 判断8: 02 の eyebrow 体系と、punch＋末尾bullet の念押し（rubric の例外にするか）
