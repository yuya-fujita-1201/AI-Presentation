## 2. 画像の共通仕様（全17枚に適用）

| 項目 | 指定 |
|---|---|
| サイズ・比率 | **4:3 の横長（1024×768 px 推奨、最低 800×600）**。表示領域が 524×378px（`image_text.img`）なので、極端な横長・縦長は letterbox になり破綻する |
| 文字 | **画像内に文字を入れない**（日本語が崩れる／PPTXで拡大縮小時に読めなくなるため）。ラベルが要る場合はアイコンや記号で表現する |
| 画風 | フラットベクターイラスト風。立体的な3Dレンダリングやフォトリアルは不可。線は細め、面はソリッド |
| 配色 | **テーマ準拠配色**。現在の `meta.theme` は `accenture-purple`（濃紫 `#460073`、アクセント `#A100FF`、薄紫 `#F7F0FC`、白）。**紫以外の色相は原則使わない**。なお **清書時に `meta.theme` を切り替えれば配色を変更できる**ので、色を画像に焼き付けすぎず「紫系で統一感が出る」程度の塗り分けにとどめること |
| 背景 | **白または極薄い紫のフラット背景**。写真的な背景・グラデーションの多用は不可（スライド背景が白なので、なじませる） |
| 余白 | 図の四辺に十分な余白。要素を端まで詰めない |
| 密度 | **1枚につき伝える概念は1つだけ**。要素は5〜7個までに抑える。情報を詰め込むと 524px 幅で潰れて読めない |
| 一貫性 | 17枚を通して**同じ画風・同じ配色・同じ線の太さ**。人物を描く場合は全枚で同じ描き方、ロボットを描く場合も全枚で同じ描き方（顔の描き込みは最小限、記号的に） |

## 3. 「良い図」の判断基準

生成した図を採用する前に、次を自問すること。1つでも No なら作り直す。

1. **隣の文章を読まずに図だけ見て、そのスライドが何の話か推測できるか？**（できないなら、それは単なる飾り＝不合格）
2. スライドの `punch`（パンチライン）と図の内容が一致しているか？
3. 図の中の要素数が7個以下か？ 524px 幅に縮小しても各要素が識別できるか？
4. 他の16枚と並べたとき、同じシリーズに見えるか？
5. 文字が入っていないか？

## 5. 画像生成の進め方（推奨）

1. **まず3枚だけ試作する**：`fig-tools-08`（比喩の代表・オンボーディング資料）、`fig-tools-12`（構造図の代表・USBハブ）、`fig-tools-14`（メタファー図の代表・計量器）。この3枚で画風・配色・線の太さを固め、**プロンプトの共通部分をテンプレート化**する
2. 試作3枚をデッキに入れてビルドし、**524×378px に縮小された状態で識別できるか**を実際のプレビューPNGで確認する（ここで潰れるなら要素を減らす）
3. 画風が固まってから残り14枚を生成する
4. 生成した画像は `decks/ai-topics-02-skills-mcp-cli/assets/` に**同じファイル名で保存**する（deck.json のパスは変更不要）

### ImageGen へ渡す共通プロンプト骨子（日本語で書いてあるが、英語で投げてよい）

> フラットベクターイラスト、白背景、紫の配色のみ（濃紫 #460073・明紫 #A100FF・薄紫 #F7F0FC）、細い線と面のソリッド塗り、テキスト・文字・数字は一切含めない、記号的でシンプルな人物とロボット、余白を広く取った 4:3 の構図、ビジネスプレゼン向けの清潔な図解、要素は5〜7個まで

## 6. deck.json を触ってよい範囲

原則として文章は変更しない（発注者要望を反映して文言は確定済み）。ただし次だけは調整してよい。

- 画像を入れた結果、**キャプションと図の内容が食い違った場合の `caption` の修正**
- 図が大きすぎ/小さすぎる場合の該当スライドの `style.img` の調整（例: `{"img": {"w": 500, "h": 360}}`）
- 本文が枠から溢れた場合の `style.body.size` / `style.body.gap` の微調整

**やってはいけないこと**: スライドの追加・削除・順序変更、`title` / `punch` / `bullets` の書き換え、テーマ変更、`templates/` の編集。

文章に問題を見つけた場合は、直さずに**報告だけ**すること（発注者が判断する）。

## 7. 参考ファクト（この範囲外の事実をスライドに足さないこと）

図の中に記号として事実を織り込む際、以下の範囲を超える主張をしないこと（出典: `knowledge/agent-capabilities/overview.md` と `decks/ai-topics-02-skills-mcp-cli/deck.json`）。

- 4手段は**プロンプト／プロジェクトルール／Skill／MCP／CLI**。実体としては「プロンプト」1本の中に「その場の指示」と「常設化したルール」の2つを含む
- Skill の必須フィールドは **name と description の2つだけ**
- 段階的開示は3階層: Level 1（フロントマターのメタデータ、起動時に常に、約100トークン）／Level 2（SKILL.md本文、要求に関連すると判断された時、目安5,000トークン未満）／Level 3（参照ファイル・スクリプト、実際に必要になった時のみ、未アクセスならゼロ）
- MCP の登場人物は3者: **Host**（AIアプリ本体）／**Client**（サーバー1つにつき1つ生成される接続担当）／**Server**（ツールやデータを公開する側）
- MCP が公開できる3大プリミティブ: **Tools**（実行可能な関数）／**Resources**（コンテキストデータ）／**Prompts**（対話テンプレート）
- MCP の固定費の実測報告: **5サーバー58ツールで約55,000トークン**（同じ枠にSkillなら約550個分のname+descriptionが入る計算）
- CLI は4手段のうち唯一「新しく作るものがない」手段。固定費ゼロ。論点はLLMの事前知識が古くhallucinationしやすいことのみ
- 判断フローは「**CLI → Skill → MCP** の順にコストの安いものから試す」
- よくある誤解4つ: ①SkillはMCPの進化形ではない ②4つは排他ではなく同時に使える ③Skillは特定製品の機能名ではなく各社に広がりつつある ④能力を足す＝モデルの再学習ではない

**この一覧にない数値・固有名詞・実績を図に登場させないこと。**

## 10. 参考：`image_text` タイプの仕様

```json
{
  "type": "image_text",
  "title": "見出し",
  "punch": "一目で伝えたい一文（全幅・太字・アクセント色）",
  "bullets": ["本文（children で子項目も可）"],
  "path": "assets/figure.png",
  "caption": "図の下の補足",
  "image_side": "right"
}
```

- 領域（`templates/layouts/default.json` の既定値）: `title` / `rule` / `punch` / `body`（本文カラム 552×420px）/ `img`（**524×378px**）/ `caption` / `footer_l` / `footer_r`
- `image_side` を `"left"` にすると本文と図の左右が入れ替わる（`body` / `img` / `caption` の x 座標がキャンバス中心で反転する）
- 詳細は `docs/deck-schema.md` の `image_text` の項を参照
