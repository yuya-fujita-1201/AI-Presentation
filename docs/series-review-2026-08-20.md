## 7. グラフエンジニアリングとしての強化観点（おまけ）

今夜の作業自体が 1 本のグラフでした:
`採点 ×3（並列・レンズ別）→ 集約（aggregate_findings.py＝アンカー）→ maker ×5（デッキ別に並列）→ 機械ゲート（gate_deck.sh＝アンカー）→ 統合担当が目視・コミット → 再採点 ×3`。
ループナレッジとグラフナレッジは「似ている」のではなく層が違います。ループは「同じ成果物を何周磨くか」、グラフは「1 周の中を誰にどう分けて、どこで合流させるか」。今夜の 1 周＝グラフ、周回＝ループです。

グラフ側で今夜分かったこと（knowledge/graph-engineering や graph-engineering スキルに足す候補）:
- **検証ノードの多重化とレンズ分け**は、ループの「採点者のブレ」問題をグラフ構造で解く手段。1 名×直列確認より 3 名×並列の方が速く、spread という新しい信号も得られる
- **合流点のアンカーは 2 種類要る**: 成果物を検査するアンカー（gate_deck.sh）と、エージェントの報告を機械的に集約するアンカー（aggregate_findings.py）。後者が無いと「採点者3名の意見をメインが読んで判断」になり、結局印象採点に戻る
- **隠れたエッジは git にあった**: 同一作業ツリーで並列 maker → 1 体の `git stash` で全員の作業が退避された。書き込み先はデッキ別に分かれていても git は共有資源。対策は (a) maker に git 操作禁止を明記、(b) ベースライン（既存警告）をファイルで渡して比較に git を使わせない、(c) ゲートが通り次第デッキ単位で即コミット、(d) 本当に隔離したいなら worktree
- **共有ファイルの隠れたエッジ**: `tools/verify_ai_eng_series.py` の枚数 TARGETS を 2 体の maker が同時に編集しうる。枚数変更は申告制にして統合担当が直す
- **maker の rejected 権**は迂回路として有効だった（01 で 23 件中 11 件を正本保護で却下）。検証役の指摘を鵜呑みにしない配線が、正本の品質を守った
- **コスト感**: 採点 15 名×3 周 + maker 5+5+1 体 + 差異分析 1 体 + 教訓蒸留 3 体 ≒ 60 エージェント。1 エージェントが deck.json 全文＋コンタクトシート 8〜12 枚を読む構成にしたので、PNG 1 枚ずつ実見する従来方式より軽い

ユーザーへの判断ポイント（グラフ）:
- レビューのたびに 3 名×5 デッキの採点を走らせるか、**変更のあったデッキだけ**にするか（差分グラフ）
- Codex を 3 名のうち 1 名にする運用を標準にするか（同一モデルのバイアスを割る。今夜は全員 Claude）
- maker を worktree 隔離にするか（安全だがビルド成果物・プレビューの二重化でディスクと時間を食う）
