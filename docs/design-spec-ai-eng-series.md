## 2. 冒頭パターン：表紙 → 全体地図 → 学べること → 章扉

### 実例（01）
1. **表紙 (`title`)**: title="プロンプトエンジニアリング超入門" / subtitle="AI活用の全体地図を確かめてから、日常と仕事の実例で「伝わる頼み方」を学びます。" / meta="AIエンジニアリングシリーズ 01　|　初版 2026-08-14／更新 2026-08-20"
2. **全体地図 (`image_text`, eyebrow="はじめに｜AI活用の全体地図")**: title="AI活用を支える5つの設計" / punch="このシリーズでは、AI活用を考えるための初心者向け「5層モデル」として整理します。今回は「頼み方（プロンプト）」です。" / bullets は5層を1行ずつ列挙し、今回の層だけ `bold: true` + 説明の`children`を付け、末尾に「この5層モデルは…業界標準ではない」の免責を`bold, color: accent`で置く。図版は5層の入れ子図（`diagram-layers-focus.svg`）。
3. **学べること (`image_text`, eyebrow="はじめに｜この資料で得られること")**: title="この資料で学べること" / punch は「〇〇を整えると、△△できるようになる」型の効能文。bullets は「この資料で学べることは、次の3つ」を`bold`親にして`children`に3項目を並べる二階層。`image_side: "left"`で図の左右を切り替え、直前スライドと絵柄が同じでも配置を変えて単調さを避ける。
4. **章扉 (`section`)**: number="01" / title="プロンプトの基本" / subtitle="プロンプトとは何か。プロンプトエンジニアリングとは何か。そして、AIはどうやって答えを作るのか"

### 実例（02、同型で内容差し替え）
1. 表紙: subtitle="AIに「何を・いつ・どれだけ」見せるかを、3つの経路で整理して学びます。"
2. 全体地図: title="5つの設計のうち、今回は「コンテキスト」"。bullets 末尾に「前回の予告『前提や資料を忘れる→渡す情報を見直す』が、今回のテーマ」という**前デッキからの橋渡し文**を追加している（01にはない、シリーズ2作目以降の型）。
3. 学べること: title="コンテキストを整えると、AIの仕事はこう変わる"。bullets 最後の項目が「そのために学ぶこと」＝各章の役割の1行要約になっている（01は「外側の仕組みへ進んでも消えない」という射程の話で、内容の型がやや異なる＝完全固定ではなく若干の自由度がある）。
4. 章扉: number="01" / title="コンテキストとは何か、どう設計するのか"

### 06/07 向けの提案（5層地図の置き換え）
06-rag と 07-okf-visual-guide は5層シリーズの外側にある「ai-topics」単発デッキのため、「今回はどの層か」を示す5層地図はそのままでは使えない。**採用案**: 2枚目 image_text の役割を「このデッキが5層シリーズのどこを深掘りする補助教材か」を示す**接続地図**に置き換える。
- 06-rag: 5層地図を出し、「コンテキスト（02）」を最も濃く塗ったうえで、punchを「RAGは、コンテキストエンジニアリング（02）の中の『必要時に取得』を深掘りする一手法です」のように**02への従属関係を明示**する。bulletsは5層を並べず、02の3経路（自動ロード／必要時取得／今回渡す）を再掲し「必要時取得」だけを強調する方が実体に合う。
- 07-okf-visual-guide: OKFは知識管理（ナレッジ）の話であり5層モデルの外にあるため、5層地図の代わりに「このデッキの位置づけ」1枚（例：「本シリーズはAI活用の5層、本資料はその5層を支える"ナレッジの持ち方"を扱う」）に差し替える。それでも**表紙→接続地図→学べること→章扉**という4枚構成の型自体は崩さない。

**規則**: 冒頭4枚の型（表紙→地図→学べること→章扉）は06/07でも維持する。2枚目だけは「5層のうちどれか」ではなく「シリーズのどのデッキ（02等）を深掘りする補助教材か」を示す接続地図に差し替え、punchでその従属関係を1文で明言する。

## 3. eyebrow の体系：01型（章ラベル固定）vs 02/05型（スライド単位で可変）

### 01の実例（10個）— 同一章内は同じeyebrowを使い回す
1. `はじめに｜AI活用の全体地図`
2. `はじめに｜この資料で得られること`
3. `01｜プロンプトの基本`（S5〜S9まで**5枚連続で同一文字列**）
4. `02｜AIへの依頼設計の5つの要素`（S12〜S16まで同一）
5. `02｜AIへの依頼設計の5つの要素｜教材用作例（実測結果ではありません）`（同章内で実測でない回のみ末尾に免責を追記する変則）
6. `03｜うまくいかないときの直し方`（S20〜S24で同一）
7. `04｜日常で使う｜教材用作例`
8. `05｜仕事で使う｜教材用作例`
9. `付録｜配布用テンプレート`（付録内の複数枚で同一）
10. `付録｜参考資料 1/5`〜`5/5`（付録の出典表だけは連番で可変）

### 02/05の実例（10個）— スライドごとに個別の見出しを付ける
1. `01｜コンテキストとは`
2. `01｜コンテキストエンジニアリングとは`
3. `01｜2つのエンジニアリングの違い`
4. `01｜3経路とガードレール`
5. `01｜具体例①` / `01｜具体例②`
6. `02｜①自動ロード・ルールファイル`
7. `02｜②必要時に取得`
8. `02｜章まとめ`
9. `05｜グラフエンジニアリングとは何か` 章内: `01｜グラフとは` / `01｜なぜ必要か` / `01｜「エンジニアリングする」の意味` / `01｜一言でいうと`（4枚とも別文字列で論の展開を刻んでいる）
10. `01｜比喩でつかむ5層` / `01｜言葉としての現在地`

### 推奨：06/07は02/05型（スライド単位で可変）を採る
**理由**: (a) 02は01より後に作られた改訂版であり、05は「最新改訂」（タスク仕様が明言）。両方とも01の固定ラベル方式から離れ、スライド単位のeyebrowに統一している＝シリーズ内で進化の方向が明確。(b) eyebrowがスライドごとの見出しとして機能すると、コンタクトシートやサムネイル一覧だけで論の展開を追えるようになり、`docs/series-diff-analysis-2026-08-20.md` が指摘する「情報の刻みの細かさ」の思想と一貫する。(c) 06/07は5層シリーズ外の単発デッキで章の反復性が01ほど高くないため、固定ラベルの再利用メリット（省力化）より個別化の可読性メリットが上回る。

**規則**: eyebrowは `{章番号}｜{そのスライド固有の要点見出し}` を毎回書き下ろす（02/05型）。教材用作例など免責が要る回だけ01同様に `｜教材用作例（実測結果ではありません）` を末尾に追記する。

## 4. punch の文体：です・ます結論型、実例10個と文字数分布

01デッキの `punch` 全21件の実測値: **最小36字／最大80字／中央値46字／平均47.7字**。

| 字数 | punch本文 |
|---|---|
| 36 | 「1回の頼み方」を整えると、欲しい答えの方向をAIへ伝えやすくなります。 |
| 36 | 守ってほしい重要な条件と、してほしくないことを、理由とセットで伝えます。 |
| 39 | AIには、まず使える下書きを作ってもらいます。完成品にする責任は人が持ちます。 |
| 41 | 毎回長文を書く必要はありません。AIが迷いそうな要素だけを、必要な分だけ書きます。 |
| 42 | この答えを何に使うかを1文添えると、AIは残す情報と省く情報を判断しやすくなります。 |
| 44 | 何がダメだったのかを分けると、「足す・減らす・替える・見直す」のどれを試すかを選べます。 |
| 46 | 前章の3つの質問に「なぜ（使い道）」と「守ること（条件）」を足したのが、この5つの要素です。 |
| 48 | AIは入力を手がかりに、続きそうな言葉のかけら（トークン）を一つずつ生成し、答えを組み立てます。 |
| 49 | 一発で完璧な答えは、人間どうしでも難しいもの。原因を切り分けたいときは、1項目ずつ直して比べます。 |
| 80（最大） | プロンプトエンジニアリングとは、AIへの質問・指示（プロンプト）と、判断材料（コンテキスト）、使い道・返し方・条件を組み合わせ、結果を見ながら調整することです。 |

**規則**: punchは必ず「です・ます」で終わる断定文にし、**そのスライドの結論を1文で言い切る**（言い換え・比喩の助走を挟まない）。文字数は35〜55字を主戦場とし、定義文など密度が高い回のみ80字までの2行化を許容する（35字超＝2行化は減点対象ではない。`loop-learnings.md` §3で「却下」済みの基準）。bulletsはpunchを裏付ける材料であり、punchの言い換えを繰り返してはいけない。

## 5. bullets の二階層構造（太字ラベル＋children）

01/02はほぼ全スライドがこの構造。実例5個:

1. （01 S6）`{"text": "動詞に迷ったら", "bold": true, "children": ["残したい項目を名詞で並べると、出力の抜けも確認できる"]}`
2. （01 S3）`{"text": "この資料で学べることは、次の3つ", "bold": true, "children": ["曖昧な頼みが、なぜ自分の意図とずれやすいのかが分かる", "AIへの依頼設計の5つの要素で、頼み方と材料の指定を組み立てられるようになる", "期待と違う答えを、対話で直せるようになる"]}`
3. （02 S5）`{"text": "コンテキスト＝今回、モデルが参照できる情報", "bold": true, "children": ["システム指示・会話履歴・読み込まれたルール・取得された検索結果など"]}`
4. （02 S8）`{"text": "①自動ロード：ルール・自動で読み戻すメモリ", "bold": true, "children": ["短く毎回必要な情報を、製品・配置・設定に応じて読み込む"]}`
5. （01 S27, two_columnの右列）`{"text": "モデルが新しくなると、これを残すと過剰な確認を招く場合がある", "bold": true, "size": 16}`（子項目なしの太字1行締めくくり）

### フラット箇条書きとの使い分け
05 S10（`言葉としての現在地`）は例外的にフラットな完結文6本を使う: `"2026年7月、個人のX投稿と1本の記事から広まった"` など。すべて独立した短い事実の列挙で、太字ラベルによる主従関係を持たせる必要がない（時系列の出来事の羅列）場合のみフラットが許容される。`series-diff-analysis-2026-08-20.md` は05のS16-20（部品説明4枚）のフラット化を「読みやすさの評価が下がる」欠陥として明示的に指摘している。

**規則**: bulletsは既定で「太字ラベル（見出し語・断定文）＋childrenに具体例や補足を1〜2本」の二階層にする。フラットな完結文の羅列は、**単純な事実列挙（年表・経緯）でラベル化するとかえって冗長になる場合に限り**例外的に許可する。判断根拠列挙・要素説明・比較には必ず二階層を使う。

## 6. caption の役割（punchの言い換え禁止・橋渡し／予告専用）

`image_text` の `caption` はpunchの結論を繰り返す2文目ではなく、**次のスライド／次の具体例への予告、または punch にはない追加情報（起源・数値・帰結）を足す**専用フィールド。良い実例4個（すべて05）:

1. S5: punch「ここでいうグラフは、丸と矢印のほうです。円グラフや棒グラフの話ではありません」／caption「起源は1736年。橋を渡り切れるか、という問題でした」→ punchが定義、captionが**このあと語る具体エピソードの予告**。
2. S6: punch「グラフの意味がわかったところで、なぜそれを設計する必要があるのか…」／caption「1体で回すと、限界は3つの形で出てきます」→ captionが**bulletsで列挙される「3つ」の件数を先出しする予告**。
3. S19: punch「前の出力を実際に読んでいるかどうか。判定はそれだけで足ります」／caption「依存を正しく描けば、並列化はあとから自然についてきます」→ punchとは別の**帰結（メリット）を追加**。

## 11. closing の書式実例

3デッキとも共通構造: `title`（明日への行動喚起・体言止めではなく命令形/勧誘形）／`bullets`（本編の要点を再掲、最後の1〜2項目は`bold, color: accent`で強調）／`message`（次デッキへの予告 or 最後の一押し）。

**01**: title="明日、よく頼む作業を1つテンプレートにしよう" / message="次回は、AIに何を・いつ・どれだけ読ませるかを扱う「コンテキストエンジニアリング」です。この後は、配布用テンプレートと出典一覧（付録）です。"

**02**: title="明日、同じ前提の置き場所を見直そう" / bullets先頭="明日やること：同じ『変わらない前提』を2回説明したら、ルール・スキル・参照資料のどこに置くか見直す"（`bold, color: accent`）/ message="次回は、AIが安全に動き、確かめて仕事を終える環境を扱う「ハーネスエンジニアリング」です。"

**05**: title="明日、5項目シートを1つ埋めよう" / bulletsは全7項目がフラット文字列（closingはbulletsが短ければフラットも許容される数少ない場所）/ message="まずは、繰り返している仕事をひとつだけ選んで、紙に描いてみてください。"（05は次デッキが存在しない最終回のため、message は次回予告ではなく**行動喚起の一押し**になっている）。

**規則**: titleは必ず「明日、〇〇しよう」型の行動喚起文にする。bulletsの1項目目（または最終項目）は次に取るべき具体行動を`bold, color: accent`で強調する。messageは次デッキがあれば「次回は、〜を扱う『（デッキ名）』です」の定型文、シリーズ最終回なら行動喚起の一押しにする。06/07は5層シリーズの外側にあるため、messageは次デッキ名ではなく「本編（02など）に戻って〜を試そう」という**還流の一文**にするのが実態に近い。

## 12. notes の文体（断定調・30秒〜1分・「さきほど／次は」の接続）

`loop-learnings.md`（ユーザー判断・2026-08-20）により**言い淀みは撤回済み**。notesは自信を持った断定調で書く。文字数実測（`series-diff-analysis-2026-08-20.md`）: 01=111字, 02=158字, 05=262字（05はやや長め、02は接続を伴う分やや長い）。

**例1**（01 S11、118字）: 「ここからAIへの依頼設計を組み立てます。**前章の**3つの質問に、なぜ（使い道）と守ること（条件）を足して、5つの要素に広げます。今回は頼み方を中心に必要な材料の指定まで扱い、コンテキスト自体の選び方・量・渡すタイミングは**次回**詳しく扱います。」

**例2**（02 S7、279字）: 「**前の2枚で**『コンテキスト』と『コンテキストエンジニアリング』を押さえました。この1枚は、整える範囲の違いです。…2つは世代交代ではなく、同じ依頼の中で重なって働きます。」

**例3**（02 S37 closing、280字）: 「本編のまとめです。コンテキストは、自動ロード、必要時に取得、今回の依頼で渡すという3経路で入ります。…**次回の**ハーネスエンジニアリングでは、権限・実行環境・ログといった外側の仕組みを扱います。」

**規則**: notesは「**さきほど／前の〇枚で／前章の**」で直前スライドを受け、「**次は／次回は**」で以降への接続を示す一文を必ず両端(または片端)に置く。全体は100〜200字（1分弱で読み上げられる分量）を基本とし、事実列挙・出典明示型で締める。言い淀み・「だと思います」等のヘッジ表現は入れない（間違っていたら後で訂正すればよい、が方針）。

## 13. table スタイルの定石（row_h/cell_size/col_widths）

layout_overridesの基準値: `header_h: 50, row_h: 62, header_size: 17, cell_size: 16`。各スライドはこの基準を出発点に、**列数・セル内の文字量に応じて`style.table`で個別上書き**する。

| 実例 | 列数 | col_widths | row_h | cell_size | 用途 |
|---|---|---|---|---|---|
| 01 S48（お手本4条件） | 3 | `[2, 4, 4]` | 94 | 16 | 短いラベル＋やさしい言い換え＋具体例。中程度の余裕 |
| 01 S50（出典1/5） | 3 | `[5.4, 2.2, 3.4]` | 118 | 17 | URLリンク付き資料名セルが長いため広め列＋大きめrow_h |
| 02 S20（経路×職種対応） | 3 | `[2.6, 3.4, 5.2]` | 92 | 15 | 説明文が長い右列を最も広く取る |
| 02 S21（章まとめ4列） | 4 | `[3.2, 2.4, 3, 3.4]` | 104 | 15 | 4列になるほどrow_hを100超まで拡張 |
| 02 S71（出典3/4、行強調） | 3 | `[2, 4.4, 5.6]` | 82 | 14 | `style.table.row_fills: {"4": "surface_sand"}` で特定行だけ背景を変え、教材上の整理行を視覚的に分離 |
| 05 S48（出典2/3） | 2 | `[3.4, 6.6]` | 58 | 16 | 列数が少ない時はrow_hを58まで縮め、cell_sizeを16に保つ |

**規則**: `col_widths`は絶対px値ではなく**相対比率**（合計が10前後になるよう配分）。文字量が多い列ほど比率を大きくする。row_hは列数×セル内行数に応じて58（2列・短文）〜120（3列・長文/複数行）まで伸縮させる。cell_sizeは13〜18の範囲で、row_hを詰めるときはcell_sizeも合わせて13〜14へ下げる。行単位で背景を変えたいときだけ`row_fills`を使う（多用しない）。

## 15. 図版の流儀：SVG/PNG構成比とimage_sideの振り方

### アセット構成比（実測）
| デッキ | SVG（`diagram-*.svg`） | PNG（`warm-*.png`） | 備考 |
|---|---|---|---|
| 01 | 19枚 | 3枚 | SVGは概念図（構造・対比・フロー）、PNGは「書きかけ文章」「多モーダル入力」など**具体シーンの挿絵**にのみ限定使用 |
| 05 | 13枚 | 15枚 | PNGがSVGとほぼ同数まで増加。抽象概念（ノード/エッジ等）はSVG、章の導入・比喩シーンはPNGという役割分担がより明確 |

いずれのデッキも`assets/`直下に`fig-*.png`という未参照の生成物が残存している（01=17枚, 05=20枚、`grep`で参照0件を確認済み）。これは`generate_assets.py`系スクリプトの中間生成物であり、**deck.jsonからは一切参照しない**（06/07制作時に同様の未使用ファイルを残さない、または残っていても無視してよい）。

### image_side の振り方
- **01**: 22枚中21枚が`image_side`省略（既定値`right`＝画像は右、本文は左）。明示的に`"left"`にしたのは1枚だけ（S3「学べること」で直前スライドと絵柄の対比を作るための単発切り替え）。＝**基本は右固定、変える時だけ理由がある**。
- **05**: `right`14枚／`left`14枚とほぼ完全な交互。ページをめくるたびに画像位置が入れ替わり、リズムを作る設計。

**規則**: 06/07は05型（左右交互）を採用する。理由: 05が最新改訂であり、`docs/deck-schema.md`が定める既定値（省略時right）に対して**明示的に毎回`image_side`を指定し交互にする**のは意図的な改善（単調さの回避）と判断できる。SVGは「構造・対比・フロー・階層関係を示す概念図」に限定し、PNGは「章の導入・具体的な業務シーン・比喩の情景」に使う棲み分けを維持する。`fig-*.png`のような中間生成物はdeck.jsonから参照しない。
