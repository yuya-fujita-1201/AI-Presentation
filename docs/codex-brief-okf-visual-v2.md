## 1. このタスクの背景（なぜこれをやるのか）

前バージョン `decks/okf-visual/`（21枚）は「画像だけのページ」と「文章だけのページ」が交互に並ぶ構成で、**画像が単なるイメージカットになり、重要な説明が別ページに分離していた**。発注者から「一目で内容が伝わらない」「他のチームメンバーが見ても一発で納得できるレベルにしたい」という指摘があった。

そこで v2 では **`image_text` という新しいスライドタイプ**を作り、1枚の中に「見出し → パンチライン（一目で伝える一文）→ 箇条書き本文 → 図 → キャプション」を同居させた。35枚中19枚がこの形式になっている。

**つまり図の役割が変わった。** 従来の「ページ全面を飾るイメージカット」ではなく、**隣に置かれた文章の内容を視覚的に理解させる図解**でなければならない。ここが今回の最重要ポイント。

### 変更禁止（絶対に触らないこと）

- `decks/okf-visual/`（旧21枚版。**温存対象**）
- `decks/graph-engineering/` および `decks/graph-engineering-visual/`
- `decks/okf-introduction/`、`decks/okf-knowledge-share/`
- `knowledge/` 配下（ナレッジは今回変更しない）
- `tools/build_deck.py`、`templates/`（image_text タイプは実装・検証済み。バグを見つけた場合だけ報告してよいが、勝手に仕様変更しない）

### あなたが触ってよいもの

- `decks/okf-visual-v2/assets/*.png`（**全19枚を差し替える**のが主タスク）
- `decks/okf-visual-v2/deck.json` の `style` / `caption` / 微修正（**§6 の範囲内でのみ**）
- `decks/okf-visual-v2/build/`（ビルド生成物。直接編集はせず再ビルドで更新）

## 2. 画像の共通仕様（全19枚に適用）

| 項目 | 指定 |
|---|---|
| サイズ・比率 | **4:3 の横長（1024×768 px 推奨、最低 800×600）**。表示領域が 524×378px なので、極端な横長・縦長は letterbox になり破綻する |
| 文字 | **画像内に文字を入れない**（日本語が崩れる／PPTXで拡大縮小時に読めなくなるため）。ラベルが要る場合はアイコンや記号で表現する |
| 画風 | フラットベクターイラスト風。立体的な3Dレンダリングやフォトリアルは不可。線は細め、面はソリッド |
| 配色 | **紫系で統一**。基調 `#460073`（濃紫）、アクセント `#A100FF`（明るい紫）、補助に薄紫 `#EDE4F7` と白。**紫以外の色相は原則使わない**（例外は §5 で個別に明記した箇所のみ） |
| 背景 | **白または極薄い紫のフラット背景**。写真的な背景・グラデーションの多用は不可（スライド背景が白なので、なじませる） |
| 余白 | 図の四辺に十分な余白。要素を端まで詰めない |
| 密度 | **1枚につき伝える概念は1つだけ**。要素は5〜7個までに抑える。情報を詰め込むと 524px 幅で潰れて読めない |
| 一貫性 | 19枚を通して**同じ画風・同じ配色・同じ線の太さ**。人物を描く場合は全枚で同じ描き方（顔の描き込みは最小限、記号的に） |

### 既存8枚も作り直す

`fig-01` 〜 `fig-08` は旧デッキから引き継いだファイルだが、**すべて 1942×809（比率 2.40:1）の横長**で、新しい 4:3 の表示枠にまったく合わない（上下に大きな余白が出て図が細い帯になる）。**19枚すべてを 4:3 で新規生成すること。** 旧デッキ側のファイルは触らない（別ディレクトリなので影響しない）。

## 3. 「良い図」の判断基準

生成した図を採用する前に、次を自問すること。1つでも No なら作り直す。

1. **隣の文章を読まずに図だけ見て、そのスライドが何の話か推測できるか？**（できないなら、それは単なる飾り＝不合格）
2. スライドの `punch`（パンチライン）と図の内容が一致しているか？
3. 図の中の要素数が7個以下か？ 524px 幅に縮小しても各要素が識別できるか？
4. 他の18枚と並べたとき、同じシリーズに見えるか？
5. 文字が入っていないか？

## 5. 画像生成の進め方（推奨）

1. **まず3枚だけ試作する**：`fig-11-library`（比喩の代表）、`fig-06-ecosystem-map`（構造図の代表）、`fig-05-human-ai-check`（フロー図の代表）。この3枚で画風・配色・線の太さを固め、**プロンプトの共通部分をテンプレート化**する
2. 試作3枚をデッキに入れてビルドし、**524×378px に縮小された状態で識別できるか**を実際のプレビューPNGで確認する（ここで潰れるなら要素を減らす）
3. 画風が固まってから残り16枚を生成する
4. 対（ペア）の図は連続して生成する：**#4↔#5（Before/After）** と **#7・#8（バラバラ→整列／箱→本棚）** は構図の一貫性が命
5. 生成した画像は `decks/okf-visual-v2/assets/` に**同じファイル名で上書き**する（deck.json のパスは変更不要）

### ImageGen へ渡す共通プロンプト骨子（日本語で書いてあるが、英語で投げてよい）

> フラットベクターイラスト、白背景、紫の配色のみ（濃紫 #460073・明紫 #A100FF・薄紫 #EDE4F7）、細い線と面のソリッド塗り、テキスト・文字・数字は一切含めない、記号的でシンプルな人物とロボット、余白を広く取った 4:3 の構図、ビジネスプレゼン向けの清潔な図解、要素は5〜7個まで

ここに §4 の「図の内容」を足して1枚ずつ生成する。

## 6. deck.json を触ってよい範囲

原則として文章は変更しない（発注者要望を反映して文言は確定済み）。ただし次だけは調整してよい。

- 画像を入れた結果、**キャプションと図の内容が食い違った場合の `caption` の修正**
- 図が大きすぎ/小さすぎる場合の該当スライドの `style.img` の調整（例: `{"img": {"w": 500, "h": 360}}`）
- 本文が枠から溢れた場合の `style.body.size` / `style.body.gap` の微調整

**やってはいけないこと**: スライドの追加・削除・順序変更、`title` / `punch` / `bullets` の書き換え、テーマ変更、`templates/` の編集。

文章に問題を見つけた場合は、直さずに**報告だけ**すること（発注者が判断する）。

## 7. ファクトシート（この範囲外の事実をスライドに足さないこと）

図の中に記号として事実を織り込む際、以下の範囲を超える主張をしないこと。

- OKF は **Google Cloud が 2026年6月12日に公開**したオープン仕様。v0.1 公開から約6週間後に **v0.2** へ改定
- 正体は **Markdown + YAML フロントマター**。プラットフォームではなくフォーマット。SDK 不要・ベンダー非依存
- **必須フィールドは `type` の1つだけ**（v0.2 でも変わらない）
- 予約ファイルは `index.md`（目次）と `log.md`（変更履歴）。この2つはフロントマター不要（例外としてバンドル直下の index.md だけ `okf_version` を書ける）
- v0.2 の5つの追加語彙: `sources`（出所）/ `generated`・`verified`（作成者と確認者を分離）/ `stale_after`（絶対日付の期限）/ `status`（draft・stable・deprecated）/ `type: Attested Computation`（検算）
- Attested Computation: 計算式をファイルとして固定し、AI にはパラメータへの値入力のみ許す。実行結果を「レシート」として返し、**LLM を使わない決定論的な attester** が「走った式が公認の式と一致するか」「表示値がレシートと一致するか」の2点を検査。不一致なら表示しない
- 関連標準: **MCP＝接続**、**OKF＝知識の中身**、**llms.txt＝知識の場所**、**AGENTS.md/CLAUDE.md＝AIへの指示書**（OKF はこのパターンを一般化）。OSI との住み分けは**解説動画の見解**であり公式見解ではない
- Google 公開のリファレンス実装: 拡充エージェント（BigQuery スキャン）、静的HTMLビジュアライザー、サンプルバンドル3種（GA4 / Stack Overflow / Bitcoin）
- Marie Haynes 氏の運用例: URLを渡す→AIが実行計画を提示→**人間が承認**→書き込み。毎日GitHubへバックアップ。type を作りすぎて最初は失敗した、と本人が語っている

**この一覧にない数値・固有名詞・実績を図に登場させないこと。**

### 独立検証で実際に見つかった誤りリスト（再発させないこと）

この deck.json は独立エージェント4体による検証を経て、次の誤りを修正済み。**図やキャプションで同じ誤りを再導入しないこと。**

| かつての誤り | 正しい内容 |
|---|---|
| 「type は3〜4個で十分」 | この数字に出典はない。Marie Haynes 氏は実際には7種類使っている。「作りすぎて失敗した」という定性的な反省談のみが事実 |
| 「レシートとして**残る**」 | 正しくは「レシートとして**返される**」。永続保存される仕組みではなく、その場の検査に使われる。レシートの形式自体は仕様が先送り中 |
| 「導入のハードルが**極めて**低い」 | ナレッジ元は「導入障壁が低い」。強調を盛らない |
| 「4ファイルは必要時のみ参照」の実験を Marie Haynes 氏の事例として扱う | **別人**。出典は note 記事（sutero 氏）の Obsidian 導入実験。混同しないこと |
| 検算（Attested Computation）を「5つの記入欄」の1つとして扱う | 検算だけはフロントマターの欄ではなく、**別ファイル＋外部の検査ツール**という別建ての仕組み。図でも「ラベルに書く4つ」と「別建ての1つ」を混同しない |

## 9. 参考：v2 で新設した `image_text` タイプの仕様

```json
{
  "type": "image_text",
  "title": "見出し",
  "punch": "一目で伝えたい一文（全幅・太字・アクセント色）",
  "bullets": ["本文（children で子項目も可）"],
  "path": "assets/figure.png",
  "caption": "図の下の補足",
  "image_side": "right"
}
```

- 領域: `title` / `rule` / `punch` / `body`（本文カラム 552×420px）/ `img`（**524×378px**）/ `caption` / `footer_l` / `footer_r`
- `image_side` を `"left"` にすると本文と図の左右が入れ替わる（`body` / `img` / `caption` の x 座標がキャンバス中心で反転する）
- 詳細は `docs/deck-schema.md` の `image_text` の項を参照
