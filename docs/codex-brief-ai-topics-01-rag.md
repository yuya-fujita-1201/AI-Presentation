## 1. このタスクの背景（なぜこれをやるのか）

このデッキは「RAG（Retrieval-Augmented Generation、検索拡張生成）」——社内の資料をAIに読ませて答えさせる仕組み——を、用語の意味から仕組み・壊れ方・導入判断まで扱う社内勉強会資料である。想定読者は、チャット型AIは使ったことがあるが社内システムとしてのRAGは未経験という段階の人（新入社員からSI/IT分野のコンサル・SE・エンジニアまで）。

デッキは `image_text` タイプ（見出し → パンチライン → 箇条書き本文 → 図 → キャプションを1枚に同居させるレイアウト）を多用しており、**35枚中20枚がこの形式**になっている。図の役割は「ページを飾るイメージカット」ではなく、**隣に置かれた文章の内容を視覚的に理解させる図解**でなければならない。ここが今回の最重要ポイント。

現状、`decks/06-rag/assets/` には `fig-rag-01.png`〜`fig-rag-20.png` が仮画像として置かれている。**清書として20枚すべてを本依頼の仕様に沿って再生成し、同じファイル名で上書きすること。**

## 2. 画像の共通仕様（全20枚に適用）

| 項目 | 指定 |
|---|---|
| サイズ・比率 | **4:3 の横長（1024×768 px 推奨、最低 800×600）**。表示領域が 524×378px なので、極端な横長・縦長は letterbox になり破綻する |
| 文字 | **画像内に文字を入れない**（日本語が崩れる／PPTXで拡大縮小時に読めなくなるため）。ラベルが要る場合はアイコンや記号で表現する |
| 画風 | フラットベクターイラスト風。立体的な3Dレンダリングやフォトリアルは不可。線は細め、面はソリッド |
| 配色 | **テーマ準拠配色**。現行 `meta.theme` は `accenture-purple` なので、仮版では基調 `#460073`（濃紫）、アクセント `#A100FF`（明るい紫）、補助に薄紫 `#F7F0FC` と白で統一する。**紫以外の色相は原則使わない**。ただし**清書時に `meta.theme` を切り替えれば別テーマの配色に変えられる**ので、色は将来差し替わりうる前提でハードコードした固有色に依存しすぎないこと（天秤・三角形・矢印など図形の意味は保ったまま配色だけ変わっても成立する構図にする） |
| 背景 | **白または極薄い紫のフラット背景**。写真的な背景・グラデーションの多用は不可（スライド背景が白なので、なじませる） |
| 余白 | 図の四辺に十分な余白。要素を端まで詰めない |
| 密度 | **1枚につき伝える概念は1つだけ**。要素は5〜7個までに抑える。情報を詰め込むと 524px 幅で潰れて読めない |
| 一貫性 | 20枚を通して**同じ画風・同じ配色・同じ線の太さ**。人物を描く場合は全枚で同じ描き方（顔の描き込みは最小限、記号的に）。ロボット＝AI、人物＝人間、という描き分けを全枚で統一する |

### 「棚」モチーフの繰り返しに注意

図1（社内キャビネット）・図15（書庫）・図19（棚に並ぶ書類）・図20（空の棚）の4枚は、いずれも「棚・書庫」を描く。**この4枚だけは棚の描き方（形・線の太さ・段数の見せ方）を統一すること**（同じ資産の別状態として見えるように）。

## 3. 「良い図」の判断基準

生成した図を採用する前に、次を自問すること。1つでも No なら作り直す。

1. **隣の文章を読まずに図だけ見て、そのスライドが何の話か推測できるか？**（できないなら、それは単なる飾り＝不合格）
2. スライドの `punch`（パンチライン）と図の内容が一致しているか？
3. 図の中の要素数が7個以下か？ 524px 幅に縮小しても各要素が識別できるか？
4. 他の19枚と並べたとき、同じシリーズに見えるか？
5. 文字が入っていないか？

## 5. 画像生成の進め方（推奨）

1. **まず3枚だけ試作する**：`fig-rag-03`（比喩・対比構図の代表）、`fig-rag-06`（構造図の代表）、`fig-rag-13`（フロー図の代表）。この3枚で画風・配色・線の太さを固め、**プロンプトの共通部分をテンプレート化**する
2. 試作3枚をデッキに入れてビルドし、**524×378px に縮小された状態で識別できるか**を実際のプレビューPNGで確認する（ここで潰れるなら要素を減らす）
3. 画風が固まってから残り17枚を生成する
4. 「棚」モチーフの4枚（`fig-rag-01` / `fig-rag-15` / `fig-rag-19` / `fig-rag-20`）は棚の描き方の一貫性を確認しながら連続して生成する
5. 生成した画像は `decks/06-rag/assets/` に**同じファイル名で上書き**する（deck.json のパスは変更不要）

### ImageGen へ渡す共通プロンプト骨子（日本語で書いてあるが、英語で投げてよい）

> フラットベクターイラスト、白背景、紫の配色のみ（濃紫 #460073・明紫 #A100FF・薄紫 #F7F0FC）、細い線と面のソリッド塗り、テキスト・文字・数字は一切含めない、記号的でシンプルな人物とロボット、余白を広く取った 4:3 の構図、ビジネスプレゼン向けの清潔な図解、要素は5〜7個まで

## 6. deck.json を触ってよい範囲

原則として文章は変更しない（発注者要望を反映して文言は確定済み）。ただし次だけは調整してよい。

- 画像を入れた結果、**キャプションと図の内容が食い違った場合の `caption` の修正**
- 図が大きすぎ/小さすぎる場合の該当スライドの `style.img` の調整（例: `{"img": {"w": 500, "h": 360}}`）
- 本文が枠から溢れた場合の `style.body.size` / `style.body.gap` の微調整（既に一部スライドで `style.body.size: 16` が設定済み。これは触った理由が分からなければ変更しない）

**やってはいけないこと**: スライドの追加・削除・順序変更、`title` / `punch` / `bullets` の書き換え、テーマ変更、`templates/` の編集。

文章に問題を見つけた場合は、直さずに**報告だけ**すること（発注者が判断する）。

## 7. ファクトシート（この範囲外の事実を図に足さないこと）

図の中に記号として事実を織り込む際、以下の範囲を超える主張をしないこと。すべて `knowledge/rag/` および `decks/06-rag/deck.json` の `notes` 由来。

- RAG = Retrieval-Augmented Generation（検索拡張生成）。「取ってくる（Retrieval）→ それを踏まえて書く（Generation）」の2段階。Google Cloud公式定義も同じ形（「事実を取得し、根拠ある回答を生成する」2段階プロセス）
- 必要とされる理由は2つ、どちらもLLM単体の性質に由来する: (1) 知識のカットオフ——学習時点で知識が止まる。社内文書はネットに非公開なので学習データに入りようがない (2) ハルシネーション——知らないことをそれらしく答えてしまう
- 原典は Lewis et al. (2020)、arXiv 2005.11401 / NeurIPS 2020。parametric memory（モデル重みに埋め込まれた知識）と non-parametric memory（外部索引から検索する知識）を組み合わせる構成。現在の「RAG」は特定の構成名ではなく手順の総称に広がった。**原典は取得漏れ・誤取得・古い文書・矛盾・権限違反を解決しない**
- パイプラインの数え方（3段・4段・5段）は粒度の違いにすぎない。事前準備（取り込み・パース→分割→ベクトル化→格納、資料を入れたとき1回）と応答（検索→再ランク→生成、質問のたび毎回）の2つの時間軸に分けると解消する
- 日本語企業文書の三大障害はPDFレイアウト崩れ・罫線帳票・スキャン画像。パース品質を最初に目視確認するのが鉄則
- チャンク分割: 小さすぎれば文脈が消え、大きすぎれば情報が薄まる。対策はセマンティックチャンキングとオーバーラップ
- 文脈付加（Anthropicの Contextual Retrieval）: 断片に説明文脈を足すと検索失敗率5.7%→3.7%（35%削減）
- 会話用LLMと埋め込みモデルは別物。埋め込みモデルの差し替えは索引の作り直しを伴う
- ベクトル検索は言い換えに強いが、型番・略語などの完全一致には弱い（「XR-2000」と「XR-3000」を取り違える例）
- ハイブリッド検索（ベクトル＋BM25）は実務標準。配合比の例はキーワード50%・意味50%だが最適値は質問内容に依存する
- 2段階検索（広く集めてから絞る＝リランキング）。Anthropicの実装は上位150件取得→上位20件へ絞る
- Anthropicが自社実験として報告した検索失敗率の推移: ベースライン5.7%→文脈付加3.7%(35%減)→+ハイブリッド2.9%(49%減)→+リランキング1.9%(67%減)
- 失敗点の7分類FP1〜FP7（Barnett et al. 2024）。3層に畳める: 層1資料が無い(FP1)／層2届いていない(FP2・FP3)／層3届いたのに取り出せない(FP4〜FP7)
- 本番でだけ出る5つの失敗（古い情報の使用・最新版の見落とし・矛盾の無視・文書の取り違え・ハルシネーション）。ハルシネーションを除く4つは「似た文書が複数ある」ことが発生条件で、PoCの小規模データでは構造的に作れない
- 索引内の件数の偏り: チャットの断片が数十万件、正式ドキュメントが数千件という報告がある。これは検索器の不具合ではなく入れたものの反映
- 評価枠組みはRagas (Es et al. 2023)。人手の正解データに依存しない3指標: Faithfulness（資料⇄答え）・Answer Relevance（質問⇄答え）・Context Relevance（質問⇄資料）。人間評価との一致率は0.95／0.78／0.70と報告
- 評価セットには壊れる条件を意図的に仕込む（改定前後・矛盾・類似資料・表記揺れ・答えの無い質問）。平均点ではなく致命傷で判定する
- 作るか借りるかは4択: Aマネージド／BOSSエンジン／C自作／Dローカル完結。手元に残るものが増えるほど自分で手当てできる範囲も増える
- 情報の外出しは「全部か無かではなく、どの工程まで外部に任せるか」という段階の問題
- 正本の一元化: 旧版を索引から外す・更新日と正式/メモの別をメタデータに持たせる・正本を誰が更新するか決める
- 導入は4段階（個人で試す→ノーコードツール→権限管理込みの社内連携→フルスクラッチ）。多くは2段階目まで進めば十分に効果が出るとされる
- RAGは学習しない。育てる対象は資料の側。答えられなかった質問は「資料が足りない場所の検出報告」として記録・棚卸しする
- 隣接概念との切り分け: 知識を変えたいならRAG、振る舞い（文体等）を変えたいならファインチューニング。情報過多はコンパクション、速度・コストの問題はプロンプトキャッシュ、単発検索の限界はエージェント的検索

**この一覧にない数値・固有名詞・実績を図に登場させないこと。**

## 9. 参考：`image_text` タイプの仕様

```json
{
  "type": "image_text",
  "title": "見出し",
  "punch": "一目で伝えたい一文（全幅・太字・アクセント色）",
  "bullets": ["本文（children で子項目も可）"],
  "path": "assets/figure.png",
  "caption": "図の下の補足",
  "image_side": "right"
}
```

- 領域: `title` / `rule` / `punch` / `body`（本文カラム）/ `img`（**524×378px**）/ `caption` / `footer_l` / `footer_r`
- `image_side` を `"left"` にすると本文と図の左右が入れ替わる（`body` / `img` / `caption` の x 座標がキャンバス中心で反転する）
- 詳細は `docs/deck-schema.md` の `image_text` の項を参照
