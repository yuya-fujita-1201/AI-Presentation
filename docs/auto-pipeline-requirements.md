## 1. 目的

「AIエンジニアリングシリーズ」の勉強会資料を、人の指示なしで継続生産する常設パイプラインを作る。

- シリーズは5段階: **①プロンプトエンジニアリング → ②コンテキストエンジニアリング → ③ハーネスエンジニアリング → ④ループエンジニアリング → ⑤グラフエンジニアリング**
- 超初心者向けに①から丁寧に。⑤グラフエンジニアリングは既にナレッジ・デッキとも完成済み（`knowledge/graph-engineering/`、`decks/_archive/graph-engineering/02-graph-engineering-visual/`）なので、その品質・プロセスが手本
- 1サイクルの理想形: **(a) 情報収集とOKFナレッジ整備 → (b) スライド原稿ドラフト → (c) deck.json生成+ビルド検証 → (d) Codexへの清書依頼書（codex-brief）発行**
- 勉強会は **2026年9月の新期から週1回**、ラジオ的にカジュアルに開催。1回30〜60分（質疑込み最大1時間）
- **9〜12月の4ヶ月で15〜16テーマ程度のストック**が長期目標（5段階シリーズの先のテーマはナレッジの育ち具合を見て提案）

## 3. 成果物仕様

- **品質基準 = `decks/07-okf-visual-guide/`（35枚・image_text型19枚・rubric全項目8点以上）**。これと同等以上
- デッキ枚数目安: 30〜35枚（発表30〜60分に対応）
- 仮版テーマカラーは **accenture-purple のまま**。清書時にCodexがテーマを差し替えられるよう、**色は必ずテーマトークンで指定**（hex直書き禁止・既存ルール）。将来「Claude風」等の汎用テーマを追加予定（テーマごとの差し色変更は不要）
- スピーカーノートは全スライドに書く（HTML専用。**PPTXには絶対に出力しない** — Keynote互換性破壊の既知問題）
- codex-brief は `docs/codex-brief-*.md`。手本は `docs/codex-brief-okf-visual-v2.md`（背景説明・変更禁止リスト・画像仕様・自己検証チェックリストの構成）
- 挿絵の生成はCodex担当（briefに仕様を書く）。Claude側は挿絵スロットとキャプションまで設計する
- デッキ命名は討議対象（例案: `decks/01-prompt-engineering/`）

## 6. 制約・防御的設計の要求（確定）

- ジョブプロンプトは **Sonnet 5 / Opus 5 前提の防御的設計**にする:
  - 手順を完全に明示（暗黙の判断を要求しない）
  - 各ステップに自己検証（実ファイル確認・ビルド実行・件数確認）
  - **「迷ったら何も書き換えず、状態ファイルに記録して終了」**を標準動作にする
  - 書き込み範囲を明示的に制限（許可パス以外は触らない）
  - 虚偽報告禁止: 実行していないことを完了と記録しない（グローバル原則）
- 多重起動防止（ロックファイル + stale検知）、1ランの実行時間・トークンの上限
- ユーザーが触れる **PAUSEスイッチ**（存在したら何もせず終了するファイル等）
- 失敗時: リトライは同一サイクル内で最小限、こじれたら記録して撤退（次サイクルが拾う）
- git がロールバック手段。**force push・履歴改変は禁止**
- タイムライン: 今日=2026-08-12。**第1弾は9月第1週の初回勉強会に間に合わせたい**（実質3週間）

## 7. 討議アジェンダ（この順で結論を出すこと）

- **論点A: ジョブ分割とスケジュール** — 1本のオールインワンジョブ（毎回stateを見て次の仕事を1つやる）か、役割別の複数ジョブか。cron式（時間帯・分オフセット）。工程ごとのモデル割当（Sonnet 5で足りる工程 / Opus 5が要る工程）
- **論点B: 状態管理** — stateファイルの形式・置き場所、フェーズ遷移（例: research → knowledge → draft → deck → grade → brief → done）、ロック、失敗時の遷移、git連携（コミット粒度・push失敗時）
- **論点C: リサーチ設計** — Webディープリサーチの手順と出典記録。YouTube: 優先チャンネル（§8）の新着走査 + 英日キーワード検索で**各テーマ5本程度**を選定する基準（再生数・新しさ・信頼性）、yt-dlp字幕取得の実手順、sources台帳への登録形式。1テーマを何サイクルに分割して蓄積するか。テーマ順序は5段階を厳守
- **論点D: 品質ゲート** — rubricの汎用化方法、採点ジョブの分離（maker≠graderをヘッドレスでどう実現するか）、8点未達時の改善ループ回数上限、機械ゲートの挿入位置
- **論点E: ジョブプロンプト** — 各ジョブのSonnet/Opus向けプロンプトの骨子（プロンプトアーキテクトが草案を提示し全員でレビュー）。プロンプトはリポジトリ内ファイルとして管理
- **論点F: 運用・監視** — launchd plist設計（StartCalendarInterval等・スキップ許容）、ヘッドレスの権限設計（settings allowlist vs スキップ、安全と無人継続の両立）、Pushover通知の内容と頻度（うるさすぎない設計）、ロールバック手順、**初回試走計画（監視付き手動実行→放流の手順）**
