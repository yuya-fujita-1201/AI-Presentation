## 想定読者（採点者はこの読者になりきる）

**SI プロジェクト（請負に近い形で、RFP から本稼働まで担う）のメンバー。** 3 つの層がいる。
- **AI 推進担当（2〜3名）**: Claude Code に習熟。9 月に OKF の初期構築をする人。デッキの「作る」章の主読者
- **実務メンバー（アプリ・アーキ・テスター、計 8 名）**: Claude Code は全員使えるが**不慣れ**。「育てる」「使う」章の主読者。コピペで動く依頼文を求めている
- **マネジメント層（PM・リード）**: AI に不慣れなこともある。「使う」章の壁打ちと「守る」章のルールの主読者
- 全員が 07（超入門）を読了している。ただし 07 のたとえ語（背表紙ラベル・身分証・3つの約束・知識のフォルダ）は**この資料では使わない**。使うなら冒頭の対応表で正式名（フロントマター・信頼性の欄など）に置き換えてある必要がある

読者が持ち帰るべき4点:
1. RFP・提案書・機能一覧から、OKF の初期ナレッジをどう作るか（誰が・何日で・何を投げるか）
2. 討議で確定・変更されていく要件を、OKF 上でどう更新し、経緯をどう残すか
3. 各工程・各層が、日々どう聞き、どう使うか
4. チームで壊さずに運用するためのルールと、やってはいけないこと

比較基準: `decks/07-okf-visual-guide/`（直前に合格した正本。文体・刻み・eyebrow/punch/caption 体系の基準）。

## 採点方式

- 採点者は**点数を書かない**。欠陥を findings として列挙する。点数は集約側が `100 − Σ(大20・中5・小1)`（下限0）で計算し、**項目ごとに 80 以上で合格**
- 採点者は 3 名並列。項目ごとの点は中央値。findings は和集合
- 機械で測れるもの（ビルド・枚数・PPTX・文字のはみ出し／重なり・SVG の明朝体フォールバック・closing 字数・Markdown 残留・AI 定型句の機械検出）は機械ゲートの担当。採点者は報告しない
- 各 finding には **再現箇所（slide-NN と実際の文言の引用）** を必ず付ける。引用できない指摘は無効
- 採点指摘も誤りうる。改善担当は実物と突き合わせてから直す（rejected の権利がある）

## 重大度

| 重大度 | 減点 | 定義 |
|---|---|---|
| 大 | 20 | 読者を止める／誤らせる／資料の信頼を損なう（OKF 仕様と矛盾する記述／出典の誤帰属／07 のたとえ語が無説明で出て読めない／図が本文と矛盾／前方参照で理解不能／上記4つの必須理解事項のどれかが答えられない／依頼文をコピペしても動かない致命的な欠落／機密（金額・個人情報）を書かせる手順） |
| 中 | 5 | 読めるが質が明確に落ちる（AI 定型句／「AではなくB」型・体言止めの3連続／抽象論の直後に例がない／同じ概念に別の比喩／留保なしの断定（本資料の提案を事実のように書く）／図が飾り／punch と caption の同一主張反復／専門的すぎる行と砕けすぎた行の同居／通し例（架空案件）の設定がスライド間で食い違う） |
| 小 | 1 | 気づく人は気づく（語尾の連続・表記ゆれ・1行の冗長・軽微な硬さ） |

## 項目

| # | 項目 | 見るもの（減点の実体） |
|---|---|---|
| 1 | 読者への適合 | 07 のたとえ語（背表紙ラベル・身分証・3つの約束）が置き換えられているか／初出専門語（フロントマター・CR・PR・CI・ADR 等）に平易な説明があるか／前方参照がないか／不慣れな実務メンバーが「自分の仕事の話だ」と思えるか。**理解度プローブ**: 必須4項目について「スライドの文言だけから一文で言えるか、何枚目で言えるようになるか」を実際に書く |
| 2 | 事実の正確性と誠実さ | OKF v0.2 の記入欄（status の3値・verified の書式・stale_after・sources）の使い方が仕様と矛盾しないか／「本資料の提案」と「仕様・出典のある事実」が区別されているか／ツール仕様（Claude Code・Copilot・GitHub Actions）を断定しすぎていないか／出典が追えるか |
| 3 | SI の現実味 | 工程（要件定義→設計→開発→テスト→リリース）・体制（PM1・アプリリード1・アーキリード1・アプリ4・テスター2・アーキ2）・契約（請負に近い、要件定義は準委任もある）・変更管理（CR）・正式文書（Office 形式で授受）と噛み合っているか／通し例（架空案件）が全章で一貫しているか／「クライアントは OKF を使わない」「金額・個人情報は書かない」が守られているか／推奨案（フォルダ構成・上書きと決定記録・確認者の二層）に理由と代替案があるか |
| 4 | 人間らしい文章（語句レベル） | AI 定型句／全角ダッシュ・丸数字の機械的多用／助詞を削った電報調・無主語文・ぶっきらぼうな体言止め |
| 5 | 人間らしい文章（構成レベル・文体の統一） | 「AではなくB」型の反復／体言止めの警句連打／punch と caption の同一主張反復／機械的な三点セット／同じ語尾の連続／専門的すぎる行と砕けすぎた行の同居／多少冗長でも人が書いた温かみがあるか。notes は自信を持った断定で構わない |
| 6 | 構成と段階性 | 冒頭が 表紙→位置づけ→おさらい（用語対応）→学べること→通し例→全体像→章扉 か／章が「作る→育てる→使う→守る」の順で、各章の切れ目で「何が分かったか」を言えるか／難易度が段階的か／closing が本編と対応しているか／40〜50 枚＋付録の厚みか |
| 7 | 図解・視覚の説明力 | **そのスライドで一番濃い色の要素が、一番伝えたい要素か**／図が本文を実際に説明しているか／図の要素数・呼び名が本文と一致するか／文字だけで済ませている難所（ライフサイクル・上書きと決定記録・確認者の二層）がないか／投影で読める文字サイズか／表とコードだけのページが続きすぎていないか |
| 8 | 実用性 | 依頼文（初期構築・議事録取り込み・毎朝の差分・工程別）がコピペでそのまま使える形か（［　］で置き換え箇所が明示、材料・守ること・報告の3点が揃う）／ひな形（要件ファイル・決定記録・CLAUDE.md・チェックリスト）があるか／9 月に AI 推進担当が着手できる具体度か／「返ってきたら人が確認する」が一貫しているか |
| 9 | 07 との整合と独立性 | 07 の続編として章扉・eyebrow「NN｜見出し」・punch（です・ます体の結論一文）・caption（橋渡し）・closing の体系が同じか／07 と矛盾する説明（status の意味・index.md の役割など）がないか／07 を読んでいなくても致命的に困らない導線（おさらい）があるか／記号（全角コロン等）が揃っているか |

## 減点しないもの（ユーザー承認済みの例外）

- punch の主張を末尾 bullet で締めに再掲する型（caption との一字一句同文の反復は引き続き減点）
- notes の断定調
- 付録（依頼文集・ひな形・出典）の情報密度が高いこと
- 章末の一言（quote）を各章のまとめに使う型（07 で確立済み）
- 依頼文（code スライド）の中の箇条書きが簡潔体で並ぶこと
