# 必須修正1：8枚目の「内包」は、まだ直っていない

現在は、

> ハーネスは上位互換ではなく、プロンプトとコンテキストを内包し実行・制御・検証へ広げる設計。

* 「プロンプトとコンテキストを内包する」

> 結局、ハーネスはコンテキストエンジニアリングの上位概念なのでは？

システム実装として、ハーネスがプロンプトやコンテキストを組み立ててモデルへ渡すことはあります。しかし、**エンジニアリングの観点としては、頼み方・判断材料・実行環境を分けて説明した方がシリーズとして一貫します。**

## 修正文案

> **プロンプト・コンテキスト・ハーネスは、別々の設計観点です。**
> ハーネスは、プロンプトやコンテキストを供給する経路に加え、実行・状態・制御・検証を設計します。

図についても、厳密な包含図ではなく、

* プロンプト／コンテキスト → モデルへ情報を渡す
* ハーネス → 情報供給、ツール実行、状態維持、制御、検証を仲介する

前回のコンテキスト資料では、コンテキストを「今回、モデルが参照できる情報」とし、CLAUDE.mdや検索結果は読み込まれたときにコンテキストへ入り、権限設定やフックは実行環境側のガードレールと整理していました。今回もこの定義を引き継ぐ必要があります。

# 必須修正5：48枚目のgVisor分類

48枚目は依然として、

> Container：namespace、cgroups、gVisor等
> host kernel共有とescape risk

という整理です。

これは技術的に不正確です。

通常のOCIコンテナはnamespaceやcgroupsを使い、ホストカーネルを直接共有します。一方、gVisorはユーザー空間にアプリケーションカーネルを置き、システムコールを仲介するサンドボックス化ランタイムです。通常コンテナと同じ行に置いて「host kernel共有」と一括りにすると、両者の隔離方式の違いが消えてしまいます。([gVisor][1])

## 修正後の分類

| 分類                | 仕組み                                       |
| ----------------- | ----------------------------------------- |
| OS native sandbox | Seatbelt、bubblewrapなど、ホストOSの機構でファイルや通信を制限 |
| 通常のOCI Container  | namespaces、cgroups。ホストカーネルを直接共有           |
| Sandboxed runtime | gVisor／runscなど。ユーザー空間カーネルでシステムコールを仲介      |
| microVM           | ゲストカーネルを持つ軽量VM                            |

「超入門」として4分類が細かいなら、gVisorを通常コンテナの例から外し、注記で、

> gVisorなど、通常コンテナより強い仲介層を持つランタイムもある

と説明するだけでも構いません。

# 必須修正6：49枚目の「stdio優先」

49枚目には、Local serverへの対策として、

> exact command表示、明示同意、sandbox、stdio優先

とあります。

「stdio優先」だけでは、何に対して、どの条件で安全なのか分かりません。

直接stdio接続は、HTTPサーバーを公開する場合よりネットワーク上の接続面を狭めやすい一方で、ローカルサーバーとして起動するコマンド自体が任意コード実行の入口になります。MCP公式のセキュリティ文書でも、ローカルサーバーやstdioプロキシを信頼境界として扱っています。([modelcontextprotocol.io][2])

## 修正文案

> **直接stdioは外部ネットワーク面を狭めやすい。
> ただし起動コマンド自体が信頼境界となるため、exact command表示、明示同意、許可リスト、Sandbox、監査を併用する。**
