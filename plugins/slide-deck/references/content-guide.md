# コンテンツ品質ガイド（deck.json を書く前に読む）

このプラグインの他の references（`deck-schema.md` / `themes.md`）は「きれいに見せる」ための仕様。
このガイドは**中身そのものの質**を上げるためのもの。デザインが整っていても、構成が悪い・タイトルが結論を言っていない・根拠がないスライドは伝わらない。deck.json を書き始める前に必ず目を通す。

対象読者はスライドを書く AI エージェント自身。ユーザーへの確認手順（6章）と依頼文の例（7章）はユーザーとの対話に使う。

## 1. 最初に決めること

deck.json を書く前に、次の4点を（ユーザーへの質問も含めて）明確にする。曖昧なまま書き始めると、後で全スライドを作り直す羽目になる。

- **聞き手（誰に）**: 意思決定者か実務者か。社内か社外か。前提知識はどのくらいあるか。
- **目的（聞き終わったあとに何をしてほしいか）**: 承認する／予算をつける／やり方を理解して自分で実行する／単に知っておく、など。目的が曖昧な資料は結論もぼやける。
- **時間と枚数の目安**: 1枚あたり1〜2分で話す前提で逆算する。持ち時間15分なら本編8〜12枚程度（表紙・アジェンダ・まとめを含む）。持ち時間が決まっていなければユーザーに確認する。
- **前提知識の深さ**: 専門用語をどこまで説明なしで使えるか。同じ内容でも聞き手が変われば説明の厚みが変わる。

これらが決まらないうちに構成（2章）や個別スライド（3〜4章）を作り込まない。

## 2. ストーリー構成の型

内容の性質に応じて型を選ぶ。どの型も「結論を先に見せてから積み上げる」か「積み上げてから結論に着地する」かの違いであり、思いつくまま並べるより明らかに伝わる。

### SCQA（状況・複雑化・問い・答え） — 現状を変える提案向け
Situation（状況）→ Complication（複雑化・困りごと）→ Question（では、どうする）→ Answer（答え＝本提案）の順で聞き手を引き込む。

骨子例（10枚）:
1. `title` — 表紙
2. `agenda` — 本日話すこと
3. `bullets`（Situation） — 現状はこうなっている
4. `bullets` または `matrix`（Complication） — このままだと何が起きるか
5. `quote` または `section`（Question） — 問いを一文で明示
6. `bullets`（Answer） — 提案の全体像
7. `steps`（詳細①） — どう実行するか
8. `two_column`（詳細②） — 代替案との比較
9. `table`（根拠） — 効果試算・実績データ
10. `closing` — まとめ・次のアクション

### PREP（結論・理由・具体例・結論） — 短時間で結論を通したいとき
Point（結論）→ Reason（理由）→ Example（具体例）→ Point（結論を再提示）。SCQA より短く、5分程度の説明や社内共有向け。

骨子例（8枚）:
1. `title`
2. `bullets`（Point） — 結論を先に言う
3. `bullets`（Reason） — 理由を2〜3個
4. `image_text` または `cards`（Example） — 具体例・事例
5. `table`（Example補強） — 数字での裏付け
6. `bullets`（想定される懸念への回答）
7. `closing`（Point再掲） — 結論と次のアクション

### 課題→原因→打ち手→効果 — 業務改善・施策提案向け
問題解決型。「何が困っているか」から入り、原因分析を経て打ち手と効果に至る、社内稟議で最も通りやすい型。

骨子例（10〜12枚）:
1. `title`
2. `agenda`
3. `bullets`（課題） — 何が起きているか（数字で）
4. `matrix` または `bullets`（原因分析） — 原因を構造化する
5. `section` — 「打ち手」への転換
6. `steps`（打ち手①） — 具体的な施策
7. `two_column`（打ち手②） — Before/After
8. `swimlane`（実行体制・フロー） — 誰が何をするか
9. `table`（効果） — 定量効果・KPI
10. `cards`（リスクと対策）
11. `closing` — 意思決定してほしいこと・次のアクション

### 比較検討型 — 複数案から選んでもらうとき
選択肢を並べて評価軸で比較し、推奨案を示す型。「決めてほしいこと」がはっきりしているときに使う。

骨子例（9枚）:
1. `title`
2. `bullets`（背景・選定の目的）
3. `cards`（選択肢の一覧） — 案A/B/Cの概要
4. `table`（評価軸×選択肢） — コスト・期間・リスク等で比較
5. `matrix`（位置づけ） — 2軸でのポジショニング
6. `bullets`（推奨案とその理由）
7. `steps`（推奨案の実行計画）
8. `cards`（リスクと対策）
9. `closing` — 判断してほしいこと・次のアクション

型はテンプレートであって鋳型ではない。内容に応じてスライドの追加・削減・並べ替えをしてよい。ただし「型を最後まで貫く」＝各スライドが型のどの位置にあるかを意識して書くと、抜け漏れと重複が減る。

## 3. 1枚のルール

- **1スライド1メッセージ**: そのスライドで伝えたいことは1つに絞る。2つ以上あるならスライドを分ける。
- **アクションタイトル**: タイトルは「〜の現状」「〜について」のような話題ラベルではなく、**そのスライドの結論を一文で言う**。
  - 悪い例: 「導入コストの現状」
  - 良い例: 「導入コストは初年度で30%削減できる」
  - 悪い例: 「新システムの特徴について」
  - 良い例: 「新システムは承認フローを3営業日から半日に短縮する」
- **根拠を本文に置く**: タイトルで言い切った結論の裏付け（数字・事例・出典）を本文（`bullets` / `table` / `lead`）に必ず置く。結論だけで根拠がないスライドは説得力を持たない。
- **粒度を揃える**: 同じ `bullets` の中で「戦略レベルの話」と「実装の細部」を混在させない。粒度が揃っていないと聞き手は重要度を誤解する。
- **専門用語は初出で説明**: 聞き手の前提知識（1章で確認）を上回る用語は、初めて出てきた箇所で一言添える（例: 「SCQA（状況→複雑化→問い→答えの説明順）」）。
- **抽象語を具体に置き換える**: 「最適化する」「推進する」「活用する」のような、何をするか分からない語は具体的な動作・数字に言い換える。
  - 悪い例: 「業務プロセスを最適化する」
  - 良い例: 「承認ステップを5段階から3段階に減らす」

## 4. 文字量と表現

- **見出し**: 25字以内（`deck-schema.md` の目安と一致）。長くなる場合は結論を削らず、修飾語を削る。
- **箇条書き**: 3〜6項目、各項目40字以内。7項目以上になるなら情報を絞るか `two_column` / `cards` に分割する。
- **体言止めと文の混在を避ける**: 同じ `bullets` 内で「〜を実施」「〜する予定」のように文末の型を混ぜない。箇条書き全体で体言止め（例: 「工数30%削減」）か文（例: 「工数を30%削減する」）のどちらかに揃える。
- **数字は単位と比較対象を付ける**: 「向上」「増加」だけでは伝わらない。「何から何へ」「何と比べて」を必ず添える。
  - 悪い例: 「処理速度が向上」
  - 良い例: 「処理速度が2.3秒から0.8秒に短縮（対前バージョン比65%減）」
- **図解が効く内容はネイティブ図解タイプで表す**: 次のような内容は文章の箇条書きより図の方が一瞬で伝わる。無理に `bullets` へ押し込めず、対応する型を使う（`deck-schema.md` 3章「スライドタイプの選び方」も参照）。
  - 手順・フロー → `steps` / `swimlane`
  - 比較 → `two_column` / `table`
  - 位置づけ・2軸評価 → `matrix`
  - 構造・分類・並列要素 → `cards`
  - システム構成・連携 → `architecture`
  - データの流れ → `dataflow`
  - 状態・ステータス遷移 → `lifecycle`
  - API 呼び出し・やり取りの順序 → `sequence`

## 5. 締め（closing）

`closing` スライドは感想や振り返りで終わらせない。必ず次の2点を明示する。

- **次のアクション**: 誰が・いつまでに・何をするか（例: 「来週金曜までに部門予算案を確定」）。
- **判断してほしいこと**: 聞き手に今この場で、または持ち帰って決めてほしいことを明示する（例: 「A案での予算確保についてご承認をお願いします」）。承認・選択・情報提供依頼のどれを求めているかをぼかさない。

## 6. 執筆前チェックリスト

deck.json を書き始める前に、次を自分の中で（または該当する場合はユーザーに確認して）満たしているか確認する。

1. 聞き手が具体的に言えるか（役職・部門・人数感）
2. 目的（聞き終わった後にしてほしい行動）が一文で言えるか
3. 想定の時間・枚数が決まっているか（1枚1〜2分換算）
4. 構成の型（2章）を1つ選んだか
5. 各スライドがその型のどの位置にあるか説明できるか
6. 全スライドのタイトルを結論文で仮に書き出せたか（1枚1メッセージになっているか）
7. 各スライドに根拠（数字・事例・出典）を置く場所があるか
8. 抽象語（最適化・推進・活用等）を具体的な動作・数字に言い換えたか
9. 図解が効く内容をネイティブ図解タイプに割り当てたか（画像に逃げていないか）
10. `closing` に次のアクションと判断してほしいことを入れる計画があるか

### ユーザーへの確認は最初に1回だけまとめて聞く

情報が足りないときは、スライドを作りながら小出しに聞き返さず、**着手前に次の項目をまとめて1回で質問する**。すでに分かっている項目は聞き返さない。

- 聞き手は誰か（役職・部門・人数、社内/社外）
- 目的（聞き終わった後に何をしてほしいか）
- 想定の時間・枚数
- トーン（フォーマル／カジュアル、社内向け／社外向け）
- 既存資料の有無（叩き台の deck.json、参考にしたい過去資料、ロゴ・データなどの素材）

## 7. ユーザー向けの「良い頼み方」の例文

ユーザーがこのプラグインで依頼するときの参考例。目的・聞き手・枚数・強調点が含まれているほど、1章の手戻りが減る。

1. 「経営会議向けに、新規事業の予算承認を得るための資料を10枚程度で作って。聞き手は役員5名で、この分野に詳しくない前提。特に投資回収期間の根拠を厚めにしたい。」
2. 「新入社員向けの社内システム操作研修を、15分で話せる分量（8枚くらい）でお願い。目的は研修後に自分でアカウント申請ができるようになること。専門用語は都度説明して。」
3. 「他部署への進捗共有会で使う資料。目的は次工程への引き継ぎ承認をもらうこと。聞き手は関連部署の担当者3名で背景は知っている前提。スケジュール遅延の原因と対策を一番強調したい。枚数は6枚以内で。」
